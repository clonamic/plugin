# 플랫폼 프로필: kakao-chatbot (카카오톡 채널 챗봇)

이 파일은 플랫폼 제약 검사관, 대화 UX 설계자, 런타임 아키텍트, 표시 형식·응답 시간 검사관, 심사 관점 분석가가 읽는다. 조직 자체는 플랫폼을 모르고, 플랫폼 지식은 이 프로필에만 둔다(대회 뒤 다른 플랫폼으로 재사용하기 위해서). 출처는 대회 프로젝트의 `CLAUDE.md`·`README.md`·`docs/kakao_bot_docs.md`이고, 확인하지 못한 것은 **확인 필요**로 적었다.

## 1. 구조 (요청 한 번의 흐름)

1. 카카오가 서버 웹훅으로 메시지 이벤트를 보낸다(`MESSAGE_CREATE`, `callbackToken` 포함).
2. 서버는 **1초 안에 2xx**(빈 204)만 돌려준다. 답은 여기 넣지 않는다.
3. 백그라운드에서 에이전트가 답을 만든다.
4. 서버가 **콜백 API**로 답을 한 번 보낸다.

## 2. 하드 제약 (어기면 봇이 깨진다)

| 제약 | 값 | 설계에 주는 영향 |
|---|---|---|
| 웹훅 응답 | 1초 안에 2xx | 핸들러에서 LLM·DB 호출 금지(이미 뼈대가 지킴) |
| callbackToken | **1회용, 5분 만료** | 한 질문에 답은 **한 번만**. "처리 중…" 같은 중간 메시지 불가. 처리 예산은 프로젝트 설정(예: 호출당 90초, 전체 240초) |
| 말풍선(outputs) | 1~3개 | 긴 답은 3개로 잘리고 넘치면 말줄임 |
| simpleText | 1000자 | 말풍선 하나에 1000자 |
| quickReplies(바로가기 버튼) | 최대 10개 | 선택지형 대화가 가능 |
| 서식 | 마크다운이 렌더링되지 않음 | 표·헤더 금지, 줄바꿈과 짧은 목록만 |
| 봇이 먼저 말 걸기 | `send_message`(토큰 없이 가능), **하루 1000건** 제한 | "매일 아침 알려줘"는 가능하지만 스케줄러·대상 관리가 필요(비용 큼) |
| 사용자 식별 | 1:1은 `botUserKey`, 단체방은 `botGroupKey` | 개인화 단위 = botUserKey |
| 호출 허용 IP | 콘솔에 서버 IP 등록 필요 | 서버 IP가 바뀌면 콜백 실패 |
| 웹훅 vs 게이트웨이 | 웹훅 등록 중엔 게이트웨이(로컬 테스트) 불가 | 대회 중 로컬 실기 테스트 대신 서버 배포 후 실기 |

확인 필요: 사용자가 보낸 **이미지·파일**을 웹훅이 어떤 형태로 넘기는지, 카드형(basicCard, carousel) 출력을 콜백에서 쓸 수 있는지. 요구사항이 이것에 기대면 플랫폼 제약 검사관이 **주의**로 판정하고 결정(D1)으로 올린다.

## 3. 요구사항 실현 가능성 판정 가이드

| 인물이 원하는 것 | 판정 | 인물에게 물을 대안(기술 용어 없이) |
|---|---|---|
| "아침마다 알려줘" (봇이 먼저) | 주의 | "제가 먼저 보내 드리는 게 좋으세요, 아니면 '오늘'이라고 치시면 바로 알려 드리는 게 괜찮으세요?" |
| 긴 보고서·표 | 주의 | "핵심 세 줄만 먼저 보고, 자세한 건 버튼을 눌러 보는 건 어떠세요?" |
| 버튼으로 고르기 | 가능 | (10개 이하로 묶기) |
| 이전 대화 기억 | 가능 | 뼈대에 기억·프로필 저장이 있음(프로젝트 바인딩의 사실 참고) |
| 여러 사람이 같이 쓰기 | 주의 | 단체방이면 사람마다 기억이 분리됨 — "가족/직원분들도 같이 쓰시나요?" |
| 결제·환불 처리 | 불가(범위 밖) | 사람에게 넘길 조건으로 처리 |
| 사진 보고 판단 | 확인 필요 | 2절 참고 |
| 실시간 외부 정보(날씨, 길찾기) | 주의 | 당일 쓸 수 있는 API 키가 있어야 함 → 통합 담당이 확인, 없으면 D1 |

## 4. 대화 UX 기본값 (인물 패턴으로 덮어쓴다)

- 카톡은 한 손으로 짧게 쓰는 환경이 기본이다. 답은 3~5줄, 자세한 건 버튼으로.
- 존댓말 기본, 이모지는 인물 말투에 맞춰(인물이 안 쓰면 쓰지 않음).
- 첫 방문: 짧은 인사 + 바로 쓸 수 있는 버튼 2~4개. 뼈대에 온보딩 문구가 있다(프로젝트 바인딩 참고).
- 모를 때: "모른다" + 다음 행동 버튼(다시 묻기, 담당자 연결 등).
- 처리 시간이 길어도 중간 메시지를 보낼 수 없다 → 질문을 받은 즉시 답이 오는 것처럼 보이게 처리 시간을 줄이는 쪽으로 설계한다.

## 5. 기술 결정 게이트 기본 항목

이미 정해진 것(프로젝트 바인딩 `[runtime] fixed_decisions`)은 다시 논의하지 않는다. 남는 기본 항목:
1. 그래프 구조를 바꿀지(기존 RAG 그래프에 노드·도구 추가 vs 새 분기)
2. 데이터 배치: 표(SQLite·SQL 질의), 문서(벡터 검색), 사람별 기억(관계형+벡터)
3. 인물 데이터를 공용(`scope=shared`)으로 깔지, 인물 전용으로 둘지
4. 외부 API 추가 여부(키 확보 가능성)
5. 버튼(quickReplies) 중심 대화 vs 자유 입력 중심
6. 선제 발송(send_message) 사용 여부
7. **심사자가 처음 들어왔을 때**: 인물 데이터를 공용으로 깔고 온보딩(사용자 결정) — 심사자를 인물로 취급할지(데모 모드), 새 사용자로 취급할지는 열린 결정

## 6. QA 기준

**표시 형식 검사관**
- 말풍선 ≤ 3, 말풍선마다 ≤ 1000자, 넘치면 말줄임 위치가 문장 중간이 아닌지
- quickReplies ≤ 10, 라벨이 짧고(14자 안팎) 겹치지 않는지
- 마크다운 표·헤더·`**` 강조가 남아 있지 않은지
- 개인정보(전화번호·이메일)가 마스킹되는지

**응답 시간 검사관**
- 처리 예산(예: 전체 240초) 안에 끝나는지. 실사용 체감 목표는 대부분 30초 이내
- 대체 모델로 넘어갔을 때도 예산 안인지, 말투가 크게 바뀌지 않는지

**맞춤 적합성 심사관**
- 첫 메시지부터 "이 사람용"이라는 게 보이는지(이름, 말투, 바로 쓸 버튼)

## 7. 심사자의 첫 3분 (심사 관점 분석가)

- 심사 기준이 공개되기 전까지는 모두 **추측**으로 다룬다.
- 심사자는 인물 본인이 아니다. 처음 들어온 사용자에게 무엇이 보이는지가 첫인상이다.
- 데모 시나리오에 "인물 패턴 → 봇 동작" 표(개인화 표)의 근거를 한두 장면으로 보여 준다.
