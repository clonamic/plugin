# 플랫폼 프로필: generic (특정 플랫폼 없음)

프로젝트 바인딩(`project.toml`)이 프로필을 정하지 않았을 때 쓰는 기본 프로필이다. 플랫폼 제약은 모른다고 가정하고, 제약에 기대는 요구사항은 모두 **확인 필요**로 다룬다.

## 1. 기본 원칙

- 요구사항마다 실현 가능성을 판정할 근거가 없으면 `feasibility: "주의"`, `feasibility_note: "플랫폼 제약 미확인"`으로 두고, 확인할 사실을 결정(D2)으로 올린다.
- 인물에게 기술 제약을 설명하는 질문은 만들지 않는다. 필요하면 "A와 B 중 어느 쪽이 괜찮으세요?"처럼 고르게 한다.

## 2. 확인할 플랫폼 사실 (기술 위원회가 처음에 채운다)

| 항목 | 왜 필요한가 |
|---|---|
| 응답 시간 한도 | 그래프 단계 수와 모델 선택이 바뀐다 |
| 메시지 길이·개수 한도 | 응답 형식이 바뀐다 |
| 서식(마크다운, 버튼, 카드) 지원 | UX 설계가 바뀐다 |
| 서버가 먼저 메시지를 보낼 수 있는지 | 알림형 요구사항의 실현 가능성 |
| 사용자 식별자 | 개인화 단위 |
| 이미지·파일 입력 | 입력 처리 범위 |

## 3. QA 기준

- 표시 형식: 플랫폼 한도를 모르면 "짧게(5줄 이내) + 다음 행동 제시"를 기준으로 본다.
- 응답 시간: 대부분 30초 이내를 목표로 한다.
