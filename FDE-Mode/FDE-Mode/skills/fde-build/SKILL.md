# 구현 루프 (P4, P5)

핵심 동결이 승인되면 구현 조직이 **백그라운드**에서 움직이고, 메인 대화는 지휘만 한다(사용자 결정: 구현은 백그라운드, 메인은 지휘). 인터뷰는 확장 기능 위주로 계속된다.

## 1. 원칙

1. **얇게 끝까지 먼저.** 조각 1은 must 기능 하나를 실제 플랫폼에서 동작하게 끝까지 연결해 배포한 것이다. 인물 이름·말투·시드 데이터가 들어간 상태로. 기능을 다 만든 뒤 마지막에 한 번 배포하는 방식은 대회에서 가장 흔한 실패 원인이다.
2. **배포할 때마다 정상 버전을 태그로 남긴다**(`fde-good-<조각>`). 어느 시점에 멈춰도 제출 가능한 상태를 유지한다.
3. **명령은 바인딩에서만.** 테스트·배포·헬스·로그는 `project.toml [commands]`에 적힌 명령만 쓴다. 인프라 생성·삭제 명령은 쓰지 않는다(가드가 막는다).
4. **배포는 한 번에 하나.** 여러 조각이 동시에 배포하지 않는다(코드가 순서를 잡는다).
5. **독립 리뷰.** 리뷰 본부와 QA 본부는 구현 과정을 보지 않고 결과만 본다. 맞춤 적합성 심사관은 spec.md를 보지 않고 인물 모델과 실제 봇 답만 본다.
6. **협업 모드가 기본.** 구현은 백그라운드지만 설계와 진행은 사용자와 같이 정한다: 조각마다 설계 확인 → 구현 → 구현 중 설계 질문 → 리뷰 → 첫 배포 확인 → QA → 진행 확인. 자율 모드(스위치 `autonomy`)는 사용자가 "자율 모드로 해"·`/fde-mode auto on`처럼 명시했을 때만 켠다 — 그때는 D2를 추천으로 자동 결정하고 설계 확인은 추천 적용, 첫 배포 확인·진행 확인은 건너뛴다(fde-director 10절).

## 2. 흐름 (조각마다, `fde next`가 진행)

설계(설계 본부장 + 필요한 설계자 + 디테일 설계자 항상) → **설계 확인**(협업) → 명세 추적 → 구현(파일이 겹치지 않는 작업끼리 동시에) → **구현 중 설계 질문**(협업) → 독립 리뷰(코드 리뷰어, 명세 대조관) → 반려면 재작업(최대 2번, 그다음 개발 본부장 + D1) → 배포(테스트 → 배포 → 헬스, 협업이면 첫 배포와 되돌린 뒤 첫 배포는 **배포 확인**) → QA 7석(시나리오, 가상 사용자, 응답 시간, 표시 형식, 맞춤 적합성, UX, AI티) → QA 본부장 판정 → 통과면 릴리스 관리자가 정상 태그 + 관측 담당이 로그 확인 / 실패면 수정 조각 생성 → **진행 확인**(협업, QA 통과 뒤). 배포 실패면 릴리스 관리자가 마지막 정상 태그로 되돌린다. 조각 단계는 15개다(`references/pipelines.md`).

협업 단계(D2 — 설계 결정점은 D1일 수도 있다. 답이 올 때까지 그 조각이 기다린다):

| 단계 | 질문 | 답 뒤 |
|---|---|---|
| 설계 확인 | "[설계·조각 N] <제목>" — 설계 본부장의 결정점(선택지·장단점·예상 분·추천, 등급 D1이면 D1) | `runs/<조각>/design-choices.json` → 명세 추적·구현 입력 `design_choices` |
| 구현 중 설계 질문 | "[구현 중 설계·B-xxx] <제목>" — 개발자가 혼자 정하지 않고 `tasks_blocked`의 `design_question`으로 넘긴 갈림길 | 그 작업을 재작업으로 되돌리고 리뷰 메모 "사용자 설계 답(D-…): … → …"로 다시 구현 |
| 배포 확인 | "조각 N을 배포할까요? (첫 배포/되돌린 뒤 첫 배포)" [배포, 보류(이유를 적어 주세요)] | 배포 / 보류면 조각 중단(failed), 지금 배포된 버전 유지 |
| 진행 확인 | "조각 N 배포·QA 통과. 다음은 어떻게 할까요?" [다음 조각 진행(남은 조각이 없으면 이대로 유지), 수정 요청(무엇을 고칠지 적어 주세요), 설계 재검토] | 다음 조각 출발 / 자유 글 = 수정 요청 → 변경 통제 `CH-NN` / 설계 재검토 → 재계획 `RP-<조각>-review` / 라벨만 오면 고칠 내용을 다시 묻는다 |

- 협업 D2는 기본으로 상한이 없다(자율 모드를 명시적으로 켜기 전까지 설계 질문은 모두 묻는다). 바인딩 `[collab] max_questions`에 양수 N을 주면 조각마다 N개까지(설계 확인·구현 중 설계 질문에만 — 첫 배포 확인·진행 확인은 늘 묻는다). 설계 결정점이 없는 조각도 "[설계·조각 N] 이 설계대로 구현할까요?"를 한 번 묻고, 바꿀 점을 적으면 설계자가 그 말로 다시 설계한다(조각당 2번까지). 넘으면 추천으로 진행하고 알림을 낸다. "추천대로" 답은 그 결정의 추천 라벨로 기록된다.

## 3. 디렉터가 사용자에게 가져오는 것

- **사람이 할 일**(`human`): 조각이 통과하면 QA 본부장이 고른 메시지 2~3개를 실제 카톡(또는 플랫폼)으로 보내 보라고 요청한다. 사용자가 결과(봇 답 화면 내용)를 붙여넣으면 `>>메모`로 받아 다음 QA에 반영된다.
- **막는 결정**: 리뷰 2번 반려, 배포를 막는 D1, 외부 API 키가 필요한 작업 등은 바로 묻는다.
- **협업 질문**(협업 모드): 설계 확인, 구현 중 설계 질문, 첫 배포 확인, 진행 확인. 그 조각을 막고 있으므로 `ask`에 나오면 라운드 보고를 기다리지 않고 바로 선택지로 묻는다(추천을 맨 위에 "(추천)"). 글을 받는 선택지("수정 요청(무엇을 고칠지 적어 주세요)", "보류(이유를 적어 주세요)")는 사용자가 쓴 문장을 그대로 `fde decide`에 넘긴다.
- **진행 알림**: 조각 시작/배포/통과/실패를 한 줄씩. 자세한 것은 대시보드 구현 탭.

## 4. 플랫폼에서 사람이 직접 해야 하는 일

봇 교체, 토큰 교체, 웹훅 URL·헤더 등록, 호출 허용 IP 등록처럼 **콘솔에서 사람이 해야 하는 일**은 에이전트가 대신하지 않는다. 바인딩의 체크리스트(예: 대회 프로젝트의 `docs/DAY_OF_CHECKLIST.md`)를 따라 사용자에게 요청하고, 끝나면 헬스 확인을 다시 돌린다.

## 5. 비밀값과 설정

- `.env`는 읽지 않는다. 확인은 `fde env check`(set/empty), 비밀이 아닌 값 변경은 `fde env set KEY VALUE`(바인딩 `env_editable`만).
- 토큰·비밀 헤더 교체(`make token`, `make secret` 같은 것)는 가드가 사용자 확인을 요구한다. 사용자가 직접 실행하게 안내한다.

## 6. 실패했을 때

- 배포 실패 → 자동 되돌리기 실행(`RB-…`). 되돌리기도 실패하면 D1: "마지막 정상 버전으로 수동 복구할까요?"와 함께 로그 요약을 보여 준다.
- 같은 테스트가 계속 실패하면 개발 본부장(unblock)이 해결하거나 사용자 결정으로 넘긴다.
- 기능 동결 시각이 다가오면 새 조각을 시작하지 않고 안정화로 전환할지 시간 예산 관리자의 수치와 함께 묻는다(D2).
