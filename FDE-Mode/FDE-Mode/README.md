# fde-mode (FDE-Mode)

## 핵심 요약

- 고객(인물)을 인터뷰하고 그 사람에게 맞는 에이전트 서비스를 만들어 배포하는 일을, Claude Code 안에서 **FDE(현장 배치 엔지니어) 조직**처럼 돌리는 플러그인이다.
- 사용자가 직접 쓰는 명령은 **`/fde-mode` 하나**다(켜기·끄기·상태·리허설). 나머지는 훅과 워크플로 엔진(`fde next`)이 자동으로 진행한다. 켜진 상태는 DB에 저장돼 세션을 다시 열어도 이어지고, `/fde-mode off`(회고가 끝나면 디렉터가 끌지 묻는다) 전까지 유지된다.
- 조직은 **18개 본부·94명의 서브에이전트**다. 모델은 전원 `claude-opus-5-5`, 추론 강도는 일반 `high`(65명)·판단·통합·중재 `xhigh`(29명)다.
- 사용자는 인물과의 대화를 복사해 붙여넣기만 한다. 조직은 서로 다른 관점으로 분석하고, 팀 안에서 보완하고, 본부끼리 토론하고, **토론 기록을 보지 않는 독립 검증석**을 거쳐, 확신도 **[확실] / [가능성 높음] / [추측]**이 붙은 질문 카드와 사용자가 정할 **D1/D2/D3 결정**을 나눠서 돌려준다.
- 그다음 기술 결정 게이트 → 단계적 동결("제작 시작해도 될까요?") → 구현 조직(설계·디테일 설계·구현·독립 리뷰·배포·QA 7석·릴리스 태그·롤백) → 마감·회고까지 같은 엔진이 이어서 돈다. 구현은 기본이 **협업 모드**다: 조각마다 설계·첫 배포·진행을 선택지와 추천으로 묻고, 자율 모드는 사용자가 명시할 때만 켠다.
- 모든 상태는 프로젝트별 `.claude/fde-mode/`(SQLite + 파일)에 남는다. 로컬 대시보드(127.0.0.1)는 읽기용이고, 결정은 메인 대화 안에서 선택지로 묻는다.
- 안전 훅이 인프라 삭제·비밀값 출력·강제 push를 막고, 분석 에이전트의 코드 수정과 독립석의 토론 기록 읽기, 시험용 봉인 폴더 읽기를 막는다.
- 플랫폼 지식은 프로필 파일(`profiles/*.md`)에, 프로젝트 지식은 바인딩(`project.toml`)에만 둔다. 그래서 대회(Kakao AI TOP 100, 카카오톡 채널 챗봇)가 끝난 뒤에도 다른 프로젝트에 그대로 쓴다.

## 1. 문제와 목표

### 1.1 왜 만들었나

대회는 5시간 안에 가상 인물을 인터뷰하고, 데이터를 모으고, 그 사람에게 맞는 AI 에이전트를 만들어 카카오톡 채널 챗봇으로 제출하는 형식이다. 사람 혼자 하면 네 가지가 무너진다.

| 무너지는 곳 | 이 플러그인의 대응 |
|---|---|
| 무엇을 더 물어야 하는지 놓친다 | 서로 다른 관점의 분석가 수십 명이 같은 대화를 각자의 렌즈로 보고, 빈틈을 질문 후보로 낸다 |
| 비판적으로 보이려고 억지 질문이 섞인다 | 독립 검증석(블라인드 검증관·반론관)과 결정표가 억지·이미 답한 것·영향 없는 것을 걸러 내고, 남은 카드에 확신도와 근거 발화를 붙인다 |
| 사용자가 정할 일과 인물에게 물을 일이 섞인다 | 질문 카드(인물에게)와 결정(D1/D2/D3, 사용자에게)을 분리하고, 결정은 대화 안에서 선택지로 묻고 Stop 훅이 묻지 않고 끝내는 것을 막는다 |
| 묻다가 만들 시간을 잃는다 | 동결 검사·동결 판단관·시간표가 "이제 만들어도 된다"를 판단하고, 구현은 백그라운드 조직이 조각 단위로 배포한다 |

### 1.2 사용자의 원래 요구 (요약 인용)

- "요구사항 분석과 내가 더 물어봐야하는것들 이런걸 객관적이고 비판적인 시선에서 개선하고, 보완해주는게 중요해. 그리고 [확신]과 같이 확신정도를 바탕으로 내가 진짜 물어봐야하는지, 아니면 그냥 클로드가 비판적으로 억지스럽게 말한건지 판단하기 쉬워야해."
- "각 단계별 관점을 다르게 두고, 빠진것을 찾아라가 아니라, 세부적인 빈틈과 관점이 필요해. … 사용자의 패턴파악같은 로직들도 필요해보여. … 그 모든 팀들이 모여서 하나의 거대 FDE 조직이 되는거지."
- "더 자세한 계층과 역할로 나눠줘. 대신 너무 독립적 분리가 아니라 하나로 상호보완과 토론도 되도록."
- "opus5.5(high)를 일반, 핵심은 opus5.5(xhigh)로 하자. … 로컬의 sqlite3를 사용해서 저장하는 방식도 좋아. AI top 100 대회가 끝나고도 사용을 위해 프로젝트 단위로 나눠서 격리시키면 되니까."
- "내가 활성화 해야 사용되는 스킬(플러그인)은 슬래시 FDE-Mode 1개야. 나머지는 자동사용이고, 흐름 설계도 확실히 되어야해. 기술스텍에 대한 결정도 그 과정에서 있어야해. … 물어봐야하는것, 내가 결정해야하는것 전부 나눠서 나한테 주고, 물어보도록 시키고, 물어봐야해."

### 1.3 하는 것과 하지 않는 것

| 구분 | 내용 |
|---|---|
| 하는 것 | 붙여넣은 인터뷰의 결정적 저장과 발화 번호, 다관점 분석, 팀 보완·본부 토론·중재, 독립 검증, 확신도·영향도가 붙은 질문 카드, 사용자 결정 큐와 강제, 인물·인터뷰어 패턴 지표, 문제 설명 분석, 환경·패키징 분석, 기술 결정 게이트(ADR), 단계적 동결과 변경 통제, 데이터 수집·검증·정제·적재·출처 감사, 조각 단위 설계·구현·리뷰·배포·QA·릴리스·롤백, 마감 체크리스트, 회고와 전역 교훈, 리허설 채점, 로컬 대시보드, 안전 가드 |
| 하지 않는 것 | 인물에게 직접 말 걸기(사용자가 복사·붙여넣기), 인프라 생성·삭제, 콘솔 작업(토큰·웹훅·허용 IP 등록), 제출, 비밀값 읽기·출력, 디렉터(메인 세션)의 직접 분석 |
| 대신 사람이 하는 것 | 인물과 대화, 결정에 답하기, 플랫폼 실기 확인, 콘솔 설정, 제출 |

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 디렉터 | FDE 모드가 켜진 메인 세션. 직접 분석하지 않고 `fde next`가 돌려준 서브에이전트를 그대로 띄우고, 사용자 결정을 묻는다 |
| 인물(페르소나) | 인터뷰 대상. 대회의 가상 인물, 실제 고객 |
| 라운드 | 붙여넣기 한 번. `R01`, `R02` … 종류는 대화(transcript)·문제 설명(brief)·메모(note) |
| 발화 | 붙여넣은 대화를 화자 단위로 나눈 한 줄. `U001` … 화자 `I`(인터뷰어=사용자), `P`(인물), `B`(브리프), `N`(메모), `?`(불확실) |
| 렌즈 | 에이전트 하나가 맡은 관점과 그 안의 세부 점검 항목(에이전트 파일의 Lenses 절) |
| 후보 | 에이전트가 낸 질문·제안·가정·결정·위험 후보(`candidate`). 근거 발화와 원문 인용, `decision_at_stake`(답에 따라 바뀌는 결정)를 가진다 |
| 질문 카드 | 검증과 결정표를 통과해 사용자가 인물에게 그대로 붙여넣을 수 있게 다듬은 질문. `Q-001` … |
| 확신도 | 그 빈틈이 진짜인가. **확실**(인용 검증 통과, 다르게 읽을 여지 거의 없음) / **가능성 높음**(발화 2개 이상 추론 또는 상식) / **추측**(근거 없음, 과잉 해석) |
| 영향도 | 답에 따라 무엇이 바뀌나. **높음**(그래프·스키마·must 기능) / **중간**(프롬프트·형식·should) / **낮음**(문구) |
| 억지 4범주 | 일반론 / 답과 무관 / 범위 밖 / 과잉 해석. 블라인드 검증관이 판정한다 |
| ⚠ 렌즈·검증 불일치 | 제안한 렌즈와 검증관의 확신도가 두 단계(확실 ↔ 추측) 차이 날 때 붙는 표시. 사람이 판단한다 |
| 확인용 | 추측이지만 영향이 높아 "짧게 확인"하려고 남긴 카드의 표시 |
| 결정 D1/D2/D3 | 사용자가 정할 일. D1 필수 승인(답 올 때까지 그 일이 멈춤) / D2 확인 요청(추천안으로 진행하며 물음) / D3 알림(자동 결정) |
| 가정 | 묻지 않고 진행하기로 한 것. `A-001` … spec.md의 "묻지 않고 가정한 것"에 남는다 |
| 요구사항 | `R-001` …. `status`(명시·추론·가정)와 `confidence`는 다른 축이다. 우선순위 must/should/could/미정 |
| 동결 | 핵심 동결(must 잠금 → 구현 출발) → 전체 동결(should까지) → 기능 동결(시각, 마감 모드) |
| 조각(slice) | 구현 단위. `S01`부터. 조각 1은 must 하나를 실제 플랫폼에서 끝까지 동작시키는 얇은 경로 |
| 독립석 | 토론 기록·설계 논리를 보지 않고 결과만 판정하는 자리(검증 본부, 리뷰 본부, QA 본부, 데이터 출처 감사관, 리허설 채점관). 일부는 가드가 읽기를 막는다 |
| 실행(run) | 파이프라인 하나의 실행. `R07-quick`, `R09-debate`, `TG1`, `FZ-core-1`, `BUILDPLAN`, `S01`, `DATA-01`, `CH-01`, `CLOSING`, `RB-S01` … |
| 디스패치 | 실행의 한 단계에서 에이전트 하나에게 보내는 작업. 출력 파일 하나(`fde.out.v1`)를 쓴다 |
| 바인딩 | 프로젝트별 설정 `<프로젝트>/.claude/fde-mode/project.toml`(명령·경로·가드·일정·이미 정해진 결정) |
| 프로필 | 플랫폼 지식 파일 `profiles/<이름>.md`(카카오 챗봇 한도 등) |
| 프로브 | 플랫폼에 보내지 않고 봇 파이프라인을 한 번 실행해 결과를 JSON 한 줄로 받는 프로젝트 명령(QA·데이터 확인용) |
| 봉인 | 수행 측이 읽으면 안 되는 폴더(리허설·시험장의 정답). 가드가 읽기를 막는다 |

## 3. 사용 흐름

### 3.1 한 번에 보기

| 순서 | 사용자 | 조직(자동) |
|---|---|---|
| 1 | `/fde-mode` (또는 `/fde-mode on`) | `.claude/fde-mode/`와 바인딩 템플릿·DB 생성, 대시보드 서버 시작, 부팅 점검(실패 항목은 D1/D2 결정으로) |
| 2 | 문제 설명을 첫 줄 `>>brief`로 붙여넣기 | 문제 설명 분석(심사 관점·도메인·범위·플랫폼·데이터·환경·패키징) → 인터뷰 첫 계획과 첫 질문 카드 |
| 3 | 인물과 대화하고, 대화를 첫 줄 `>>`로 붙여넣기(표시 없이도 자동 판별) | 훅이 원문을 고치지 않고 저장·발화 번호 → 빠른 라운드(포그라운드, 같은 턴에 끝남) → 맨 위 "인터뷰어에게"(고칠 점·빠진 질문·다음 대화 제안·반복 습관), 지금 물어볼 질문 최대 5개, 다음 10분 전략, 경고 |
| 4 | 카드를 복사해 인물에게 묻고 답을 다시 붙여넣기 | 다음 붙여넣기에서 카드가 "물어봄/답 받음"으로 자동 연결 |
| 5 | (3라운드마다 자동) | 토론 라운드(백그라운드): 개별 분석 → 팀 보완 → 본부 입장 → 교차 검토 → 반박 → 중재 → 통합 → 독립 검증 → 카드·확인 요약·회의록 → 질문 순서 |
| 6 | 결정 질문(AskUserQuestion)에 답하기 | `fde decide`로 기록. D1은 답할 때까지 그 일이 멈춘다 |
| 7 | (must가 안정되면 자동) | 기술 결정 게이트: 위원 6명 제안 → 반대 위원 → 테크 리드 ADR + D1/D2 |
| 8 | "제작 시작해도 될까요? (핵심 동결)"(D1)에 답하기 — 제작 시작 / 이것만 더 확인하고 시작 / 인터뷰 계속 / 막는 항목만 가정으로 처리하고 시작 | 요구사항 잠금, spec.md 확정, 구현 계획 → 조각별 설계·구현·리뷰·배포·QA(백그라운드). 인터뷰는 확장 기능 위주로 계속 |
| 9 | (협업 모드, 기본) 조각마다 설계 확인·구현 중 설계 질문·첫 배포 확인·진행 확인에 답하기 | 답이 올 때까지 그 조각이 기다린다. 자율 모드(`/fde-mode auto on`)면 추천대로 진행 |
| 10 | 조각 통과 뒤 실기 확인 요청에 따라 실제 플랫폼에서 메시지 보내 보기 | 실패면 수정 조각 자동 생성 |
| 11 | (기능 동결 시각) | 마감 모드: 최종 QA, 데모 시나리오, 최종 태그·보고서, 제출 체크리스트 |
| 12 | 제출(직접), `fde run retro` 요청, `/fde-mode off` | 회고 → `docs/retro.md`, 전역 `lessons.md` |

### 3.2 `/fde-mode` 인자

| 인자 | 동작 |
|---|---|
| (없음) · `on` | 켜기: `fde on` → `fde serve --detach` → `fde boot` → 디렉터 규칙(fde-director 스킬) 적용 → 사용법 5줄 안내 → `fde next` |
| `off` | `fde off`. 기록은 남는다. 대시보드 서버는 그대로(끄려면 `fde serve --stop`) |
| `status` | 단계·라운드·열린 질문·대기 결정·진행 중 실행·남은 시간 |
| `rehearsal` · `rehearsal start [주제]` | 리허설 시작(가짜 인물 생성) |
| `rehearsal grade` | 봉인 해제 후 채점 |
| `rehearsal end` | 채점 결과 표시 후 `fde archive`(기록 보관, project.toml 유지) |

- 이 스킬은 `disable-model-invocation: true`라 모델이 스스로 켜지 않는다. 다른 단계 스킬 8개(`fde-director`, `fde-interview`, `fde-tech-gate`, `fde-freeze`, `fde-build`, `fde-data`, `fde-closing`, `fde-rehearsal`)는 `user-invocable: false`이고, 훅이 매 턴 지금 단계의 스킬 이름을 알려 준다.

### 3.3 붙여넣기 규칙

| 첫 줄 | 종류 | 비고 |
|---|---|---|
| `>>`, `>>>`, `[대화]`, `대화:`, `#대화`, `::t` | 대화 | 확실(점수 1.0) |
| `>>brief`, `>>문제`, `>>브리프`, `[문제]`, `[브리프]`, `문제:`, `#문제` | 문제 설명 | 브리프 분석 실행이 생김 |
| `>>메모`, `>>note`, `[메모]`, `메모:`, `#메모` | 사용자 메모 | 분석 실행 없이 기록(사람이 한 실기 확인 결과 등) |
| 표시 없음 | 자동 판별(스위치 `auto_detect_paste`) | 4줄 이상이고 ① 카카오톡 내보내기 줄 2개 이상(0.95) ② `이름: 말` 꼴 라벨 2종 이상·합 3회 이상(0.85) ③ 이름만 있는 줄 2종 이상·합 4회 이상(0.75)이면 대화로 저장. 아니면 일반 메시지 |

- 터미널 붙여넣기는 Claude Code가 `<pasted_content id="…">…</pasted_content>`로 감싼다. 이 꼬리표는 벗기고 본다. 표지는 직접 친 첫 줄이든 붙여넣은 글의 첫 줄이든 되지만, 붙여넣은 글 안에서는 **줄 전체가 표지**일 때만 받는다(`>>>`로 시작하는 코드·인용은 표지가 아니다). 표지와 내용은 한 메시지로 보낸다: 표지를 치고 Shift+Enter(또는 Ctrl+J, `\`+Enter)로 줄을 바꾼 뒤 붙여 넣고 Enter, 또는 클립보드 맨 윗줄에 표지. Claude Code는 800자 또는 3줄을 넘는 붙여넣기만 꼬리표로 감싸고, 그보다 짧은 붙여넣기는 그냥 글자로 들어온다. 표지만 먼저 보냈으면 훅이 그 종류를 10분 동안 기억했다가 바로 다음 메시지의 붙여넣기(꼬리표가 있거나 2줄 이상)를 그 종류로 저장한다. 다른 말이나 명령이 오면 기다림을 취소한다.
- 저장하지 못한 붙여넣기(표지만 있고 내용이 없음, 또는 한글 문장 위주의 붙여넣기인데 표지·화자 표시를 찾지 못함)는 훅이 "저장하지 않았다"를 알리고, 디렉터가 사용자에게 "표지를 직접 치고 다시 붙여 넣어 주세요"를 전한다. 코드·로그 붙여넣기에는 알리지 않는다.
- 원문은 `inbox/R07.transcript.raw.md`에 **그대로** 저장된다(이후 수정 없음).
- 화자: 바인딩의 인터뷰어 별칭(기본 `나`, `me`, `Q`, `질문`, `인터뷰어`, `참가자` …)과 인물 별칭, 이전에 배운 라벨로 정한다. 모르는 라벨은 "물음표로 끝나는 비율이 높은 쪽 = 인터뷰어"로 추정하고, 라벨 없는 덩어리는 물음표면 I(0.45) 아니면 P(0.4). 확신 0.7 미만 발화가 있으면 기록관이 확인한다.
- 이전 붙여넣기와 겹친 앞부분은 빼고(가장 긴 꼬리-머리 일치 + 최근 40개 발화의 긴 문장 완전 반복), 경고를 붙인다: "겹친 발화 N개를 뺐습니다", "직전 질문에 대한 인물 답이 빠졌을 수 있습니다"(인터뷰어 발화 연속), "화자가 불확실한 발화 N개".
- 잘못 저장됐으면 `fde undo-paste R07`(발화 삭제, 그 라운드 실행 취소, 원문 파일은 기록으로 남김). 화자 교정은 `fde speakers <인물 라벨> P --round R07`.
- 인물이 준 파일은 바인딩의 `data_raw` 폴더(기본 `data/raw/`)에 넣으면 데이터 실행(`DATA-NN`)이 자동으로 생긴다.

## 4. 단계 P0~P7

| 단계 | 이름 | 들어가는 때 | 이 단계 스킬 |
|---|---|---|---|
| P0 | 부팅·점검 | `fde on` | fde-mode |
| P1 | 인터뷰 루프 | 첫 `fde next` | fde-interview |
| P2 | 기술 결정 게이트 | 인터뷰와 병행(`TG1` 실행으로 표현, 저장 단계는 P1 유지) | fde-tech-gate |
| P3 | 핵심 동결 | 동결 실행(`FZ-core-N`)으로 표현 | fde-freeze |
| P4 | 구현 루프 | 핵심 동결 승인 | fde-build |
| P5 | 확장 인터뷰(구현과 병행) | P4와 함께 진행(인터뷰 붙여넣기는 계속 받음) | fde-build |
| P6 | 마감 모드 | 기능 동결 시각 | fde-closing |
| P7 | 회고·보관 | `fde run retro` | fde-closing |

- 실제로 DB의 `state.phase`에 저장되는 값은 P0(`fde on`)·P1(첫 `fde next`)·P4(핵심 동결 적용)·P6(기능 동결 시각)이다. P2·P3·P5·P7은 실행(`TG1`, `FZ-core-N`, 구현과 병행하는 인터뷰, `RETRO-NN`)으로 표현되는 개념 단계다. 훅은 저장 단계에 맞는 스킬 이름을 매 턴 알려 준다.
- 그래서 자동 트리거가 보는 단계는 사실상 이렇다: 기술 게이트·동결 제안은 P1에서, 변경 통제는 P4에서, 마감(`CLOSING`)은 P1~P5 어디서든(핵심 동결을 안 했어도) 기능 동결 시각에 생긴다.

## 6. 상호보완과 토론

"너무 독립적 분리가 아니라 하나로 상호보완과 토론"이 되도록, 관점은 나누되 결과는 여러 단계를 거쳐 합친다.

| 단계 | 하는 일 | 규칙 |
|---|---|---|
| 개별 분석 | 켜진 본부의 분석가 36명이 각자 렌즈로 분석 | 같은 라운드의 빠른 분석 출력은 다시 돌리지 않고 재사용. 직전 출력(`your_previous_output`)을 받아 이어서 본다 |
| 팀 내 보완 | 같은 팀 동료의 출력을 한 번 읽고 **합쳐야만 보이는 것**만 추가, 자기 항목은 `"revises"`로 이유와 함께 수정 | 재진술 금지. 스위치 `team_complement` |
| 본부 입장 | 본부장 7명이 팀 결과를 하나의 본부 입장으로 통합 | 팀 간 이견을 숨기지 않는다. 인물 이해 본부장은 `persona.md`를 쓴다 |
| 교차 검토 | 검토하는 본부의 본부장이 짝지어진 본부의 입장을 정해진 질문으로 검토 | 동의할 때도 이유와 덧붙일 것을 쓴다(근거 없는 "동의"는 무효) |
| 반박 응답 | 검토받은 본부장이 자기 본부를 겨냥한 지적에 수용 / 부분 수용 / 반론 + 근거 | 반박 → 응답 한 번으로 끝낸다 |
| 중재 | 중재관이 남은 쟁점을 합의·조건부 합의로 정리 | 소수 의견을 지우지 않고 `docs/minority-opinions.md`에 남긴다 |
| 통합·검증 | 후보 통합관 → 독립 검증(토론 기록을 보지 않음) | 판정이 토론의 목소리 크기에 끌려가지 않게 |
| 기록 | 서기장이 회의록(`docs/minutes/<실행>.md`)과 입장 변화 이력(`docs/stance-history.md`) | 입장을 바꾸면 이유를 남긴다 |

교차 검토 짝(`roster.CROSS_REVIEW`):

| 검토하는 본부 | 검토받는 본부 | 묻는 것 |
|---|---|---|
| 인물 이해 | 솔루션 설계 | 이 기능이 이 사람의 패턴과 맞나, 일반적인 사람용 기능은 아닌가 |
| 솔루션 설계 | 인물 이해 | 이 패턴 분석이 봇 동작으로 바뀔 수 있나, 쓸모없는 분석은 아닌가 |
| 문제 정의 | 전략·범위 | 범위를 줄이다가 핵심 문제를 잘라 내지 않았나 |
| 전략·범위 | 문제 정의 | 이 깊이까지 파는 게 남은 시간 안에서 의미 있나 |
| 리스크·품질 | 솔루션 설계 | 이 설계가 이 인물의 실제 입력에서 깨지지 않나 |
| 인물 이해 | 문제 정의 | 도메인 일반론을 이 사람에게 덮어씌우지 않았나 |
| 문제 정의 | 인물 이해 | 성향 분석이 실제 문제와 연결되나 |
| 데이터 | 솔루션 설계 | 이 설계에 필요한 데이터가 실제로 있고 믿을 만한가 |
| 문제 정의 | 데이터 | 이 데이터가 실제 문제에 답하나, 엉뚱한 데이터를 모으고 있지 않나 |
| 커뮤니케이션 | 전 본부 | 이 빈틈을 이 인물에게 실제로 물을 수 있는 말로 바꿀 수 있나 |

- 반박 응답은 교차 검토를 받는 6개 본부(인물·문제·솔루션·리스크·전략·데이터)만 한다. 커뮤니케이션 본부는 모든 본부를 검토하지만 검토를 받지 않는다.
- 엔게이지먼트 리드는 매 라운드 결론에서 **관점 충돌**을 질문으로 바꿔 `extra.next_round_candidates`로 내고, 그 질문은 다음 라운드에 다른 후보와 똑같이 검증을 거친다(바로 카드가 되지 않는다).
- 모든 출력에 `covers_until`(읽은 마지막 발화)이 있고, 늦게 끝난 토론 라운드는 그 사이 들어온 발화로 이미 답이 나온 "낡은 항목"을 보고서에 따로 표시한다.

## 7. 검증과 확신

### 7.1 거르는 순서

```
후보(렌즈 자기 확신도·영향 추정·근거·인용·decision_at_stake)
 → decision_at_stake 없는 질문·제안은 저장 시 자동 탈락(rejected:no-stake)
 → kind=risk 는 위험 목록, kind=decision 은 결정 큐로 이동(질문 흐름에서 빠짐)
 → 후보 통합관: 같은 빈틈 묶기, 이미 물은·답한·가정한 것 이유와 함께 빼기
 → 인용 검사(코드): 근거 발화 id가 실제로 있고 인용이 그 발화의 원문인지
 → 블라인드 묶음: 제안자·자기 확신도·동의 수를 지운 목록
 → 블라인드 검증관(확신도·영향도·이미 답함·억지 판정) ∥ 반론관(ask / assume / skip)
 → 결정표(rank.decide_bucket) → 지금 물어볼 / 보류 / 가정 제안 / 버림 / 제안
 → 질문 작성가(인물에게 붙여넣을 문장) → (토론 라운드) 질문 순서 설계자
```

- **인용 검사**(`cite.py`): 인용을 `…`·`...`·`[중략]`으로 나눠 각 조각이 근거 발화 원문에 들어 있는지(정규화 후 부분 문자열 또는 포함도 0.85 이상) 본다. 실패하면 그 후보는 무조건 **추측**으로 내려간다. LLM 검증관이 없는 인용을 통과시키는 일을 문자열 비교로 막는다.
- **블라인드 묶음**(`report.blind_pack`): 검증석이 보는 것은 빈틈, 질문 초안, 근거 id, 인용, 인용 검사 결과뿐이다. 누가 냈는지, 얼마나 확신했는지, 몇 명이 동의했는지는 일부러 뺀다.

### 7.2 결정표 (`rubric.MATRIX`)

| | 영향 높음 | 영향 중간 | 영향 낮음 |
|---|---|---|---|
| **확실** | 지금 물어봄 | 지금 물어봄 | 가정으로 처리 |
| **가능성 높음** | 지금 물어봄 | 보류 | 가정으로 처리 |
| **추측** | 확인용으로 물어봄 | 가정으로 처리 | 버림 |

### 7.3 최종 판정 규칙 (`rank.decide_bucket`, 위에서부터 적용)

| # | 조건 | 결과 |
|---|---|---|
| 1 | 검증관 판정이 없음 | 표시 "검증 누락"(렌즈 확신도로 계속) |
| 2 | 인용 검사 실패 | 확신도 = 추측, 표시 "인용 불일치" |
| 3 | 렌즈와 검증관 확신도가 두 단계 차이 | 표시 "⚠ 렌즈·검증 불일치" |
| 4 | 검증관: 이미 답함 | 버림("이미 답함 U…") |
| 5 | kind = assumption | 가정 제안 |
| 6 | 결정표(검증관의 확신도·영향도 우선) | 기본 버킷 |
| 7 | 억지 판정 | 영향 높음 + 반론관 ask → 보류(표시 "억지 의심"), 아니면 버림 |
| 8 | 반론관 skip | 영향 높음이 아니면 ask·hold → 가정(추측이면 버림), 영향 높음이면 질문 유지 + 표시 "반론 있음" |
| 9 | 반론관 assume, 기본이 ask, 영향 높음 아님 | 가정 |
| 10 | kind = proposal 이고 ask·hold | 제안("이런 것도 되면 쓰시겠어요?") |
| 11 | 추측 + 영향 높음 + ask | 표시 "확인용" |

- 정렬: 영향 → 확신 → 출처 수(통합된 후보 수) 순. 보고서에는 상위 `top_cards`(기본 5)개만 "지금 물어볼 질문"으로 싣고 나머지는 대시보드에 둔다.
- 보류·가정·버림도 이유와 함께 보고서·대시보드에 남는다. 검증관이 진짜 중요한 것을 잘못 버렸는지 사람이 확인할 수 있게 하려는 것이다.
- **가정 문장**(`rank.assumption_text`): "가정으로 처리 제안"에는 사용자가 한눈에 거부할 수 있는 "무엇을 가정하고 진행하는지" 한 문장이 나온다. 우선순위: 반론관의 `default`(assume·skip일 때 필수) → 반론관 이유 속 "기본값/기본안 …" 문장 → 후보가 가정이면 그 문장 → 없으면 "묻지 않고 진행(기본값 미기재) — <빈틈>". "답에 따라 바뀌는 것"은 가정 문장이 아니라 이유 뒤에 " · 틀리면: …"으로 붙는다(실측 라운드에서 가정 자리에 "바뀌는 것"이 나오던 문제를 고침).
- 카드 배지: `[확신 | 영향 | 표시]`, 근거 발화 원문 3개까지, "답에 따라 바뀌는 것", ⚠면 렌즈·검증관 판단과 이유를 나란히, 반론관이 skip·assume이면 그 이유.

### 7.4 물어봤는지 자동 추적 (`asked.py`)

- 사용자가 카드를 복사해 인물에게 물으면 다음 붙여넣기에서 그 문장이 인터뷰어 발화로 나타난다. 카드 문장과 인터뷰어 발화의 유사도(포함도·자카드 중 최댓값)가 **0.55 이상**이면 그 카드를 "물어봄"으로, 바로 뒤 인물 발화가 있으면 "답 받음"으로 바꾸고 답 발화 id를 연결한다. 이미 답한 것을 다시 묻지 않게 하는 장치다.
- 고쳐서 물었다면 `fde question Q-012 asked`. 가정으로 넘기면 `assumed`(가정 목록에 자동 추가), 버리면 `dropped`.

## 8. 인물·인터뷰어 패턴 분석

세는 일은 코드가(`metrics.py`, `lexicon.py`), 해석은 인물 이해 본부와 인터뷰어 코치가 한다(LLM은 잘못 센다).

| 지표 묶음 | 내용 |
|---|---|
| 인물 — 영역별 | 영역마다 발화 수, 처음·마지막 라운드, 평균 길이, 강조어·모호어·회피어 수, 구체성(0~1) |
| 인물 — 말버릇 | 자주 쓴 표지어 상위 25개, 시간 표현이 나온 발화와 단어, 언급한 다른 사람(가족·동료·직원 …, '〈직함〉님' 꼴 호칭), 앞말 정정 발화, 망설임 발화, 웃음·이모티콘 횟수 |
| 인터뷰어 | 질문 수, 질문 형식 분포, 10개 영역 커버리지와 **한 번도 안 건드린 영역**, 모호한 답 뒤 후속 질문률, 발화량 비(인터뷰어:인물), 해결책을 먼저 내민 질문, 질문 형식별 답의 구체성, 한 영역에 가장 오래 머문 연속 횟수, 최근 5개 질문의 영역 |

- 10개 영역: 문제 · 현재방식 · 사용맥락 · 여정 · 데이터 · 성공기준 · 예외 · 말투 · 우선순위 · 이해관계자.
- 질문 형식: 유도(leading) > 선택지(choice) > 열린(open) > 닫힌(closed) > 질문 아님(statement). "~면 좋겠죠?" 같은 유도 질문에 대한 "네"는 자발적 발화가 아니어서 **확실**이 될 수 없다(유도 답변 판별가).
- 발화 태그(발화 태거): 사실, 의견, 감정, 요청, 해결책 제안, 망설임, 회피, 앞말 정정, 되묻기, 예시 제공, 숫자·시간 포함, 질문.
- 결과는 라운드마다 `runs/<실행>/metrics.json`과 DB `metrics` 표에 남고, 대시보드 "인물 패턴" 탭에 보인다.
- **"인터뷰어에게"**(`report._interviewer_section`): 인터뷰어 코치의 `to_interviewer`가 라운드 보고서 **맨 위**(질문 카드보다 앞)에 나온다. 디렉터는 이 절을 가장 먼저 그대로 보여 준다.
  1. 이번 라운드에서 고칠 점(최대 3): `U012 · 유도 질문 [확실] — 왜` + `→ 이렇게: "…"`. 없으면 "이번 라운드는 고칠 점 없음."(억지로 지적하지 않는다)
  2. 빠진 질문: 코치의 `missing_questions`, 없으면 질문 카드 상위 3개와 지금 물어야 하는 이유
  3. 다음 대화 제안: 전환 문장·순서·인물 말투에 맞춘 표현
  4. 반복 습관: 같은 실수 `kind`가 이번 라운드를 포함해 2라운드 이상이면 코드가 세서 굵게 "⚠ <kind> — N번째 라운드(R01·R02)"
- 예전의 아래쪽 "인터뷰어 코치" 절은 없앴다. `to_interviewer`가 없는 옛 코치 출력의 `feedback`은 "인터뷰어에게" 안에 "코치 의견"으로 나온다. 토론 보고서는 그 라운드 빠른 분석의 코치 출력을 쓴다.

## 8.5 단계 지도와 의뢰 유형 (`stage.py`)

P0~P7(흐름 제어) 위에 덧씌우는 점검표다. 흐름은 바꾸지 않고, 라운드가 끝날 때마다(보고서 직전) 데이터베이스만 보고 계산한다.

- **의뢰 유형 E1~E8**(업종이 아니라 관계): E1 본인이 직접 쓸 도구, E2 본인이 운영하고 다른 사람이 쓰는 서비스, E3 외주 의뢰(의뢰인의 고객용), E4 조직 내부 도구, E5 조직 이름의 대외 서비스, E6 공동체·비영리·모임, E7 중개·다자, E8 기타·불명. 겹칠 수 있고, 유형마다 확신도와 근거 U가 붙는다. 이해관계자 분석가의 `extra.engagement`가 있으면 그 판단이 신호 추정을 대신한다.
- **역할 지도**: 의뢰인·결정권자·비용 부담·최종 사용자·운영·관리·데이터 주인·장애·민원 책임·영향받는 제3자·채널 주인·인수인계. 칸마다 근거 U, 모르면 "모름".
- **단계 S1~S8**: 상황 파악 → 문제 정의 → 요구 수집 → 확인 → 범위 확정 → 설계 → 구현·검수 → 전달·운영. 단계마다 기계로 재는 완료 조건이 있고(역할 지도의 사용자·운영자·결정권자 근거, 근본 문제 근거 2개, 예외 2개, 비기능 3종, 확인 요약, 열린 모순 0 …), 빈칸은 이유 한 줄과 함께 남는다.
- **되돌림**: 뒤 단계에서 앞 단계 빈칸이 드러나거나 의뢰 유형이 바뀌면 그 단계를 "다시 열림"으로 표시하고 횟수를 센다. 흐름을 강제로 옮기지 않는다. 협업 모드면 "Sx로 돌아가 n개 묻기(추천) / 가정으로 진행 / 나중에" D2를 라운드당 1개까지 묻고, 자율 모드면 추천대로 간다. 빈칸이 닫히면 완료로 돌아간다.
- **깊이**: 숫자·예시 없이 막연한 답("보통", "가끔", "알아서" …)에는 후속 질문 카드를 만든다. 같은 주제는 2회까지 묻고, 그 뒤에는 가정으로 정리하는 D2로 확인한다.
- **카드**: 빈칸·깊이 카드는 라운드당 2장까지만 새로 만든다. 분석 카드와 같은 표·순위에서 경쟁하며(보고서에 보이는 카드 수 `top_cards`는 그대로), 의뢰 유형이 불확실할 때의 "누가 쓰고, 누가 관리하고, 누가 정하나요?" 카드만 맨 앞에 선다.
- **보고서**: "인터뷰어에게" 맨 위에 단계 지도 한 줄(S1 ✓ · S2 ◐(빈칸 2) …), 의뢰 유형, 역할 지도 빈칸, 되돌림 추천, 허점 상위 3, 인터뷰 코치·반론관이 짚은 단계별 허점(`extra.stage_review`)이 붙는다.
- **좌석**: 단계 지도 파일 `docs/stage-map.json`이 공통 입력과 질문 작가·순서 담당·반론관·엔게이지먼트 리드·설계 본부장·릴리스 관리자 입력에 들어간다. 릴리스 관리자의 `extra.operations`·`extra.handover`는 `docs/operations.md`·`docs/handover.md`로 쓴다(S8 완료 조건).
- **스위치**: `[switches] stage_map`(기본 켬). 끄면 점검·카드·D2·보고서 줄만 멈춘다.

## 9. 사용자 결정과 강제

| 등급 | 기준 | 처리 |
|---|---|---|
| D1 필수 승인 | 되돌리기 어렵다(데이터 구조, 외부 서비스), 취향의 문제, 또는 시간 30분 이상 차이 | 답이 올 때까지 그 일을 진행하지 않는다(`blocking`: core_freeze, full_freeze, deploy) |
| D2 확인 요청 | 되돌릴 수 있지만 영향이 크다 | 추천안으로 진행하면서 묻는다. 다른 답이면 되돌린다 |
| D3 알림 | 되돌리기 쉽고 영향이 작다 | 자동 결정(추천안), 보고서에 한 줄 |

- 같은 제목(자카드 0.8 이상)의 결정이 다시 올라오면 하나로 합치고 더 엄격한 등급을 남긴다. 단, 엔게이지먼트 리드와 테크 리드는 등급을 정할 권한이 있어 낮출 수도 있다("라운드당 D1 2개 이하" 규칙을 지키려고).
- `fde next`의 `ask`(상태 `new`인 D1·D2 최대 4개, D1 먼저)를 디렉터가 AskUserQuestion으로 묻는다: 추천안을 맨 위에 "(추천)"으로, 선택지가 하나면 "아니오/나중에"를 붙인다. 답은 `fde decide <id> <답>`.
- 미루기 `fde defer <id>`: 상태가 `asked`가 되어 지금 턴의 `ask` 목록과 Stop 훅 검사에서 빠진다. 다음 라운드 보고서가 나올 때 미룬 결정은 모두 다시 `new`가 되어(이벤트 `decision.reopened`) 그 보고 뒤에 다시 묻는다. 그 전에 다시 열려면 `fde reask`. 미룬 D1이라도 `blocking`(동결·배포)은 계속 막는다.
- D3는 만들어지는 순간 추천안으로 자동 결정된다(`auto`). 자율 모드(스위치 `autonomy` 켬, 사용자가 명시할 때만)에서는 D2도 만들어지는 순간 추천으로 자동 결정된다. 기본인 협업 모드에서 구현 조각의 협업 D2(설계 확인·구현 중 설계 질문·첫 배포 확인·진행 확인)는 답이 올 때까지 그 조각을 멈춘다(14.2).
- 답이 "추천대로"·"추천"·"추천안"이면 그 결정의 추천 라벨로 기록한다(`decisions.answer`). 디렉터는 같은 묶음의 나머지 D2도 추천으로 할지 한 번 묻는다.
- **Stop 훅 강제**: `fde next`가 한 번 내놓은(surfaced) D1·D2가 아직 답도 미룸도 없으면 턴을 끝내지 못하게 막는다. 실행할 작업(새 라운드, 대기 디스패치, 끝난 포그라운드 출력)이 남아 있어도 막는다. 같은 사용자 메시지(훅 입력의 `prompt_id`)당 최대 2번만 막고, 이미 Stop 훅 때문에 이어진 턴(`stop_hook_active`)은 막지 않아 턴이 영원히 안 끝나는 일은 없다(스위치 `stop_enforce`).
- 무인 실행(`fde on --autopilot`, 시험장)에서는 AskUserQuestion 대신 운전석 운영자가 고르거나, 운전석이 없으면 디렉터가 `recommended`로 `fde decide`하고 이유를 보고서에 한 줄 남긴다(fde-director 스킬 9절).
- 인물에게 물을 질문 카드와 사용자 결정은 섞지 않는다: 질문(인물) / 제안(인물, 반응 보기) / 결정(사용자) / 가정(아무에게도 묻지 않음, 기록).

## 10. 기술 결정 게이트

- 기술 스택은 구현 도중이 아니라 **동결 전에** 확정한다. 게이트는 인터뷰와 병행하고 인터뷰를 멈추지 않는다.
- 자동으로 열리는 때(`TG1`, 스위치 `tech_gate`, 한 번만): must 요구사항이 2개 이상이고 최근 2라운드 동안 바뀌지 않았으며 라운드가 3 이상일 때, 또는 핵심 동결 30분 전. 스위치는 자동 열림만 막는다 — `fde run techgate`는 언제든 연다.
- 단계: 기술 항목 정리(바인딩의 `fixed_decisions`·`facts`·`open_items` → `items.json`) → **위원 6명 제안**(런타임 아키텍트, 데이터 아키텍트, 통합 담당, 플랫폼 제약 검사관, 구현 비용 추정가, 패키징 전략가: 선택지·장단점·분 단위 비용·추천·확신) → **반대 위원**("더 단순한 방법은 없나", accept/simplify/reject) → **테크 리드**가 ADR(`tech/ADR-*.md`, DB `adrs`)을 쓰고 등급을 매긴다 → 완료 알림.
- 바인딩 `fixed_decisions`는 이미 정해진 것이라 다시 논의하지 않는다. `open_items`가 없으면 기본 7항목(그래프 변경 범위, 데이터 배치, 인물 데이터 공용/전용, 외부 API, 버튼 중심 대화, 선제 발송, 심사자 첫 방문 처리)을 쓴다.
- ADR이 D1·D2이고 상태가 proposed면 `[기술] <제목>` 결정이 큐에 들어가고, 선택지는 결정안 + 대안들이다. 동결 판단관은 남은 D1 기술 결정을 동결을 막는 항목으로 올린다.

## 11. 환경·패키징 분석 (솔루션 설계 본부 › 환경·패키징팀)

같은 요구도 쓰이는 환경과 전달 형태에 따라 설계가 달라진다. 대회는 형태가 카카오톡 챗봇으로 고정이지만, 고객의 이상적인 형태(앱·웹·웹앱·확장·플러그인)와의 긴장을 분석해야 좋은 보상 패턴이 나온다.

| 에이전트 | 하는 일 | 남기는 문서 |
|---|---|---|
| 환경 분석가(`fde-environment-analyst`, high, 빠른 라운드) | 12개 차원 — 기기, 장소·자세, 주의력·시간 압박, 연결, 디지털 숙련도·신체 조건, 사용자 구성, 시점·빈도, 데이터가 있는 곳, 조직·법 규칙, 운영·유지, 언어·문화, 대체 수단 — 을 근거 발화와 함께 표로 만들고 "설계는 …해야 한다" 제약으로 바꾼다. 모르는 환경 사실 중 설계를 뒤집을 것만 질문으로 | `docs/environment.md` |
| 패키징 전략가(`fde-packaging-strategist`, xhigh) | 형태가 열려 있으면 후보 형태를 기준표(도달·입력·출력·먼저 말 걸기·신원·오프라인·심사·구현 시간·운영)로 비교해 D1로 올린다. 형태가 고정이면(`packaging_fixed`) 요구마다 **기본 지원 / 우회 / 불가**, 보상 패턴, 분 단위 비용, 사용자가 잃는 것을 적은 적합·격차 표를 만들고, 보조 표면(읽기 전용 웹 페이지 등)은 실제 비용(공개 경로 추가 = 인프라 변경, D1)과 함께만 제안한다. 핵심(그래프·도구·데이터·기억)을 표면과 분리해 대회 뒤 다른 형태로 다시 포장할 수 있게 한다 | `docs/packaging.md` |

- 두 문서가 생기면 **모든 분석가**의 공통 입력(`environment`, `packaging`)이 된다. UX 검사관은 `environment`를 입력으로 받고, 디테일 설계자는 작업 폴더에서 직접 찾아 읽는다(설계 디스패치 입력에는 없다). 대시보드 "인물 패턴" 탭에 사용 환경·전달 형태로 함께 보인다(`/api/persona`의 `environment_md`, `packaging_md`).
- 형태 비교의 일반 지식은 `skills/fde-director/references/packaging-catalog.md`(메신저 챗봇, 모바일 앱, 웹앱/PWA, 웹사이트, 데스크톱, 브라우저 확장·호스트 플러그인, 음성, 알림 채널, 스프레드시트 연동, 결합 패턴)에 있다. 바뀌는 정책 사실은 "확인 필요"로 표시돼 있다.

## 12. 동결과 변경 통제

### 12.1 동결 검사 (`report.freeze_check`)

| 수준 | 막는 항목 |
|---|---|
| 핵심(core) | must가 없음 / must인데 근거 없는 가정 상태(확인 안 됨) / must인데 플랫폼상 불가 / must인데 수용 테스트 없음 / must에 발화 충돌 미해결 / 영향 높음 + 확신 [확실]·[가능성 높음]인 열린 질문 / 핵심 동결을 막는 D1 |
| 전체(full) | 핵심 기준 + should가 가정 상태 + 영향 높음인 열린 질문 전부 |

- 동결 판단 실행(`FZ-core-N`)이 저절로 생기는 때: 검사 통과 + 끝난 대화 라운드 ≥ `min_rounds_before_freeze`(기본 3) + 분석 중인 빠른·브리프 실행 없음(그래서 라운드 보고 직후, 시각과 별개), 또는 핵심 동결 시각이 지남(검사 실패여도 묻는다), 또는 "이것만 더 확인"으로 만든 카드가 다 닫힘.
- 검사 결과(`check.json`)는 막는 항목과 함께 `must`, `must_with_tests`, `must_with_evidence`, `open_high_impact`, `open_questions`, `would_assume_if_frozen`을 센다.
- 흐름: 검사 + spec.md 초안 → 동결 판단관(추천 `freeze` / `confirm_first` / `wait` / `freeze_with_assumptions`, 내부 확신 `internal_confidence`, 근거 `confidence_basis`, 부족한 정보 `missing_info`, 가정으로 넘어갈 목록) ∥ 문서 일관성 감사관(persona.md가 있을 때) → D1 **"제작 시작해도 될까요? (핵심 동결)"**(전체는 "확장 기능까지 닫아도 될까요? (전체 동결)", `blocking: core_freeze`) → 답에 따라:
  - 맥락 한 줄: "내부 확신 [..] · must 근거 n/m · 영향 높음 열린 질문 k · 지금 시작하면 가정으로 넘어갈 질문 j · 막는 항목 b (· 관점별 막는 허점) / 판단: … / 막는 항목: … / 부족한 정보: X(받으면: Y); …". 숫자는 코드가 센 값을 먼저 쓰고, 판단관이 확신을 안 냈으면 "(코드 추정)"을 붙인다.
  - 선택지(추천은 판단관 `recommend`): 핵심 [제작 시작, 이것만 더 확인하고 시작, 인터뷰 계속, 막는 항목만 가정으로 처리하고 시작], 전체 [전체 동결, 이것만 더 확인하고 동결, 인터뷰 계속, 막는 항목만 가정으로 처리하고 동결].
  - 답은 선택지에 정확히 대응돼야 한다(`planner._freeze_choice`, "(추천)"은 무시): 선택지 라벨, 짧은 말("제작 시작", "시작", "동결", "지금 동결" 등), 예전 라벨("지금 동결", "아직 (인터뷰 계속)")만 받는다. "인터뷰 계속…"·"아직…" = 보류, "이것만 더 확인…" = 먼저 확인, "막는 항목만…" = 가정으로 처리하고 동결, 나머지 짧은 말 = 동결.
  - 이것만 더 확인: 판단관 `missing_info` 상위 3개가 바로 질문 카드가 된다(영향 높음, 표시 "제작 전 확인", 플래그 `core_freeze_confirm`). 그 카드가 다 닫히면(또는 핵심 동결 시각이 지나면) 엔진이 같은 D1을 다시 올린다. 전체 동결은 저절로 다시 묻지 않는다(`fde run freeze --level full`).
  - 보류: 다음 대화 라운드의 분석이 끝난 뒤 다시 판단(미룰 때까지 끝난 라운드 수 기준 — 이미 붙여넣은 라운드가 그 다음 라운드), 핵심 동결이 계속 없으면 전체 동결 계획 시각에 한 번 더 묻는다(강제 동결 없음).
  - 동결: must(전체 동결이면 should도) 잠금(`frozen=1`), spec.md 확정. 핵심이면 단계 P4와 `BUILDPLAN` 시작, 인터뷰는 계속(P5). "막는 항목만"이면 열린·보류 질문을 모두 가정(`assumed`)으로 바꾼 뒤 동결.
  - 그 밖의 자유 입력("조금 더 물어보고요" 등): 동결하지 않는다. 결정을 다시 `new`로 돌리고 답을 지우고, 맥락 앞에 "(앞의 답 '…'은 선택지와 달라 다시 묻습니다)"를 붙여 다시 묻는다(이벤트 `decision.reasked`).
- 전체 동결은 자동으로 열리지 않는다: `fde run freeze --level full`.

### 12.2 변경 통제

- 핵심 동결 뒤 요구사항 관리관이 잠긴 요구의 문장·우선순위를 바꾸거나 새 must를 올리면, 동기화 단계가 그것을 `pending_changes`로 모으고 `CH-NN` 변경 영향 실행이 자동으로 생긴다. 사용자가 직접 `fde run change --text "<요청>"`로도 연다.
- 변경 영향 분석관이 바뀌는 요구사항·파일·작업, 예상 분, 권고(수용/미룸/거절), 등급을 내고 결정 큐로 올린다. 구현 중인 조각은 중간에 바꾸지 않고 그 조각 배포 뒤에 반영한다. 기능 동결 이후 변경은 원칙적으로 거절을 권고한다.
- 변경 실행은 두 단계다(`ch_analyze` → `ch_decide`). 분석관이 결정을 올리지 않았으면 "명확화"로 보고 끝낸다(알림). 결정이 있으면 사용자 답(또는 D3 자동 답)을 기다렸다가 재계획 실행 `RP-<변경 실행>`을 만든다. 테크 리드는 답이 변경을 받아들이면 기존 모든 조각보다 높은 번호의 새 조각에 작업을 더하고, 미룸·거절이면 작업을 더하지 않는다.
- 실행 이름: 동결된 요구가 바뀌어 자동으로 생기면 `CH-NN`, `fde run change --text …`로 직접 열면 `CHANGE-NN`(재계획은 `RP-CH-01`, `RP-CHANGE-01`).

## 14. 구현 조직

### 14.1 원칙

1. 얇게 끝까지 먼저: 조각 1은 must 하나를 실제 플랫폼에서 끝까지 동작시켜 배포한 것(인물 이름·말투·시드 데이터 포함).
2. 배포할 때마다 정상 버전을 `fde-good-<조각>` 태그로 남겨, 어느 시점에 멈춰도 제출할 수 있게 한다.
3. 명령은 바인딩 `[commands]`에서만. 인프라 생성·삭제 명령은 쓰지 않는다(가드).
4. 배포는 한 번에 하나(다른 조각의 배포 담당이 진행 중이면 대기).
5. 리뷰·QA는 독립석: 구현 과정을 보지 않고 결과만 본다.
6. 협업 모드가 기본(스위치 `autonomy` 꺼짐): 조각마다 설계 확인 → 구현 → 구현 중 설계 질문 → 리뷰 → 첫 배포 확인 → QA → 진행 확인을 사용자와 같이 정한다. 자율 모드는 사용자가 명시할 때만(`/fde-mode auto on`, "자율 모드로 해").

### 14.2 흐름

```

조각 S0N (15단계, ★ = 협업 모드에서 사용자에게 묻는 곳):
  0 이전 조각 대기(S0N-1 이 끝날 때까지 — 협업이면 앞 조각의 진행 확인 답까지)
  1 설계: 설계 본부장 + 디테일 설계자(항상) + 계획이 지정한 설계자(그래프·프롬프트·스키마)
  2 ★설계 확인: 설계 출력의 decision_points → D2 "[설계·조각 N] <제목>"(등급 D1이면 D1), 답이 다 올 때까지 대기
     → runs/<조각>/design-choices.json (자율이면 추천을 적용해 같은 파일, mode autonomy)
  3 명세 추적: 명세 추적관(R-id ↔ 설계 ↔ T-id, 근거 없는 기능, 설계자 간 모순). 입력에 design_choices
  4 구현: 작업 담당 개발자. 파일이 겹치지 않는 작업끼리 한 묶음(wave), 겹치면 다음 묶음. 입력에 design_choices,
     협업이면 "진짜 갈림길은 혼자 정하지 말고 tasks_blocked 에 {task, design_question:{title, options, recommended, why}}로"
  5 ★구현 중 설계 질문: design_question → D2 "[구현 중 설계·B-xxx] <제목>" → 답이 오면 그 작업 재작업
     + 리뷰 메모 "사용자 설계 답(D-…): … → …" 로 4로
  6 독립 리뷰: 코드 리뷰어 ∥ 명세 대조관
  7 리뷰 판정: REJECT면 4로(최대 2번)
  8 반려 2번: 개발 본부장(unblock) + 사용자 D1(개발 본부장이 직접 해결 / 이 작업을 빼고 배포 / 마지막 정상 버전 유지)
  9 배포: 배포 담당 — test → deploy → health 순서, 첫 실패에서 멈춤. 배포를 막는 D1이 있으면 보류
     ★협업이면 첫 배포와 되돌린 뒤 첫 배포만 D2 "조각 N을 배포할까요? (첫 배포|되돌린 뒤 첫 배포)"
     [배포, 보류(이유를 적어 주세요)] — 보류면 조각 중단(failed), 지금 배포된 버전 유지
 10 QA 7석(병렬) → 11 QA 본부장 판정
 12 릴리스: 릴리스 관리자(PASS일 때만 정상 태그) ∥ 관측 담당(로그 확인)
 13 마무리: PASS → 사람에게 실기 확인 2~3개 / FAIL → 수정 작업으로 수정 조각 S9N 생성(없으면 재계획 RP-…)
 14 ★진행 확인(QA PASS 뒤): D2 "조각 N 배포·QA 통과. 다음은 어떻게 할까요?"
     [다음 조각 진행 | 이대로 유지(남은 조각 없음), 수정 요청(무엇을 고칠지 적어 주세요), 설계 재검토]
     자유 글 = 수정 요청 → 변경 통제 CH-NN / 설계 재검토 → 재계획 RP-<조각>-review / 라벨만 오면 고칠 내용을 다시 묻는다
배포 실패 → 되돌리기 실행 RB-…(릴리스 관리자가 가장 최근 fde-good-* 태그로, 바인딩의 배포 명령만 사용)
```

- 협업 D2는 기본으로 상한이 없다: 자율 모드를 명시적으로 켜기 전까지 설계 질문은 모두 묻는다. 바인딩 `[collab] max_questions`에 양수 N을 주면 조각마다 N개를 넘는 설계 질문(설계 확인·구현 중 설계 질문에만 — 첫 배포 확인·진행 확인은 늘 묻는다)은 추천으로 D3 자동 + 알림 "질문 상한(N개)을 넘어 추천으로 진행합니다…". 0·음수·읽을 수 없는 값은 상한 없음이다. D1은 상한이 없다.
- 자율 모드: 설계 확인은 추천을 적용하고(결정점 전부), 첫 배포 확인·진행 확인은 건너뛰고, D2는 만들어지는 순간 추천으로 자동 결정된다. 무인 실행(`--autopilot`)은 자율 모드가 아니다 — 협업 질문은 그대로 생기고 운전석 운영자가 답한다.

- 구현 담당이 `implement` 모드가 없는 에이전트로 지정되면 도구 개발자로 바뀐다.
- 리뷰가 REJECT인데 작업별 재작업 목록이 없으면 그 조각의 모든 작업을 반려로 본다(반려가 통과로 새지 않게).
- 설계 출력과 추적 출력은 그 조각의 모든 개발자 디스패치에 그대로 입력된다. 설계가 모호하면 개발자가 추측하고, 그 추측은 반려로 돌아온다.

### 14.3 디테일 설계자 (`fde-detail-designer`)

피그마·Claude Code 급의 세부를 조각마다 정한다: 흐름별 상태 목록(첫 방문·재방문·정상·빈 상태·일부 누락·오류·한도·완료·취소·재개), 상태마다 **정확한 한국어 문구**와 버튼, 다음 행동(막다른 길 금지), 확인·취소·되돌리기, 입력 변형(오타, "두시/2시/14시", "내일/다음 주 수요일", "ㅇㅇ", 음성 입력 흔적, 한 메시지에 두 의도), 중단 뒤 재개 문구, 날짜·금액 형식과 용어 통일, 중간 메시지가 없는 플랫폼의 기다림, 첫 방문(심사자)에게 보일 버튼, 접근성. 결과(`design.detail`)를 개발자가 받아 적고 QA가 시험한다.

### 14.4 QA 7석과 판정

| 석 | 보는 것 | FAIL 기준(요지) |
|---|---|---|
| 시나리오 시험관 | 수용 테스트(인물이 말한 성공·실패 기준) | 기대 요소 하나라도 빠짐, 실패 기준 해당, 근거 없는 사실 |
| 가상 사용자 시험관 | 인물 말투의 3~5턴 대화(모호·지시어·정정 턴) | 이미 말한 것 되묻기, 기억·지시어 실패, 턴 사이 모순 |
| 응답 시간 검사관 | 유형별 시간(인사, 도구, 검색, 긴 답, 앞 대화 참조, 첫 방문) | 하드 예산 초과, 중앙값이 목표(프로필 값, 없으면 30초) 초과 |
| 표시 형식 검사관 | 말풍선 수·글자 수·버튼 수·라벨·마크다운·잘림 | 플랫폼 한도 초과, 서식 기호 노출, 요청 정보 잘림, 빈·깨진 답 |
| UX 검사관 | 과업 단위 다중 턴: 완료, 턴 수(설계 경로 대비), 막다른 길, 다시 묻기, 오류 복구·마음 바꾸기, 발견 가능성, 인지 부하, 일관성, 확인·되돌리기, 환경 적합, 실패 시 품위 | must 흐름 미완료, must 흐름의 막다른 길, 복구가 처음부터 다시 |
| AI티 검사관 | 상투 서두·맺음, 번역투, 과잉 구조, 불필요한 고지·사과, 과장된 호응, 어휘 이질감, 템플릿 반복, 길이 부풀림, 일반론, 목소리 흔들림(주 모델 vs 대체 모델) | 서식 기호·불필요한 AI 고지, 서두+맺음 상투구 동시, 이 사람 맥락을 무시한 템플릿 |
| 맞춤 적합성 심사관 | **persona.md와 실제 답만**(명세 금지): 첫 접촉, 말의 높이, 어휘, 말버릇 처리, 핵심 동기·두려움, 분량, 신뢰, 맞춤의 흔적 | 말투·핵심 동기·첫 접촉 부적합 |

- 석마다 받는 입력이 다르다(`planner._qa_steps`): 시나리오·가상 사용자·응답 시간·표시 형식은 spec.md, 바인딩, 수용 테스트(+가상 사용자 메시지). UX 검사관은 여기에 persona.md와 `docs/environment.md`. AI티 검사관은 바인딩, persona.md, 용어 사전, 가상 사용자 메시지만. 맞춤 적합성 심사관은 persona.md와 바인딩만. 뒤의 둘은 spec.md를 열면 가드가 막는다(17.4절).
- QA 본부장(xhigh)은 시험관 결과만 보고 PASS/FAIL 하나를 낸다. 차단: must 테스트 FAIL, 무응답·사과문·오류 노출·잘린 문장, 형식 위반, 하드 예산 초과, 맞춤 부적합, must 다중 턴 붕괴, must 과업 미완료·막다른 길, 눈에 보이는 서식 기호·불필요한 AI 고지·과반 답의 상투구(또는 측정 점수 60 미만). 검증 못 한 항목은 통과로 세지 않고, must면 사람 확인으로 돌린다. 시험관끼리 엇갈리면 프로브 1회로 직접 확인한다.
- 출력: `qa_verdict {verdict, blocking, fix_tasks[{title, files, owner, requirements}], human_checks}`. 수정 작업은 근본 원인당 하나. `human_checks`는 인물 말투로 쓴 실기 메시지 2~3개와 볼 것.
- 테스트 사용자 키는 `qa-<실행>-<석>-<n>`, 끝나면 `probe_wipe`로 지운다. 인물·데모 데이터를 오염시키지 않는다.

## 15. 마감·회고·리허설

- **마감(`CLOSING`)**: 바인딩 `feature_freeze` 시각이 지나면(저장 단계 P1~P5) 자동으로 생기고 단계가 P6이 된다. 핵심 동결 없이 왔으면(P1·P2) spec.md를 지금 요구사항으로 만들고, "핵심 동결 없이 왔으므로 지금 배포돼 있는 것이 제출본입니다 — 최종 QA로 확인합니다."를 알리고 실행에 `unfrozen=true`를 남긴다. 일정에 날짜가 없으면 시각 트리거가 없으므로 `fde run closing`으로 연다. 최종 QA 7석(tag `final`) → QA 본부장 최종 판정 ∥ 데모 시나리오 작가(`docs/demo-scenario.md`) → 릴리스 관리자 최종 태그·노트 ∥ 서기장 최종 보고서(`docs/final-report.md`) → 제출 체크리스트(바인딩 `[submission].checklist`)를 사람에게. 새 기능 금지, 제출은 사람이 한다.
- **회고(`fde run retro`)**: 회고 분석가가 이벤트·실행·결정·디스패치를 내보낸 파일(`events.json`)과 산출물로 타임라인을 재구성하고, 교훈(최대 8개, 증거·다음에 적용할 것)을 `docs/retro.md`와 전역 `~/.clonamic/fde-mode/lessons.md`(새 날짜 절을 끝에 덧붙임)에 남긴다.
- **리허설(`/fde-mode rehearsal`)**: 가짜 인물이 `rehearsal/sealed/`(persona-secret.md, hidden-requirements.json, roleplay-prompt.md)와 공개 브리프(`rehearsal/public-brief.md`)를 만든다. 사용자는 역할극 프롬프트를 **다른 채팅**에 붙여 인물을 맡기고, 브리프는 `>>brief`로 붙인다. 봉인 폴더는 디렉터와 분석 에이전트가 도구로도 셸로도, 대시보드가 파일 API로도 읽지 못한다(17.2). 끝나면 `rehearsal grade`가 봉인을 풀고 채점관이 `rehearsal/grade.md`(발견률, 특수 유형, 발견 시점, 억지 비율, 재질문, 질문 효율, 결정 부담, 시간, 조정 제안 최대 10개)를 쓴다. `rehearsal end` → `fde archive`.

## 16. AI티 측정기 (`fde aitell`)

AI티 검사관의 수치를 재현 가능하게 만드는 결정적 측정기(`src/fde_mode/aitell.py`)다. 판단(일반론, 말투 흔들림, 이 사람에게 맞는지)은 검사관이 직접 더한다.

| 범주 | 예 | 가중치 | 주요(하나면 FAIL) |
|---|---|---|---|
| 상투 서두(앞 40자) | 좋은 질문, 물론이죠, 네 알겠습니다, 궁금하셨군요 | 3 | |
| 상투 맺음(뒤 60자) | 더 궁금한 점, 언제든지 말씀, 도움이 되셨길, 좋은 하루 되세요 | 3 | |
| 번역투·문어체 | 하는 것이 가능합니다, ~에 대해, ~를 통해, 다양한, 최적의, 해당, 하시기 바랍니다 | 1 | |
| 서식 기호 노출 | `**굵게**`, `#` 헤더, 표, 코드블록, 링크 문법 | 4 | ✔ |
| 불필요한 고지 | 저는 AI라서, 정확하지 않을 수 있, 학습 데이터 | 4 | ✔ |
| 얼버무림 | ~수 있습니다, 참고하세요, 일반적으로, 것 같습니다 | 1 | |
| 불필요한 사과 | 죄송합니다만, 불편을 드려, 양해 부탁 | 2 | |
| 과장된 호응 | 물론이죠, 정말 좋은, 훌륭한, 완벽한, `!!` | 2 | |
| 어색한 외래어 | 케어, 프로세스, 솔루션, 니즈, 인사이트, 리마인드 | 1 | |
| 짧은 답의 과잉 목록 | 400자 미만 답에 목록 3줄 이상 | 2 | |

- 답마다: 범주별 적중(범주당 최대 2회 감점), 감점, 점수 `100 − 8 × 감점`, 판정(주요 범주 적중·서두와 맺음 동시·감점 8 이상이면 FAIL), 글자 수, 이모지 수, 제공자.
- 전체: 평균 점수에서 **템플릿 반복 쌍**(서로 다른 질문에 대한 답의 첫·마지막 문장 3-gram 유사도 0.6 이상) 하나당 5점(최대 30점)을 뺀 점수, FAIL 수, 범주별 비율(서두·맺음·서식·고지·번역투·호응), 평균 길이, 답당 이모지, **제공자별 평균 점수**(주 모델과 대체 모델의 말투 차이).
- `--allow "<표현>"`: 이 인물이 실제로 쓰는 표현은 감점에서 뺀다. 봇임을 밝히는 정직한 고지("저는 ○○ 도우미 챗봇이에요")는 범주에 없어 감점되지 않는다.
- 사용: `fde aitell --file replies.json [--allow 감사합니다]` (문자열 목록 또는 `[{"input","output","provider"}]`), `fde aitell --text "답1" "답2"`.

## 17. 가드 (PreToolUse 훅)

FDE 모드가 켜져 있을 때 메인 세션과 모든 서브에이전트의 도구 호출(Bash, Read, Edit, Write, MultiEdit, Grep, Glob, NotebookEdit)을 검사한다. 순서: 명령 규칙 → 봉인 → 독립석 읽기 격리 → 에이전트별 쓰기 제한.

### 17.1 명령 (기본 + 바인딩 `[guard].deny/ask` 추가)

| 판정 | 기본 규칙 |
|---|---|
| 막음(deny) | `make down`, `deploy/down.sh`, `FORCE=1`, AWS 리소스 삭제(terminate-instances, delete-security-group/key-pair/volume/db-instance/bucket/snapshot/stack, release-address, deregister-image), 광범위한 `rm -r`(/, ~, $HOME, ., *), 강제 push, `git reset --hard`, `git clean -f`, `DROP TABLE/DATABASE/SCHEMA`·`TRUNCATE`, 도커 볼륨 삭제, `.env`를 화면에 출력하는 cat/less/head/tail 등, `printenv`, 단독 `env`, `export -p`, 비밀값 이름(KEY·TOKEN·SECRET·PASSWORD)을 echo |
| 확인 요청(ask) | `RECREATE=1`·`--recreate`(벡터 컬렉션 재생성), `make up/setup/token/secret/harden*/caddy/myip`, `git push`, 작업 변경 전부 버리기(`git checkout -- .`, `git restore .`), 보안 그룹 규칙 변경, `.env`를 grep, `sudo`, `curl … | sh` |

- 막힌 명령은 우회하지 않고 사용자에게 그대로 알린다. 사용자는 터미널에서 의도적으로 실행할 수 있다. 확인: `fde guard-test -- <명령>`, 파일은 `fde guard-test --file <경로> --tool Read|Write`(FDE가 꺼져 있어도 바인딩 규칙으로 판정).

### 17.2 파일

- 비밀값 파일(`[guard].secret_files`, 기본 `.env`): 읽기·Grep 막음, 쓰기는 확인 요청. 값 확인은 `fde env check`(set/empty/missing만), 비밀이 아닌 키 변경은 `fde env set KEY VALUE`(바인딩 `env_editable` 목록만, 이름에 KEY·TOKEN·SECRET·PASSWORD·DATABASE_URL·QDRANT_URL이 있으면 거부, 값에 `#`·줄바꿈 금지).
- 보호 경로(`[guard].protected_paths`): Edit·Write·MultiEdit 막음(프로젝트 루트 기준 앞부분 일치).
- 리허설 봉인(`rehearsal/sealed`): 채점 단계(`fde run rehearsal-grade`가 켜는 `unsealed` 플래그) 전에는 Read·Grep·Glob과 **셸 명령 모두** 막는다. 셸은 `guard.rehearsal_sealed_roots`가 봉인 폴더(있을 때)를 17.5의 봉인 경로 검사에 더해 막는다. 가짜 인물·채점관만 예외.

### 17.3 에이전트별 쓰기 제한

- 적용 대상은 **FDE-Mode 명단의 에이전트**뿐이다(`fde-mode:<이름>` 또는 접두사 없는 명단 이름, `guard.is_fde_agent`). 다른 플러그인의 `fde-`로 시작하는 에이전트(시험장의 `fde-exam`, `fde-eval`, `fde-feedback`, `fde-pilot`)와 메인 세션(디렉터)은 이 제한을 받지 않는다.
- 코드 담당 8명(테크 리드, 프롬프트 엔지니어, 개발 본부장, 그래프·노드 개발자, 도구 통합 개발자, 플랫폼 연결 담당, 데이터 정제·적재 담당)만 프로젝트 파일을 고칠 수 있다.
- 나머지는 `.claude/fde-mode/` 안에만 쓴다(출력 파일, 선언된 문서). 회고 분석가는 전역 `lessons.md`도 쓴다.
- 검사 대상 도구는 Write·Edit·MultiEdit·NotebookEdit다. Bash를 가진 검사 17명이 셸로 파일을 바꾸는 것은 막지 않는다(에이전트 규칙으로만 금지).

### 17.4 독립석 읽기 격리 (`guard.BLIND_SEATS`)

| 자리 | 읽지 못하는 것(.claude/fde-mode/ 기준) |
|---|---|
| 블라인드 검증관, 반론관 | `runs/`(다른 에이전트 출력), `board.md`, `fde.db`, `snapshots/debates.json` |
| 맞춤 적합성 심사관, AI티 검사관 | `spec.md`, `docs/requirements.md`, `runs/`, `board.md`, `fde.db`, `snapshots/` |
| 리허설 채점관 | `runs/`, `board.md` |

- 이 격리도 FDE-Mode 명단 에이전트에만 적용된다(17.3과 같은 판정).
- 단, 자기 디스패치(발행·대기 중)의 입력 파일·출력 파일·출력 옆 임시 파일(`<출력 이름>.*`)은 항상 열 수 있다. 막힌 폴더를 품은 상위 폴더 전체 검색(Grep·Glob)도 막는다("받은 입력 파일로 좁혀 주세요"). Bash에서는 명령 문자열에 막힌 경로(`.claude/fde-mode/<막힌 것>` 또는 그 절대 경로)가 들어 있으면 막는다.

### 17.5 봉인 폴더 (`[guard].sealed_paths`, `sealed_readers`)

- 시험장·리허설의 정답 폴더처럼 수행 측이 읽으면 안 되는 곳. 경로는 절대 경로 또는 프로젝트 기준 상대 경로(`../문제/sealed`처럼 프로젝트 밖도 된다). `sealed_readers`에 적은 접두사(예: `fde-exam:`)로 시작하는 에이전트만 읽는다. 디렉터·FDE 에이전트는 읽지 못한다.
- 막는 것:
  - 봉인 경로 안을 가리키는 Read·Grep·Glob, 그리고 프로젝트 **밖**에 있는 봉인의 상위 폴더를 Grep·Glob으로 검색하는 것.
  - 셸 명령: 봉인 절대 경로가 문자열에 들어 있는 경우(경로 구성 요소 단위로 비교 — `…/sample1`이 `…/sample12`에 걸리지 않는다), 명령 속 경로 토큰(`..`, `../x`, `~/x`, 글롭은 앞부분까지)이 봉인 안으로 풀리거나 프로젝트 밖의 봉인 상위 폴더로 풀리는 경우(`grep -r foo ..`, `cd .. && cat 문제/sealed/…`, `find ../..`, `rg foo ../*/sealed`).
  - 프로젝트 **안**에 봉인 폴더가 있을 때 `.gitignore`를 무시하는 재귀 읽기로 그 상위를 읽는 것(`grep -r foo .`, `find … -exec`/`| xargs`, `tar`, `zip`, `rsync`, `cp -r`). `rg`와 Grep 도구는 `.gitignore`를 따르므로 허용한다 — 그래서 프로젝트 안 봉인 폴더는 `.gitignore`에 있어야 한다(카카오 프로젝트는 `kakao-demo-test/`를 무시한다).
- 허용 예(테스트로 고정): `ls docs`, `cat data/raw/a.csv`, `grep -rn foo app`, `git status`, `make test`, 메시지에 `../`가 들어간 프로브(`--message '아 ../ 그거요'` — 작은따옴표로 감싼 한 덩어리라 봉인 경로로 풀리지 않는다).

## 19. 워크플로 엔진 (`fde next`)

- 흐름은 모델이 기억하지 않고 코드가 계산한다. 파이프라인은 단계의 목록이고, 단계는 먼저 **스크립트**(코드, 밀리초)를 실행한 뒤 **에이전트 디스패치**를 낸다. 단계의 디스패치가 모두 끝나야(유효한 출력, 또는 2번 실패) 다음 단계로 간다. 여러 실행이 동시에 돈다(빠른 라운드 ∥ 백그라운드 토론 ∥ 조각 ∥ 데이터).
- `fde next` 한 번: 트리거 확인 → 진행 중인 실행 전진(대기·이동·종료 포함) → 출력 검증·반영 → 오래된 디스패치 재발행 → 새 디스패치 발행 → 물어볼 결정(최대 4개). 단계 스크립트가 새 실행을 만들면(동결 → `BUILDPLAN`, 변경 → 재계획, QA → 수정 조각·재계획) 같은 호출 안에서 그 실행도 전진시킨다(최대 6번, 실행마다 한 번). 그래서 "할 일 없음"으로 멈췄는데 새 작업이 다음 메시지까지 띄워지지 않는 일이 없다. 출력 JSON: `dispatch`(id, subagent_type, agent, title, background, prompt), `ask`, `notify`, `waiting`, `human`, `reports`, `idle`, `active_runs`.
- 디렉터는 `background=false` 디스패치를 한 메시지에 모아 동시에 띄우고 기다린 뒤 다시 `fde next`, `background=true`는 백그라운드로 띄우고 끝나면 다시 `fde next`. 프롬프트는 **그대로** 전달한다(디렉터가 고치지 않는다). `subagent_type`은 `fde-mode:<에이전트>`(환경 변수 `FDE_AGENT_PREFIX`로 바꿀 수 있음). Agent 호출에는 `run_in_background`를 항상 값으로 적는다(빼면 백그라운드로 뜬다).
- **`fde wait`**: 실측 스모크에서 `run_in_background:false`로 띄운 Agent 호출 18개 중 9개가 "Async agent launched"로 돌아와 기다리지 않고 지나갔다. 그래서 하나라도 비동기로 돌아오면, 그 메시지의 호출이 다 돌아온 뒤 Bash로 `fde wait`(Bash 타임아웃 600000)를 실행한다. 발행된 포그라운드 디스패치(무인 실행이거나 `--all`이면 전부)의 출력 파일이 모두 생길 때까지 기다리고(기본 540초, 3초 간격), 남은 것이 없으면 종료 코드 0, 시간이 다 되면 3을 내고 `{pending, waited_s, next: "fde next"}`를 출력한다. 그다음은 늘 `fde next`(늦은 것의 재발행·실패 처리는 엔진이 한다). 디렉터가 모니터나 sleep 반복을 직접 만들지 않는다(fde-director 스킬 2·9절).
- 디스패치 프롬프트: `FDE DISPATCH <id>` / 역할·모드·실행·라운드 / 프로젝트 루트 / 먼저 읽을 것(contract.md, rubric.md, 플랫폼 프로필) / 입력 파일 목록 / 이번 라운드 새 발화 범위 / 쓸 JSON 파일 하나와 봉투 / 임시 파일 위치 / 추가로 쓸 수 있는 문서 / 메모 / 이전 시도의 거절 사유 / "디렉터에게 한국어 3줄 이내 + 출력 경로".
- 출력 계약 `fde.out.v1`: `schema, agent, mode, run, covers_until, summary_ko, <모드별 필수 섹션>, extra`. 모드별 필수 섹션(`sync.REQUIRED`)이 없거나 JSON이 아니면 거절하고 오류와 함께 한 번 다시 보낸다(최대 2번, 이후 실패로 건너뛰고 경고). 같은 단계를 다시 돌릴 때 이전 출력은 `.prevN.json`으로 보존한다.
- 25분(`stale_minutes`) 넘게 출력이 없으면 다시 보낸다(2번째면 실패).
- 무인 실행 `fde on --autopilot`(시험장 운전석 `fde-pilot`, 헤드리스 `claude -p`): 헤드리스에서는 턴이 끝나면 세션이 끝나 백그라운드 알림을 기다릴 수 없으므로, `fde next`가 모든 디스패치를 포그라운드(`background=false`)로 낸다. 디렉터는 결정을 AskUserQuestion으로 묻지 않고 운전석 운영자(`fde-pilot:fde-pilot-operator`)의 규칙을 따르거나, 운전석이 없으면 `recommended`로 `fde decide`한다. 무인 실행은 자율 모드가 아니어서 협업 질문도 그대로 생기고 운영자가 답한다. 사람 확인(`human`)은 운전석의 사람 대역이 로컬 프로브로 대신하고 결과를 `fde ingest --kind note`로 넣는다(운전석이 없으면 통과로 치지 않는다). fde-director 스킬 9절.

## 21. 대시보드

- `fde serve --detach`(켜기 절차에 포함): 127.0.0.1의 28420번부터 빈 포트, 표준 라이브러리 서버(ThreadingHTTPServer). 이미 떠 있으면 재사용하고, 플러그인 버전이 바뀌었으면 다시 켜라고 알린다(`fde serve --status`, `--stop`).
- 보안: 127.0.0.1에만 묶이고, Host 헤더가 127.0.0.1/localhost가 아니면 403(DNS 재바인딩 방지). `/api/` 읽기도 Origin이 다른 사이트이거나 `Sec-Fetch-Site: cross-site`면 403(대화 원문이 다른 사이트에서 읽히지 않게). 쓰기(POST·PUT·DELETE)는 `X-FDE: 1`과 **서버를 띄울 때마다 바뀌는 토큰**(`X-FDE-Token`, 페이지 `<meta name="fde-token">`)이 있어야 한다. 본문은 2MB까지, 다른 사이트가 화면을 iframe으로 띄우지 못한다(`X-Frame-Options: DENY`). 파일 보기 API(`/api/file?path=`)는 작업 폴더 안의 텍스트 파일(.md .json .jsonl .txt)만, 경로에 `sealed`가 있으면 거부.
- 여러 프로젝트: 전역 `registry.json`에 있는 프로젝트만 `?project=<루트>`로 고를 수 있고, 없으면 가장 최근 프로젝트를 보여 준다. 주소로 탭을 바로 열 수 있다(`/#convo`, 좁은 화면 열은 `#convo:claude`·`#convo:notes`).
- API: `GET /api/<overview|cards|decisions|requirements|persona|debates|data|build|org|events|transcript|reports|board>`, `/api/file`, `/api/ping`, `/api/projects`. 대화 화면: `GET /api/convo?since=&rsince=`, `GET /api/chat?since=`, `GET|POST|PUT|DELETE /api/drafts`, `POST /api/drafts/save`, `GET|POST|PUT /api/notes`, `GET /api/gaps`. 쓰기: `POST /api/question`(질문 카드 상태)과 대화 화면의 임시 턴·메모뿐.
- 탭 13개: 개요(지표·시간표·스위치·알림·실행), **대화**(아래), 질문 카드(복사 버튼, 물어봄/가정으로/버림/보류/다시 열기, 가정 목록, 억지·중복 탈락 목록과 낸 렌즈), 결정, 보고서, 요구사항(잠금 🔒·실현 가능성·근거·수용 테스트·위험), 인물 패턴(persona.md, 최근 지표, 개인화 표, 사용 환경 `environment.md`, 전달 형태 `packaging.md`, 용어 사전, 가상 사용자 메시지), 토론(쟁점·중재·소수 의견·입장 변화·회의록), 데이터, 구현(작업·ADR·릴리스·QA 산출물·spec), 조직 현황(디스패치·명단), 발화 표(발화·태그·영역·질문 형식·화자 확신), 기록(이벤트).
- 결정은 대시보드에서 하지 않는다. 메인 대화가 결정의 자리다.

### 21.1 대화 화면 (탭 "대화")

맨 위에는 "놓친 것" 띠와 그 아래 **단계 띠**(S1~S8, 지금 단계 강조, 빈칸 수, ↺ 다시 열림)가 따로 있다. 단계를 누르면 그 단계의 빈칸 목록과 단계 카드(상태, 근거 U 번호 표시)가 펼쳐지고, 카드를 누르면 질문 카드 탭의 그 카드로 간다. 메모 열 위의 **의뢰 유형·역할 지도** 패널은 칸마다 근거 U 버튼을 두고(누르면 그 말풍선), 그 유형에 꼭 필요한 칸의 "모름"만 강조한다(나머지는 "필요하면 확인"). 데이터는 `GET /api/stages`이고, 실패하면 띠와 패널을 숨긴다.


입력은 처음 연 Claude Code 세션에 붙여넣는 그대로이고, 이 화면은 그것을 보여 준다. 웹에서 쓰는 것은 저장 버튼으로 확정하는 두 가지뿐이고, 웹에서 Claude Code로 입력을 보내는 기능은 없다.

| 자리 | 보이는 것 | 쓰는 것 |
|---|---|---|
| 위 "놓친 것" | 아직 안 물어본 높음 카드, 물었지만 답 못 받은 질문, 아무 데도 반영 안 된 인물 발화(요청 태그 또는 문제·예외·성공기준·우선순위 영역인데 카드·요구사항 근거 0), 근거 없는 메모(대화·자료에 없는 숫자·시각·날짜·따옴표 이름), 근거 없는 업종 낱말(1개도 경고, 플랫폼·기술 뜻 어구는 `src/fde_mode/run_time_ok.json`으로 뺌). 누르면 그 자리로 간다 | — |
| 왼쪽 인물 ↔ 나 | 라운드 구분선(R03 · 14:20 · 발화 12 · 분석 상태), 인물 말풍선(왼쪽)·내 말풍선(오른쪽), U 번호, 반영 표시(이 발화를 근거로 한 카드·요구 수) | [인물·나] 고르고 Enter로 임시 턴(점선), 고치기·지우기·순서 바꾸기, 대화를 통째로 붙여넣으면 나눠서 화자 확인, [저장]이면 붙여넣기와 같은 경로(`transcript.ingest`, source=web)로 새 라운드 |
| 가운데 나 ↔ Claude | 내 프롬프트(오른쪽)와 Claude 답(왼쪽, 마크다운, 긴 답은 접힘), 붙여넣은 인터뷰는 "대화 원문 R05 · 발화 12" 칩(누르면 왼쪽 그 라운드), 라운드 보고서, D1/D2 결정 카드(질문과 선택지마다 [복사]) | 보기만 |
| 오른쪽 메모 | 메모 목록, 저장 안 됨 표시, 기록에 없는 것 경고 | 제목·본문, 말풍선의 [메모에 연결] 또는 U 번호 입력으로 근거 연결, [저장](자동 저장 아님, 다른 창이 먼저 저장했으면 덮어쓰지 않음) |

- 수집: UserPromptSubmit 훅이 프롬프트를, Stop 훅이 그 턴의 Claude 답(세션 기록 끝 64KB, 도구 출력·서브에이전트 글 제외)을 `convo`에 넣는다. 비밀값 꼴(sk-…, KakaoAK …, Bearer …, token=…, 긴 키)은 가린다. 아무것도 출력하지 않고, 데이터베이스 잠금은 50ms만 기다린다. 실패해도 프롬프트·턴 종료 판정은 그대로다.
- 웹에서 저장하면 다음 프롬프트 상태 줄에 "웹 저장: 인터뷰 턴 n·메모 n"이 붙는다. 메모는 `docs/interviewer-notes.md`로도 나가고, 확인 요약 작성관·문서 감사관·인터뷰 코치만 기록과 대조한다. 메모는 인물 근거(U)로 쓰지 않는다.
- 2초마다 새 항목만 가져오고, 맨 아래를 보고 있을 때만 따라 내려간다. 넓으면 3열, 좁으면(899px 이하) 열 버튼으로 바꾼다. 시스템 밝게·어둡게를 따르고 글자 대비 4.5:1 이상, 말풍선 최대 너비 72%.
- 단축키: `/` 검색(입력 중에는 아님), ⌘S·Ctrl+S 저장, Esc 임시 턴 입력·고치기·붙여넣기 확인 취소. 한글 IME가 글자를 만드는 중에 누른 Enter·Esc는 무시한다.
- 스위치: 바인딩 `[switches]`의 `conversation_view`(탭과 경로), `capture_claude_turns`(훅 수집). 둘 다 기본 켬. `capture_claude_turns = false`면 수집만 멈춘다.

## 24. 프로브 계약

QA·데이터 에이전트는 프로젝트의 프로브로 실제 봇을 돌린다. 바인딩이 이 계약을 지키는 명령을 제공해야 한다.

| 명령 | 자리표시자 | 동작 |
|---|---|---|
| `probe_local` | `{user}`, `{message}`(선택 `{conv}`) | 로컬에서 파이프라인 1회(플랫폼에 보내지 않음). 대량 QA용 |
| `probe_remote` | 같음 | 서버(실제 저장소·검색)에서 1회. 실서비스와 같은 기계라 한 번에 하나씩만 돈다. 좌석당 3개 이하, 배포 확인용 |
| `probe_wipe` | `{user}` | 그 테스트 사용자의 프로필·기억·대화 삭제 |

- 출력: 표준 출력 마지막 줄 JSON — `bubbles`, `quick_replies`, `elapsed_s`, `provider`, `onboarding`, `fallback`, `response`(플랫폼 원본), `error`, 가능하면 `trace`, `profile_after`, `memories_after`, `extract_s`, `mode`(검색이 돌았는지 `rag: local|server|off`).
- 메시지는 작은따옴표로 감싸고 안의 `'`는 `'\''`로 바꾼다. 프로브 1회 = 실제 모델 호출이므로 Bash 타임아웃 300초.
- 사용 규칙(계약 `references/contract.md` 4절 "Probe policy"):
  - **대량은 `probe_local`**: 같은 코드, 격리된 테스트 저장소. 서로 다른 테스트 키는 동시에 돌려도 된다. 프로브가 검색을 못 돌렸으면(`mode`) 그 동작은 FAIL로 치지 않고 `extra.unverified`에 적는다.
  - **`probe_remote`는 아껴서**: 실서버에서 한 번에 하나씩(나머지는 줄을 선다). 좌석당 디스패치 하나에 3개 이하, 배포를 증명하는 것(must 경로, 실제 지연)만. 비어 있으면 로컬만 쓴다.
  - **키**: `qa-<실행 id 소문자>-<석>-<n>`. 시뮬레이션 사람·대화마다 키 하나, 인물의 실제 키는 절대 쓰지 않는다. 출력 전에 쓴 키를 모두 `probe_wipe`로 지우고 `extra.users_wiped`에 적는다.
  - 프로브로 증명할 수 없는 것(실제 플랫폼 화면, 웹훅·응답 토큰 경로, 콘솔 설정)은 QA 본부장이 `human_checks`로 사람에게 넘긴다.
- 카카오 프로젝트 구현: `scripts/probe.py`(`say`/`wipe`/`ingest`/`health`/`reset`). 카카오 콜백만 가로채 같은 파이프라인을 1회 실행한다. 로컬은 사용자별 상태 파일(`.probe/users/<키>.json`)로 대화·프로필·기억이 프로세스를 넘어 이어지고, 백그라운드 기억 추출을 기다렸다 저장한다(`extract_s`). 로컬 RAG는 `probe.py ingest`로 임베딩한 문서(`.probe/docs.*`)를 메모리 Qdrant(서버와 같은 필터)로 검색한다. 서버는 `deploy/probe_remote.sh`(메시지를 base64로 넘기고 서버에서 잠금으로 한 번에 하나), 지우기는 `deploy/probe_wipe.sh`.

## 26. 시험장(arena)과의 관계

같은 저장소의 `FDE-Mode/` 아래에 이 제품과 시험장 4팀이 플러그인으로 함께 있다. 시험장은 이 제품을 실전 조건으로 자율 시험하고 개선하는 장치다(계약 원본: `FDE-Mode/Docs/arena-contract.md`, 비공개).

| 팀 | 플러그인 | 이 제품과의 관계 |
|---|---|---|
| 문제출제팀 | `fde-exam` | 분야가 겹치지 않는 매우 어려운 문제(공개 브리프, 봉인된 인물·숨은 요구사항·숨은 수용 테스트·환경·데이터)와 인물 배우 |
| 수행팀 | `fde-mode`(이 제품) + `fde-pilot` | 운전석의 운영자 에이전트가 사용자 역할: 카드를 인물 배우에게 그대로 옮기고, 대화를 `fde ingest`로 넣고, 결정에 답한다. 제품은 `fde on --autopilot`으로 `claude -p --plugin-dir`에서 돈다 |
| 평가팀 | `fde-eval` | 13개 관점(요구사항 발견, 인터뷰, 기능, 맞춤, UX, UI, AI티, 환경, 플랫폼, 엔지니어링, 프로덕션, 과정, 심사)으로 숫자 채점 |
| 피드백팀 | `fde-feedback` | 놓친 요구의 원인을 단계별로 추적하고, 두 문제 이상에서 같은 원인이 보이거나 일반 원칙으로 설명될 때만 이 제품을 고친다(특정 문제 맞춤 금지) |

- 위치: 시험장은 대회 프로젝트 안의 `kakao-demo-test/`(git 무시). 문제 하나 = `sampleN/` 하나(`문제/`, `답지/`, `REPORT.md`), 같은 문제는 다시 내지 않고 번호만 늘어난다(sample6, 7 …).
- 답지(`sampleN/답지/`)는 봇 뼈대의 사본에 시험용 바인딩을 넣은 별도 프로젝트다. 수행 측은 봉인을 읽지 못한다: 시험용 바인딩의 `sealed_paths`(자기 문제의 `sealed`·`data`·`exam-review.md`, `REPORT.md`, 시험장 `docs`, 다른 sample 전부) + 가드(17.5, 경로 구성 요소 단위 비교). `sealed_readers`는 `fde-exam:`, `fde-eval:`, `fde-feedback:`(접두사 없이 등록되는 환경을 위해 `fde-exam-` 등도)라서 디렉터·FDE 에이전트·운전석 운영자는 읽지 못한다. 시험장 플러그인 에이전트는 FDE 쓰기 제한·독립석 격리·에이전트 카드 주입 대상이 아니다(17.3).
- 시험 중에는 실서버·AWS·카카오에 손대지 않는다. 시험용 바인딩의 `deploy`는 로컬 검사(테스트 + 앱 임포트 + 프로브 상태)이고, QA·평가는 로컬 프로브로 한다.
- 시험용 바인딩의 시간표는 실전 바인딩과 같은 비율이다: 시작 기준 핵심 동결 +70분, 전체 동결 +210분, 기능 동결 +270분, 제출 +290분, 끝 +300분(실전 11:10·13:30·14:30·14:50·15:00). `arena setup --scale 0.5`면 모두 절반.
- 운전석 루프(`arena loop`)는 실전을 지킨다: 대회 바인딩의 날짜·시작·끝을 보고 실전 3시간 전부터 끝난 30분 뒤까지는 시작하지 않고, 그 전(또는 `--stop-at`)에 스스로 멈추며, 끝까지 못 마칠 단계는 시작하지 않는다(`--ignore-event`로 끔). `--no-patch`면 피드백팀이 분석만 하고 제품을 고치지 않는다.

## 27. 의존성과 설치

### 27.1 의존성

- Claude Code(플러그인·스킬·서브에이전트·훅). 서브에이전트 모델 `claude-opus-5-5`, 추론 강도 `high`/`xhigh`.
- Python **3.12 이상**, 표준 라이브러리만(SQLite, http.server, tomllib). `bin/fde`가 `FDE_PYTHON` → python3.14 → 3.13 → 3.12 → python3 → Homebrew 경로 순으로 찾고, 없으면 `uv run --python 3.12`로 실행한다. 둘 다 없으면 훅은 조용히 넘어가고 명령은 설치 안내를 낸다(`uv python install 3.12` 또는 `brew install python@3.12`).
- 플러그인 규격: Agent Plugins 1.0.0(루트 `plugin.json`의 `$schema`) + `.claude-plugin/plugin.json`.

### 27.2 설치 (마켓플레이스 `clonamic`)

1. 마켓플레이스 `plugin/.claude-plugin/marketplace.json`의 `plugins` 목록에 다른 clonamic 플러그인과 같은 꼴로 `{"name": "fde-mode", "source": "./FDE-Mode/FDE-Mode", "version": "1.0.0", "description": "…"}`가 있어야 한다.
2. 쓰는 프로젝트의 `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "clonamic": { "source": { "source": "directory", "path": "/Users/<you>/…/clonamic-plugin-skills/plugin" } }
  },
  "enabledPlugins": { "fde-mode@clonamic": true }
}
```

3. 폴더를 신뢰하면 마켓플레이스가 등록된다. 등록이 안 되면 `/plugin`(또는 `claude plugin marketplace add <경로>` → `claude plugin install fde-mode@clonamic`)으로 한 번 설치한다.
4. 대안: `claude --plugin-dir /…/plugin/FDE-Mode/FDE-Mode` (마켓 없이 그 세션에만 로드, 시험장 운전석이 쓰는 방식).
5. 확인: `fde doctor`, `claude plugin validate /…/plugin/FDE-Mode/FDE-Mode`.
