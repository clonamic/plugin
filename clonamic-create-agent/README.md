# clonamic-create-agent

## 핵심 요약

- 사용자와 AI가 대화하며 에이전트 파이프라인을 노드와 간선의 그래프로 설계하고, 그 설계를 구현 방식에 묶이지 않는 문서로 끝까지 정리하는 플러그인이다.
- 명령은 `/clonamic-create-agent [프로젝트명 또는 만들고 싶은 것]` 하나이고, 사용자가 직접 입력했을 때만 실행된다.
- 실행하면 로컬 웹 편집기가 열린다. 가운데 캔버스에서 그래프를 보고 고치고, 오른쪽 사이드바에서 각 노드와 연결의 내용을 채우며, 검토 챗봇이 설계를 객관적으로 평가해 제안한다.
- 결과물은 사용자가 지정한 폴더에 내보내는 설계 문서 묶음이다. 전체 흐름(Mermaid), 에이전트 문서, 단계 문서, 연결 문서, 용어 사전, 변경 이력으로 이루어진다.
- 코드는 만들지 않는다. 문서를 스킬(.md), 플러그인, 웹, 앱, Hermes, LangGraph 등 어디로든 옮겨 구현할 수 있게 하는 것이 목적이다.

## 1. 문제 정의

- AX 자동화의 기본은 여러 기능이 모여 하나의 파이프라인을 이루는 것이다. 그래서 설계 단계가 결과를 좌우한다.
- 파이프라인은 기능과 분기로 이루어진다. 노드와 간선으로 생각하는 LangGraph의 방식이 이 구조를 가장 잘 담는다.
- 설계에는 세 가지가 필요하다.
  - 한눈에 보기: 전체 흐름이 시각적으로 바로 보여야 한다.
  - 재현성: 정확한 문서만으로 누구나 같은 파이프라인을 다시 만들 수 있어야 한다.
  - 쉬운 수정: 파이프라인마다 나중에 고치기 쉬워야 한다.
- 이 플러그인은 파이프라인을 한눈에 보여 주고, 쉽게 고칠 수 있게 하며, 설계와 그 과정을 여기서 완전히 문서화한다.

## 2. 목표와 범위

| 구분 | 내용 |
|---|---|
| 하는 것 | 사용자의 의도를 확인하고, 에이전트와 단계의 그래프를 설계하고, 객관적으로 검토하고, 설계와 결정 과정을 문서로 완성한다 |
| 하지 않는 것 | 코드 생성, 실행, 테스트. 특정 구현 방식(프레임워크, 언어)에 맞춘 문서 |
| 문서의 쓰임 | 사람이 직접 코드로 구현, 스킬이나 플러그인으로 구성, 웹·앱·Hermes·LangGraph 등으로 구현, AI에게 맡겨 구현 |

- LangGraph는 설계 사고의 틀(노드, 연결, 조건 분기, 시작과 끝, 하위 그래프)로만 쓴다. 문서에는 LangGraph 용어나 코드 용어가 드러나지 않는다.
- 문서는 기능과 분기 자체에만 집중한다. 변수 이름, 함수 이름 같은 어려운 말 없이, 깔끔하고 읽기 쉽게 쓴다.

## 3. 용어

| 용어 | 뜻 |
|---|---|
| AI | 모델이 아니라 Claude Code, Codex, Grok Build, Cursor 같은 에이전트 도구 |
| 에이전트 폴더 | 호스트마다 다른 설정 폴더. `.claude`, `.codex`, `.grok`, `.cursor` 등. 이 문서의 `.claude`는 예시다 |
| 프로젝트 | 설계 하나. 하나의 파이프라인이다 |
| 에이전트 | 역할 하나를 맡는 큰 노드. 1에이전트 = 1기능 |
| 단계 | 에이전트 안에서 그 역할을 이루는 노드. 하나의 기능을 한다 |
| 연결 | 노드와 노드를 잇는 간선. 항상 이어지는 연결과 조건에 따라 갈리는 연결이 있다 |
| 출구 | 에이전트 안의 흐름이 끝나는 지점. 출구마다 에이전트 사이의 연결 하나로 이어진다 |
| 제안 카드 | 검토 챗봇이 낸 개선안. 사용자가 "적용"을 눌러야 반영된다 |

## 4. 사용 흐름

1. 사용자가 `/clonamic-create-agent`를 입력한다. 뒤에 만들고 싶은 것을 적으면(예: `여행 일정 짜주는 에이전트`) 첫 입력으로 쓴다.
2. 준비를 확인한다. Python 3.12 이상, clonamic-korean 설치 여부(없으면 설치), 편집기 서버를 확인한다.
3. 브라우저에 편집기가 열린다.
4. **의도 인터뷰**: 웹 채팅에서 빈 곳만 한 번에 하나씩, 추천 답과 함께 묻는다. 원하는 것, 받는 것과 내놓는 것, 성공 기준, 제약, 사람 개입 지점을 묻는다. 프로젝트 문서의 "의도"가 채워지면 끝난다. 답은 바로 그 칸에 저장된다.
5. **에이전트 초안**: AI가 에이전트 단위 그래프를 그린다. 사용자가 역할 나누기를 확인한다.
6. **단계 초안**: 에이전트마다 내부 단계를 그리고 각 문서 칸을 채운다.
7. **검토**: 검토 챗봇이 평가하고 제안 카드를 낸다. 사용자는 직접 고치거나 카드를 적용한다.
8. **내보내기**: 검사 → 한국어 다듬기 제안과 적용 → 문서 생성 순서로 진행한다.
9. 브라우저 탭을 모두 닫으면 끝난다.

- 이미 있는 프로젝트를 열면 인터뷰를 건너뛰고 저장된 상태에서 이어간다.

## 5. 편집기 화면

| 위치 | 내용 |
|---|---|
| 왼쪽 사이드바 | 프로젝트 목록(이름), 새 프로젝트, 가져오기(`design.json`), 삭제(⋯ 메뉴에서 프로젝트 이름을 입력해 확인. DB에서만 지우고 내보낸 문서 폴더는 그대로 둔다) |
| 상단 | Colab처럼 바로 바꿀 수 있는 프로젝트 이름, 저장 상태(`저장됨 · 방금`), 내보내기 |
| 가운데 캔버스 | n8n처럼 흐름이 보이고 Figma처럼 조작하는 그래프. 기본 화면은 에이전트 지도이고, 에이전트를 더블클릭하면 그 내부 단계로 들어간다. 상단 경로(`프로젝트 › A1 여행 계획`)로 돌아온다 |
| 오른쪽 사이드바 | `[문서] [검토]` 탭. 문서 탭은 클릭한 노드나 연결의 템플릿 섹션별 입력칸과 md 미리보기, 검토 탭은 검토 챗봇과의 대화 |

- 노드는 직사각형, 연결은 화살표로 깔끔하게 그린다.
- 노드 안에는 이름(짧은 기능명)만 쓴다. 예: 설계 검토, 질문 생성, 여행 정보 분석, 내용 확인. 상세 내용은 문서에만 쓴다.
- 에이전트마다 색을 자동으로 정하고 사용자가 바꿀 수 있다. 내부 단계 노드는 소속 에이전트의 색을 따른다.
- 노드나 연결을 클릭하면 문서 탭이 열린다. 빈 곳을 클릭하거나 처음 의도 인터뷰를 할 때는 검토 탭이 열린다.
- AI가 답하면 검토 탭에 새 메시지 표시가 붙는다. 입력 중인 흐름이 끊기지 않도록 탭은 저절로 바뀌지 않는다.
- 제안 카드에 마우스를 올리면 바뀌는 노드와 연결이 캔버스에 강조된다.
- 그래프 조작은 이동, 확대와 축소, 드래그로 연결하기, 자동 정렬이다. AI가 그린 초안은 자동 정렬로 배치된다.
- UI는 꼭 필요한 것만 둔다. 기능의 로직과 단계의 품질이 먼저이고, 나머지 UI는 필요해질 때 더한다.

## 6. 그래프 모델

- 깊이는 두 단계로 고정한다: 프로젝트 → 에이전트 → 단계. 에이전트 안에 에이전트를 넣지 않는다.
- 에이전트 사이의 연결은 에이전트 단위 그래프에만 둔다.
- 에이전트 안에는 시작과 하나 이상의 출구를 둔다. 출구와 에이전트 사이 연결은 1:1로 맞는다. 예: 검증 실패 출구 → 수정 에이전트.
- 에이전트가 하나뿐인 프로젝트도 같은 구조를 쓴다.

| 대상 | 번호 |
|---|---|
| 에이전트 | A1, A2 … |
| 에이전트 사이 연결 | L1, L2 … |
| 단계 | A1-N1, A1-N2 … |
| 에이전트 안의 연결 | A1-L1, A1-L2 … |

- 번호는 시작점부터 흐름 순서대로 매긴다.
- 되돌아가는 연결(반복)에는 반드시 탈출 조건이 있어야 한다. 예: 이 되돌림이 2번째면 대신 A2-L5로 간다.
- 단계마다 유형 하나를 붙인다: `판단`, `처리`, `외부 연동`, `사람 확인`.

## 7. 검토 챗봇

- 플러그인을 실행한 AI 세션의 서브에이전트가 맡는다. 서브에이전트를 읽지 못하는 Codex에서는 같은 세션이 같은 기준으로 직접 검토한다.
- 별도 터미널 세션은 쓰지 않는다. 한 프로젝트에는 대기하는 세션이 하나만 붙고, 나중에 실행한 세션이 이어받는다.
- 현재 설계의 주의점, 보완할 점, 개선할 점을 객관적으로 평가한다. 불필요한 과정을 줄이는 방향으로 제안하고, 억지 개선은 하지 않는다.
- 권한
  - 처음 초안은 AI가 직접 그린다.
  - 이후 개선안은 제안 카드로 낸다. 무엇을 왜 바꾸는지와 바뀌는 노드·연결을 보여 주고, 사용자가 "적용"을 눌러야 반영된다.
  - 사용자는 언제든 직접 고칠 수 있다.
- 적용한 제안은 프로젝트 문서의 "설계 결정"에 자동으로 한 줄 남는다. 거절한 제안은 문서에 남기지 않는다.

### 웹 메시지 대기

웹을 연 그 세션이 대기하며 메시지를 받는다. 네 호스트 모두 같은 대기 스크립트를 쓴다.

| 호스트 | 방식 |
|---|---|
| Claude Code | Monitor로 대기 스크립트를 실행한다. 메시지가 올 때마다 한 줄이 출력되어 AI가 깨어난다. 터미널이 묶이지 않고, 30분마다 다시 건다 |
| Grok Build, Codex | 대기 스크립트가 메시지가 오거나 110초가 지나면 돌아온다. AI는 답하고 다시 실행한다. Grok 기본 명령 제한 120초 안이고, Codex는 150초 명령을 끊지 않았다 |
| Cursor | 같은 반복이고 대기 시간은 55초다. 명령 제한을 확인하지 못해 안전한 값으로 둔다 |

- 30분 동안 채팅이 없으면 AI가 대기를 멈추고, 검토 탭에 "AI 대기 멈춤 — 터미널에서 '계속'이라고 입력하세요"를 표시한다. 그사이 보낸 메시지는 SQLite에 쌓였다가 대기를 다시 시작하면 차례대로 처리된다.
- AI 대기가 멈춰도 편집과 자동 저장은 그대로 동작한다. 서버의 수명은 브라우저 탭에 묶여 있다.
- 탭을 모두 닫으면 대기 스크립트가 "closed"를 돌려주고, AI가 마무리 보고를 한다.
- 대기 스크립트의 출력은 짧은 JSON 한 줄이다(Grok 출력 제한 20KB).

### 평가 기준

위에 있을수록 먼저 본다.

| 순위 | 기준 | 보는 것 |
|---|---|---|
| 1 | 구조 정합 | 아래 내보내기 전 검사 항목. 스크립트가 찾고, 챗봇은 왜 문제인지와 고치는 방법을 설명한다 |
| 2 | 의도 부합 | 설계가 "원하는 것"과 "성공 기준"을 달성하는가. 검증 시나리오가 성공 기준을 모두 확인하는가 |
| 3 | 불필요한 과정 | 합쳐도 되는 단계, 판단 없이 전달만 하는 단계, 같은 일을 하는 두 단계, 역할이 겹치는 에이전트 |
| 4 | 분기 품질 | 조건을 실제로 판별할 수 있는가. 규칙으로 될 일을 AI 판단으로 맡기지 않았는가. 실패 경로가 빠지지 않았는가 |
| 5 | 위험과 제약 | 결제, 발송, 삭제처럼 되돌리기 어려운 동작 앞에 사람 확인이 있는가. 제약을 어기는 흐름이 있는가 |
| 6 | 문서 명확성 | 다른 사람이 문서만 보고 구현할 수 있는가. 받는 것과 내놓는 것이 구체적인가. 판단 단계의 "고정과 재량"이 비어 있지 않은가 |

### 제안 규칙

- 근거 필수: 제안마다 걸리는 기준, 대상 번호, 고치지 않으면 무엇이 깨지는지를 적는다. 근거를 댈 수 없으면 제안하지 않는다.
- 억지 개선 금지: 문제가 없으면 "문제 없음"이라고만 답한다. 취향 차이와 문장 다듬기는 제안하지 않는다. 문장은 한국어 다듬기 단계가 맡는다.
- 중요한 것부터 낸다. 사소한 것 여러 개는 카드 하나로 묶는다.
- 카드 형식: 제목, 근거(기준·대상 번호), 바꿀 것(추가·삭제·수정 목록), 효과, [적용] 버튼.
- 검토 시점: 에이전트 초안 뒤, 단계 초안 뒤, 사용자가 요청할 때, 내보내기 전(검사 결과 요약). 평소 질문에는 답만 하고, 관련이 있을 때만 제안한다.

### 내보내기 전 검사

아래 중 하나라도 걸리면 내보내지 않고 해당 위치를 표시한다. 검토 챗봇도 같은 항목을 평가의 근거로 쓴다.

- 앞 단계가 내놓은 것을 뒤에서 받지 않거나, 받는 것을 앞에서 아무도 내놓지 않는다.
- 같은 출발점의 조건 연결끼리 겹치거나 빠진 경우가 있다.
- 에이전트의 출구와 에이전트 사이 연결이 1:1로 맞지 않는다.
- 막다른 단계가 있거나, 시작점에서 닿을 수 없는 단계가 있다.
- 되돌아가는 연결에 탈출 조건이 없다.
- 용어 사전에 없는 데이터 이름이 쓰였거나, 비슷한 이름이 두 개 있다(예: 여행 조건 / 여행 요구사항).
- 필수 섹션이 비어 있다.

장황함이나 불필요한 내용은 검사로 막지 않고, 검토 챗봇이 판단해 제안한다. `판단` 유형 단계에 "고정과 재량"이 비어 있으면 채우도록 제안한다.

```text
├── CHANGELOG.md                    # 변경 이력
├── edges/
│   └── L1_<이름>.md                # 에이전트 사이 연결
├── A1_<에이전트_이름>/
│   ├── README.md                   # 에이전트 문서
│   ├── steps/A1-N1_<단계_이름>.md
│   └── edges/A1-L1_<연결_이름>.md
└── design.json                     # 다시 가져오기용 전체 구조(좌표·색 포함). 사람이 읽는 문서가 아니다
```

- 파일 이름은 `번호_이름.md`이고, 이름의 공백은 `_`로 바꾼다. 공백이 있으면 md 링크가 깨진다.
- 연결 이름은 조건 연결이면 조건 요약(예: 후보 부족), 항상 연결이면 도착 단계 이름이다. Mermaid의 연결 라벨과 같다.
- 루트(에이전트 폴더 + `edges/`)와 에이전트 폴더(`steps/` + `edges/`)는 같은 모양이다.

### 공통 규칙

- **구조는 고정한다.** 섹션 이름과 순서, 필수와 선택, 표의 칸, 번호와 링크 형식은 모든 프로젝트에서 같다. 그래서 일관성이 보장된다.
- **내용은 가이드한다.** 글자 수, 문장 수, 줄 수 같은 숫자 제한은 두지 않는다. 섹션마다 무엇을 담고 무엇을 담지 않는지만 정하고, 작성하는 AI를 믿는다.
- 설계 문서이므로 결정에 필요한 내용만 쓴다. 같은 사실은 한 곳에만 쓰고, 꾸밈말, 일반론, 당연한 말은 쓰지 않는다.
- 선택 섹션이 비면 섹션째 생략한다. "없음"이라고 쓰지 않는다.
- 제목: H1은 `번호 · 이름`이다(번호가 없는 프로젝트 README, GLOSSARY, CHANGELOG는 이름만). H2는 고정 섹션이다. H3는 쓰지 않는다.
- 한 줄에 속성이 둘 이상이면 표, 하나면 글머리표를 쓴다. 체크박스는 완료 기준과 미결 사항에만 쓴다.
- 링크는 항상 `[A1-N2 질문 생성](…)`처럼 번호와 이름을 함께 쓴다. 본문에 번호만 쓰지 않는다.
- Mermaid는 README 파일에만 파일당 하나 둔다. 방향은 위에서 아래(TD)다. 노드는 `["N3 일정 후보 생성"]`, 연결은 `-- L4: 후보 부족 -->`, 시작은 `([시작])`, 출구는 `((확정))`로 쓴다.
- 도구는 "필요한 능력"(예: 웹 검색)을 먼저 쓰고, "추천 도구"(예: Tavily)와 "대안"을 옆에 둔다. 도구 이름을 넣으면서도 특정 구현에 묶이지 않게 한다.

### 섹션별 담지 않을 것

| 섹션 | 담지 않을 것 |
|---|---|
| 의도 | 하는 일 다시 쓰기, "효율을 위해" 같은 일반론 |
| 하는 일 | 이유(의도에 쓴다), 도구 이름(도구 섹션에 쓴다), 다음 단계가 할 일 |
| 받는 것 / 내놓는 것 | 용어 사전에 없는 새 이름, 담기는 내용 설명(용어 사전에 쓴다) |
| 완료 기준 | "잘", "적절히", "충분히"처럼 판별할 수 없는 말 |
| 조건 | "필요할 때", "적절하면"처럼 판별할 수 없는 말, 같은 출발의 다른 연결과 겹치는 조건 |
| 고정과 재량 | 언어나 프레임워크 같은 구현 기술 선택. 원래 재량이므로 쓰지 않는다 |
| 주의점 | 모든 단계에 해당하는 일반론. 에이전트의 공통 주의점에 한 번만 쓴다 |
| 예시 | 실제 개인정보, 꾸며 낸 수치를 사실처럼 쓴 것 |
| 검증 시나리오 | 코드 단위 테스트. 입력과 기대 결과만 쓴다 |
| 설계 결정 | 거절된 제안, 사소한 문구 변경 |

### 넣지 않는 것

- 변수 이름, 함수 이름, 구현 파일 경로, 프롬프트 원문
- 네트워크 재시도 같은 구현 세부
- 캔버스 좌표, 색, 크기(design.json에만 저장)
- 거절된 제안
- 다른 문서 내용을 다시 쓰는 것. 단계 문서에 에이전트 역할을 다시 쓰지 않고, 연결 문서에 단계가 하는 일을 다시 쓰지 않는다.

### 단계 문서

기능 하나를 만드는 사람이 "정확히 무엇을, 무엇을 가지고, 언제까지 하는가"를 알게 한다.

| 섹션 | 필수 | 담을 것 |
|---|---|---|
| 머리 | 필수 | 유형 태그, 소속 에이전트 링크, 한 줄 요약 |
| 의도 | 필수 | 이 단계가 왜 있는가. 없으면 무엇이 깨지는가 |
| 하는 일 | 필수 | 처리 순서를 번호 목록으로. 고르는 기준이 있으면 여기에 쓴다. 너무 많아지면 단계를 쪼갤지 검토한다 |
| 받는 것 / 내놓는 것 | 필수 | 표: 구분, 항목. 항목은 용어 사전 링크 |
| 도구 | 선택 | 표: 필요한 능력, 용도, 추천 도구 |
| 완료 기준 | 필수 | 다음으로 넘어가도 되는 조건. 체크리스트 |
| 다음 연결 | 필수 | 표: 연결, 조건 요약. 이 파일만 열어도 어디로 가는지 알 수 있게 |
| 고정과 재량 | 선택 | 에이전트 문서와 같은 뜻으로, 이 단계에 한정해서 |
| 예시 | 선택 | `받음: … → 내놓음: …` 한 건. 판단 단계의 재현성을 높인다 |
| 주의점 | 선택 | 구현할 때 놓치기 쉬운 점 |
| 실패 시 | 선택 | 실패가 분기를 만들 때만 쓴다 |

### 연결 문서

분기 하나를 만드는 사람이 "어디서 어디로, 어떤 조건에, 무엇을 들고 가는가"를 알게 한다. 에이전트 안의 연결(`A1-L1`)과 에이전트 사이 연결(`L1`)이 같은 틀을 쓴다. 에이전트 사이 연결은 출발 칸에 `A1 출구「완료」`처럼 적는다.

| 섹션 | 필수 | 담을 것 |
|---|---|---|
| 머리 | 필수 | H1 `번호 · 출발 → 도착`과 표: 출발, 도착, 종류(항상 / 조건) |
| 조건 | 조건 연결만 | 쉬운 말로 쓴 규칙, 판단 주체(정해진 규칙 / AI 판단 / 사람), 같은 출발의 다른 연결. 되돌아가는 연결이면 탈출 조건 |
| 의도 | 조건 연결만 | 왜 이 분기가 필요한가 |
| 넘기는 것 | 필수 | 용어 사전 링크 목록 |

- 항상 연결 문서는 머리와 넘기는 것만 있다. 그래도 번호와 파일이 늘 1:1이 되도록 파일은 만든다.

## 9. 저장, 내보내기, 가져오기

- **자동 저장**: 노드와 연결의 이동·추가·삭제, 사이드바 입력값, 프로젝트 이름, 적용한 제안 카드를 즉시 SQLite에 저장한다. 연속 입력은 잠깐 모아서 한 번에 저장한다. 저장 버튼은 없다.
- **원본은 하나**: 편집기의 데이터(SQLite)가 유일한 원본이다. md 문서는 내보낼 때마다 새로 생성하므로, md를 손으로 고친 내용은 다음 내보내기 때 사라진다. 수정은 편집기에서 한다.
- **수정 경로**: 웹과 AI 모두 로컬 서버를 거쳐서만 그래프를 고친다. 서버는 버전을 확인해 충돌을 막고, 변경을 화면에 바로 반영한다.
- **내보내기**: "내보내기" 버튼을 눌렀을 때만 한다.
  1. 내보내기 전 검사를 한다(7절).
  2. 한국어 다듬기: 설치된 clonamic-korean의 규칙 파일을 읽어 모든 문장 칸을 다듬는다. 결과는 제안 카드 하나(변경 N건, 바뀐 곳 비교)로 나오고, 적용하면 SQLite에 반영된다. 사실, 번호, 용어 사전의 이름은 바꾸지 않는다.
  3. 스크립트가 템플릿에 데이터를 채워 문서를 만든다. 같은 데이터면 언제나 같은 문서가 나온다.
- **저장 경로**: 프로젝트마다 처음 내보낼 때 내보내기 창의 경로 입력칸에서 정한다. 추천 경로 `~/Documents/clonamic-agents/<프로젝트명>`이 미리 채워져 있고 고칠 수 있다. 브라우저는 폴더 선택 창으로 경로 문자열을 넘겨주지 못하므로 입력칸을 쓴다.
  - 서버가 폴더가 있는지, 쓸 수 있는지 확인한다. 이 도구가 만들지 않은 파일이 폴더에 있으면 "이 파일은 건드리지 않음"이라고 알린다.
  - 정한 경로는 SQLite에 문자열로 저장하고, 바꾸지 않으면 다음에도 그 경로에 저장한다. 내보내기는 AI 대기 상태와 상관없이 웹 안에서 끝난다.
- **다시 내보내기**: 폴더를 통째로 다시 쓰되, 도구가 만든 파일만 교체하거나 지운다. 사용자가 같은 폴더에 둔 다른 파일은 건드리지 않는다.
  - 도구가 만든 파일 목록은 이전 `design.json`에서 읽는다. 그 파일은 고쳐졌거나 다른 곳에서 왔을 수 있으므로, 폴더 밖을 가리키는 항목(`..`, 절대 경로)은 버린다.
  - 저장 경로는 사용자가 정하므로 홈 아래 어느 폴더든 쓸 수 있다. 막는 곳은 홈 폴더 자체, 그 위의 폴더, 최상위 폴더, 편집기 데이터 폴더다. 이 도구가 만들지 않은 같은 이름의 파일이 있으면 덮어쓰지 않고 멈춘다.
- **가져오기**: 내보낸 폴더의 `design.json`으로 다른 PC나 다른 곳에서 프로젝트를 그대로 가져와 추가할 수 있다.

## 10. 동작 구조

### 수명주기: 화면 = 수명

| 시점 | 동작 |
|---|---|
| 시작 | 스크립트 하나가 준비를 확인하고, 편집기 서버가 떠 있으면 다시 쓰고, 없으면 빈 포트로 띄운 뒤 브라우저를 연다. AI는 대기에 들어간다 |
| 작업 중 | 편집할 때마다 자동 저장된다. 채팅 메시지가 오면 AI가 깨어나 답한다 |
| 종료 | 브라우저 탭을 모두 닫으면 서버가 마지막 저장을 마치고 스스로 꺼진다. AI의 대기도 풀리고, AI가 짧게 마무리 보고를 한다 |
| 비정상 종료 | 터미널을 중단하거나 PC가 꺼져도 데이터는 이미 저장되어 있다. 다음 실행 때 이어간다 |

### 서버와 저장 위치

- 서버는 Python 3.12 표준 라이브러리(http.server, sqlite3)만 쓴다. 따로 설치할 의존성이 없다.
- 포트는 23232부터 확인하고, 쓰이고 있으면 1씩 올려 빈 포트를 찾는다. 이미 떠 있는 서버가 이 편집기인지 확인해서 다시 쓴다.
- 서버는 `127.0.0.1`에서만 열어 외부 접속을 막는다.
- 데이터(DB, 설정, 프로젝트별 저장 경로)는 `~/.clonamic/create-agent/`에 둔다. 어느 호스트에서 열어도 같은 프로젝트 목록이 보인다.
- 웹페이지(HTML, CSS, JS)는 미리 만들어 플러그인 설치 폴더에 두고 그곳에서 바로 서비스한다. 복사하지 않으므로, 플러그인을 업데이트하면 페이지도 함께 바뀐다.

### 실제 설치 환경 기준

모든 경로, 설치 확인, 저장 위치는 이 플러그인을 설치해서 쓰는 사람의 PC를 기준으로 한다. 제작 저장소를 기준으로 하지 않는다.

1. `~`는 실행하는 사람의 홈 폴더로 해석한다. 고정 경로를 쓰지 않으며, macOS, Linux, Windows가 같은 코드로 동작한다.
2. 웹페이지와 스크립트는 스크립트 자기 위치를 기준으로 찾는다. 플러그인 설치 위치를 미리 가정하지 않는다.
3. clonamic-korean은 사용자 PC에 설치된 위치에서 찾는다. 없으면 그 호스트의 방식으로 설치한다.
4. `~/.clonamic/create-agent/`는 처음 실행할 때 만들고 한 줄로 알린다. Python이 3.12보다 낮으면 설치 방법을 안내한다(`uv python install 3.12` 또는 OS 패키지 관리자).
5. `tests/`와 제작용 메모는 배포물에 넣지 않는다.
6. 서버는 사용자 PC의 `127.0.0.1`에서만 연다.
7. 검증은 임시 홈 폴더에 실제로 설치한 상태에서 한다. 사용자의 실제 `~/.claude`, `~/.clonamic`은 건드리지 않는다.

### clonamic-korean 설치

| 호스트 | 확인 | 없을 때 |
|---|---|---|
| Claude Code | Claude 매니페스트의 `"dependencies": ["clonamic-korean"]` | 이 플러그인을 설치할 때 함께 자동 설치된다 |
| Codex | 찾기 스크립트 | `codex plugin marketplace add clonamic/plugin` 다음 `codex plugin add clonamic-korean@clonamic`을 자동 실행하고 한 줄로 알린다 |
| Grok Build | 찾기 스크립트 | `grok plugin install https://github.com/clonamic/plugin#clonamic-korean --trust` 다음 `grok plugin enable clonamic-korean`을 자동 실행하고 한 줄로 알린다 |
| Cursor | 찾기 스크립트(`~/.cursor/plugins/local/clonamic-korean/`) | CLI에 설치 명령이 없어, clonamic-task-log와 같은 방식으로 저장소를 내려받아 `~/.cursor/plugins/local/`에 복사한다 |

- 찾기 스크립트는 네 호스트의 설치 경로를 차례로 확인하고, 처음 찾은 `SKILL.md`와 `references/`를 쓴다.
- 설치하지 못하면 다듬기만 건너뛰고, 내보낸 README에 "다듬기 미적용"이라고 표시한다. 내보내기는 막지 않는다.

### 설치

```text
/plugin marketplace add clonamic/plugin
/plugin install clonamic-create-agent@clonamic
```

- Claude Code는 clonamic-korean을 함께 설치한다. Codex는 `codex plugin marketplace add clonamic/plugin` 다음 `codex plugin add clonamic-create-agent@clonamic`, Grok Build는 `grok plugin install https://github.com/clonamic/plugin#clonamic-create-agent --trust`로 설치한다.

### 제거

- 플러그인을 제거한 뒤 `~/.clonamic/create-agent/` 폴더를 지우면 남는 것이 없다. 내보낸 문서는 사용자가 정한 폴더에 그대로 남는다.

| 결정 | 이유 | 버린 대안 |

| 편집기만 원본, md는 매번 생성 | 원본이 하나여야 재현성과 쉬운 수정이 지켜진다 | 손편집 감지 후 덮어쓸지 묻기 |

## 13. 구현 중 확인한 것

| 항목 | 결과 | 근거 |
|---|---|---|
| Claude 매니페스트의 `dependencies` | 통과 | `claude plugin validate` 통과. 임시 홈 폴더에 설치하면 clonamic-korean이 함께 설치된다(`+ 1 dependency`) |
| Codex와 Grok의 clonamic-korean 설치 | 셸 명령으로 동작 | 임시 홈 폴더에서 `codex plugin add`, `grok plugin install --trust`가 묻는 창 없이 설치를 마쳤다. 네 호스트의 설치 위치 모두에서 찾기 스크립트가 clonamic-korean을 찾았다 |
| Codex 명령 시간 제한 | 150초 이상 | `codex exec`에서 150초 걸리는 명령이 끊기지 않고 끝났다(149891ms). 대기 시간을 110초로 올렸다 |
| Cursor 명령 시간 제한 | 미검증 | `cursor-agent`가 로그인을 요구해 실행하지 못했다. 대기 시간은 55초로 둔다 |
| Codex 실제 세션 | 통과 | `codex exec`로 스킬을 실행했다. 웹 메시지를 8초 안에 받아 추천 답이 붙은 인터뷰 질문을 `say`로 올렸고, 탭을 닫자 `closed`를 받았다. 사용자의 전역 하네스 규칙 때문에 편집기를 열기 전에 작업명세서와 개발명세서 승인을 먼저 요구했다 |
| Grok 실제 세션 | 통과 | `grok -p`로 스킬을 실행했다. 편집기를 열고 웹 메시지를 받아 인터뷰 질문을 올렸다. 이후 계정의 무료 사용 한도에 걸려 더 진행하지 못했다 |
