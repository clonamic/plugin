# 검토 기준과 제안 규칙

설계를 객관적으로 평가한다. 불필요한 과정을 줄이는 방향으로 제안하고, 억지 개선은 하지 않는다.

## 평가 기준 (위에 있을수록 먼저 본다)

| 순위 | 기준 | 보는 것 |
|---|---|---|
| 1 | 구조 정합 | `check` 결과. 왜 문제인지와 고치는 방법을 설명한다 |
| 2 | 의도 부합 | 설계가 "원하는 것"과 "성공 기준"을 달성하는가. 검증 시나리오가 성공 기준을 모두 확인하는가 |
| 3 | 불필요한 과정 | 합쳐도 되는 단계, 판단 없이 전달만 하는 단계, 같은 일을 하는 두 단계, 역할이 겹치는 에이전트 |
| 4 | 분기 품질 | 조건을 실제로 판별할 수 있는가. 규칙으로 될 일을 AI 판단으로 맡기지 않았는가. 같은 출발의 조건이 겹치거나 빠지지 않았는가. 실패 경로가 빠지지 않았는가 |
| 5 | 위험과 제약 | 결제, 발송, 삭제처럼 되돌리기 어려운 동작 앞에 사람 확인이 있는가. 제약을 어기는 흐름이 있는가 |
| 6 | 문서 명확성 | 다른 사람이 문서만 보고 구현할 수 있는가. 입력과 출력이 구체적인가. 과정의 순서와 단위가 실제 구현 흐름을 보여 주는가. 도구의 종류와 위치가 분명한가. 판단 단계의 "고정과 재량"이 비어 있지 않은가. 뜻이 같은데 이름이 다른 데이터가 있는가 |

장황하거나 불필요한 내용도 6번에서 본다(검사 스크립트는 길이를 보지 않는다).

## 제안 규칙

- **근거 필수**: 제안마다 걸리는 기준, 대상 번호, 고치지 않으면 무엇이 깨지는지를 쓴다. 근거를 댈 수 없으면 제안하지 않는다.
- **억지 개선 금지**: 문제가 없으면 "문제 없음"이라고만 답한다. 취향 차이와 문장 다듬기는 제안하지 않는다(문장은 한국어 다듬기 단계가 맡는다).
- 중요한 것부터 낸다. 사소한 것 여러 개는 카드 하나로 묶는다.
- 사용자의 의도와 이미 내린 설계 결정(`decisions`)을 뒤집는 제안은, 그 결정의 이유가 틀렸다는 근거가 있을 때만 한다.

## 카드 형식

```json
{"title": "무엇을 바꾸는지 한 줄", "criterion": "분기 품질", "reason": "고치지 않으면 무엇이 깨지는지",
 "targets": ["A1-N3", "A1-L5"], "changes": ["A1-L5 조건을 '후보 1개 이하'로 바꾼다"], "effect": "바뀐 뒤 좋아지는 점",
 "rejected": "검토했지만 버린 다른 방법(있으면)"}
```

`targets`에는 번호(A1, L2, A1-N3, A1-L5)만 쓴다. 리더가 `changes`를 문서에 그대로 반영할 수 있을 만큼 구체적으로 쓴다.
