# 칸 작성 기준

설계 문서의 목표는 하나다. **구현하는 사람이나 AI가 이 문서만 보고 바로 만들 수 있어야 한다.** 묻지 않고는 만들 수 없는 곳이 남으면 설계가 끝나지 않은 것이다.

문서의 구조(섹션 이름, 순서, 표의 칸, 번호와 링크)는 스크립트가 만든다. 여기서는 칸마다 무엇을 얼마나 구체적으로 쓰는지 정한다. 글자 수 제한은 없다. 같은 사실은 한 곳에만 쓰고, 꾸밈말과 일반론은 쓰지 않는다. 대신 구현에 필요한 규칙, 수치, 필드, 예외 처리는 줄이지 않는다.

- 구현 이름(파일, 모듈, 클래스, 함수, 주소)은 **과정의 이름**과 **도구의 위치·접속**에만 쓴다. 나머지 칸은 쉬운 말로 쓴다.
- 판별할 수 없는 말("잘", "적절히", "필요하면", "충분히")은 쓰지 않는다. 숫자, 데이터 필드, 비교로 쓴다.
- 정하지 못한 값은 지어내지 않는다. 추천 값과 이유를 `미결 사항`에 남기고 사용자에게 묻는다.

## 프로젝트

| 칸 | 쓸 것 | 쓰지 않을 것 |
|---|---|---|
| 요약 | 무엇을 받아 무엇을 내놓는지 한 줄 | 기술 이름 |
| 요구사항 | 사용자가 원하는 결과를 사용자 말에 가깝게 | 단계 나열 |
| 배경 | 왜 필요한가(있을 때만) | 일반론 |
| 성공 기준 | 완성 여부를 판별할 수 있는 기준. 숫자나 관찰할 수 있는 결과 | "잘 동작한다" |
| input / output | 파이프라인 전체가 받는 데이터와 내놓는 데이터. 이름은 데이터 사전과 같게 | 중간 데이터 |
| 범위 밖 | 하지 않기로 한 일 | — |
| 제약 | 응답 시간, 비용 한도, 개인정보, 언어, 동시 사용자처럼 숫자로 지킬 조건 | 구현 기술 선택 |
| 도구 목록 | 종류, 이름, 용도, 위치·접속(서버 이름, 파일 경로, 주소, 인증 방식), 대안. 실제로 쓰는 것만 | 쓰지 않는 도구 |
| 사람 확인 지점 | 사람이 판단하는 단계 번호, 사람이 하는 일, 그동안 흐름(기다림, 기본값으로 진행) | — |
| 검증 시나리오 | 정상 하나 이상과 실패·예외마다 하나. input(실제 값), 경로(번호), 기대 결과, 확인하는 성공 기준 | 코드 단위 테스트 |
| 설계 결정 | 결정, 이유, 버린 대안. AI가 추정해서 정한 값도 여기에 근거와 함께 | 사소한 문구 변경 |
| 미결 사항 | 아직 정하지 못한 것과 추천 값 | 이미 정한 것 |

## 에이전트

에이전트의 input과 output은 연결이 전달하는 데이터로 자동 계산된다. 따로 쓰지 않는다.

| 칸 | 쓸 것 | 쓰지 않을 것 |
|---|---|---|
| 이름 | 짧은 기능명(예: 여행 계획) | 문장 |
| 역할 | 이 에이전트가 맡는 역할 하나 | 단계 나열 |
| 필요한 이유 | 다른 에이전트와 합치지 않고 나눈 이유 | 역할 다시 쓰기 |
| 범위 밖 | 다른 에이전트와 헷갈릴 수 있지만 맡지 않는 일 | — |
| 지켜야 할 것 | 구현 방식이 달라도 꼭 지킬 것 | — |
| 구현자가 정할 것 | 구현하는 쪽이 정해도 되는 것 | 언어·프레임워크(원래 구현자 몫) |
| 정상·예외 흐름 | 내부 흐름도로 드러나지 않는 순서나 예외(있을 때만) | 흐름도 다시 쓰기 |
| 공통 제약 | 모든 단계에 걸리는 제약을 한 번만 | 단계 하나에만 해당하는 것 |

에이전트 사이 분기는 연결의 조건이 맡는다. 한 에이전트에서 나가는 연결이 둘 이상이면 모두 조건 연결이다.

## 단계

| 칸 | 쓸 것 | 쓰지 않을 것 |
|---|---|---|
| 이름 | 짧은 기능명(예: 질문 생성) | 문장, 번호 |
| 유형 | 판단(AI가 판단), 처리(정해진 규칙), 외부 연동(도구·서비스 호출), 사람 확인 | — |
| 요약 | 이 단계가 하는 일 한 줄 | 이름 되풀이("~을 한다") |
| 필요한 이유 | 이 단계가 없으면 무엇이 깨지는지 | 하는 일 다시 쓰기 |
| input / output | 받는 데이터와 내놓는 데이터의 이름(데이터 사전에 구조가 있어야 한다) | 새 이름, 구조 설명 |
| 과정 | 이 단계 안의 처리 순서를 한 행씩: 단위, 이름, 하는 일, 행의 input → output, 도구. 하는 일은 처리 절차를 한 줄에 하나씩 번호를 붙여 쓴다. 고르는 기준, 계산식, 거르고 정렬하는 조건, 호출할 때 넘기는 값, 빈 결과와 예외를 처리하는 방법, 시간 제한과 다시 시도 횟수 같은 수치를 넣는다. 행이 읽고 쓰는 필드는 `여행 조건.지역 → 지역 정보.장소 목록`처럼 적는다. 행이 일곱 개를 넘으면 단계를 쪼갤지 본다 | 이유(필요한 이유에 쓴다), 다음 단계가 할 일, 동사 하나로 끝나는 하는 일("데이터를 처리한다") |
| 판단 기준 | (판단 단계 필수) AI가 지켜야 할 기준. 한 줄에 하나, 판별할 수 있게 | "좋은 결과를 낸다" |
| AI 지시 | (판단 단계 필수) AI에게 줄 역할, 받는 input, 지킬 것, 내야 할 output 형식(JSON이면 필드와 예), 좋은 답과 나쁜 답의 예 하나씩. 그대로 프롬프트로 옮길 수 있을 만큼 쓴다 | 모델 이름(도구 목록에 쓴다) |
| 도구 | 도구 목록에서 고른다. 과정의 한 행에서만 쓰면 그 행의 도구로 | 목록에 없는 도구 |
| 완료 기준 | 다음으로 넘어가도 되는 조건. 판별할 수 있게 | "이름 완료" |
| 예시 | 실제 값으로 정상 한 건(`input: … → output: …`)과 실패·예외 한 건(`input: … → 처리: …`) | 실제 개인정보, 꾸민 수치를 사실처럼 |
| 실패 처리 | (판단, 외부 연동, 사람 확인 필수) 실패 종류마다 다시 시도(몇 번), 대체 값, 멈춤 중 무엇을 하는지. 사람 확인은 응답이 없을 때 | "실패 없음" |
| 지켜야 할 것 / 구현자가 정할 것 | 판단 단계라면 특히 채운다 | 구현 기술 선택 |
| 주의점 | 구현할 때 놓치기 쉬운 점 | 모든 단계에 해당하는 일반론 |

## 연결

| 칸 | 쓸 것 | 쓰지 않을 것 |
|---|---|---|
| 종류 | 항상 / 조건. 같은 곳에서 나가는 연결이 둘 이상이면 모두 조건 | — |
| 이름 | 조건 연결이면 조건을 짧게(예: 후보 부족). 항상 연결은 비워 두면 도착 이름이 쓰인다 | 문장 |
| 조건 | 데이터 필드로 판별할 수 있는 규칙(예: 후보 목록이 2개 이상이면) | "필요할 때", 같은 출발의 다른 조건과 겹치는 조건 |
| 판단 방식 | 정해진 규칙 / AI 판단 / 사람. 규칙으로 될 일은 규칙으로 | — |
| 최대 반복 횟수, 한도 초과 시 연결 | 되돌아가는 연결이면 반드시. 한도 초과 시 연결은 같은 곳에서 나가는 다른 연결 | — |
| 필요한 이유 | 이 분기가 왜 필요한지(조건 연결) | 단계가 하는 일 다시 쓰기 |
| 전달 데이터 | 데이터 사전의 이름 | 새 이름 |

## 데이터 사전

- 설계에 나오는 데이터는 모두 올린다. 처음 생기는 곳과 쓰이는 곳은 스크립트가 채운다.
- 데이터마다 필드를 적는다: 필드 이름, 형식(문자열, 숫자, 정수, 참/거짓, 날짜, 날짜와 시각, 목록, 객체, 파일, 기타), 필수 여부, 설명(단위, 허용 값, 길이), 예.
- 목록이나 객체는 안에 무엇이 들어 있는지 설명에 쓴다(예: "장소 이름, 분류, 영업시간"). 안의 필드도 구현에 필요하면 필드 행으로 따로 적고, 이름은 `장소 목록[].영업시간`처럼 계층으로 쓴다.
- 같은 것을 다른 이름으로 부르지 않는다(예: 여행 조건 / 여행 요구사항).

## 구현 준비 점검표

설계를 넘기기 전에 단계마다 확인한다. 하나라도 "아니오"면 채운다. 1, 2, 3(모델 도구), 5(사람 확인 지점), 7, 9(경로 번호)는 `check`도 잡는다.

1. input과 output의 데이터마다 데이터 사전에 필드와 형식이 있는가?
2. 과정의 행마다 하는 일과 행의 input → output이 있는가? 행을 이어 붙이면 단계의 input에서 output까지 이어지는가?
3. 판단 단계에 판단 기준, AI 지시(output 형식 포함), 예시, 실패 처리가 있는가?
4. 외부 연동 단계의 도구에 위치·접속(주소, 인증 방식)이 있고, 실패 처리가 다시 시도 횟수와 대체 값을 말하는가?
5. 사람 확인 단계에 사람이 보는 것, 고를 수 있는 것, 응답이 없을 때가 있는가?
6. 조건 연결의 조건이 데이터 필드로 판별되는가? 같은 출발의 조건이 겹치거나 빠진 경우가 없는가?
7. 되돌아가는 연결마다 최대 반복 횟수와 한도 초과 시 연결이 있는가?
8. 완료 기준이 판별할 수 있는 말인가?
9. 검증 시나리오가 성공 기준을 모두 확인하고, 실패 처리마다 한 번은 지나가는가?
