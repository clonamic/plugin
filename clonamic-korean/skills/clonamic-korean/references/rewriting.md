# 고쳐 쓰기 처방

[ai-tells](ai-tells.md)에서 감지된 문장을 실제로 고칠 때 쓴다. 예문은 한다체와 합쇼체를 섞어 적었으나, 실제 결과의 문체 높낮이는 언제나 원문을 따른다.

## 지킬 것

1. **뜻은 그대로.** 사실, 주장, 수치, 이름, 인용, 원인과 결과는 바꾸지 않는다. 문장이 모호해도 짐작으로 채우지 않는다.
2. **말투는 그대로.** 보고서는 보고서로, 블로그는 블로그로 둔다. 격식도 임의로 높이지 않는다(`-했-`을 `-하였-`으로 바꾸지 않는다).
3. **어색한 곳만.** 문단을 통째로 새로 쓰지 않는다. 한 문장 안에서도 어색한 구절만 손댄다.
4. **군더더기는 덜되 호흡은 살린다.** 처방표의 단어는 기계적 치환표가 아니다. 정착된 개념어(명사)까지 억지 순우리말로 바꾸거나 문장을 단문으로만 토막 내지 않는다.
5. **자연스러운 실무 문장.** 문학적으로 꾸미지 않는다. 생각을 명확히 정리하는 동료가 쓴 글처럼 막힘없이 읽히는 호흡이 목표다.
6. **자연스러운 구어는 살린다.** `~거든요`, `~인데요`, `~한 겁니다` 같은 구어 종결과 생생한 입말은 사람이 쓴 흔적이다. 이를 딱딱한 한자어 명사구로 바꾸지 않는다.

## 고치는 순서

상투구 → 근거 없는 틀 → 번역투 구문 → 형식 명사 → 유보 → 접속 → 수식 → 영어 끼워 넣기 → 형식과 장식 → 규범([norms](norms.md)) → 리듬.

앞쪽은 불필요한 군더더기를 덜어 내는 단계이고, 뒤쪽은 남은 문장의 연결과 호흡을 다듬는 단계다. 리듬을 먼저 손대면 앞단계 수정을 거치며 호흡이 다시 흐트러진다.

## 번역투 구문

자연스러운 한국어 문장은 **핵심 개념어(명사)는 정확한 용어로 두고, 서술어(동사·형용사)와 조사·연결어미를 한국어 호흡에 맞게 잇는 문장**이다. 아래 네 가지 연결 원리를 기본으로 삼는다.

- **명사구 덩어리를 동사절로 푼다:** “사용자 인증 실패 시의 예외 처리 방안” → “사용자 인증이 실패했을 때 예외를 처리하는 방법”
- **선후·원인·조건은 연결어미로 잇는다:** 무조건 마침표로 끊어 단문만 나열하지 않고 `~해 / ~해서(선후·원인)`, `~하므로 / ~기 때문에(근거)`, `~하려면(조건)`, `~하되(단서)`로 문장 안의 논리 흐름을 살린다.
- **번역투 관형격(`~의`, `~에 대한`, `~를 위한`)을 부사격·목적격으로 바꾼다:** “성능에 대한 개선을 위한 캐시 도입” → “성능을 높이려고 캐시를 도입”
- **무생물 주어 피동문을 능동문으로 바꾼다:** “검증이 서버에 의해 수행된다” → “서버가 검증한다” 또는 “서버에서 검증한다”

| 어색한 표현 | 자연스러운 수정 예 |
|---|---|
| 장애 원인에 대해 분석했다 | 장애 원인을 분석했다 |
| 성능 개선에 있어서 가장 큰 걸림돌은 | 성능을 개선할 때 가장 큰 걸림돌은 |
| 보안과 관련하여 점검했다 | 보안을 점검했다 |
| 로그 데이터에 기반하여 판단했다 | 로그를 보고 판단했다 |
| 높은 확장성을 가지고 있다 | 확장하기 쉽다 |
| 검토되어진 안 | 검토한 안 / 검토된 안 |
| 문서에 쓰여진 절차 | 문서에 쓰인 절차 |
| 운영팀에 의해 배포되었다 | 운영팀이 배포했다 |
| 테스트를 자동화시켰다 | 테스트를 자동화했다 |
| 배포를 더 안전하게 만들었다 | 배포가 더 안전해졌다 |
| 고객사로부터 요청을 받았다 | 고객사에게서 요청을 받았다 / 고객사가 요청했다 |
| 신규 가입자의 경우 | 신규 가입자는 |
| 서울에 위치한 사무실 | 서울에 있는 사무실 |
| 왜 실패했는가를 정리했다 | 왜 실패했는지 정리했다 |
| 여러 문제들이 겹쳤다 | 여러 문제가 겹쳤다 |
| 비용 절감을 위해 캐시를 붙였다 | 비용을 줄이려고 캐시를 붙였다 |
| 점검이 이루어졌다 | 점검했다 |
| 처리 속도 향상 | 처리 속도가 빨라졌다 (원문이 사실로 말할 때) |
| 캐싱을 통해 응답 시간을 단축할 수 있었다 | 캐시를 적용해 응답 시간을 줄였다 |
| 단순한 로그 수집을 넘어 실시간 알림까지 제공한다 | 로그를 수집할 뿐 아니라 실시간 알림도 보낸다 |

`에 의해`를 고칠 때 행위자가 원문에 없으면 억지로 주어를 만들지 않는다. `가지고 있다`가 실제 소유를 뜻하면 그대로 둔다. `할 수 있다`를 단정형으로 바꾸는 것은 원문이 이미 일어난 사실로 말할 때만이며, 가능성을 뜻하면 `할 여지가 있다`처럼 유보를 유지한다.

관형절이 길게 겹치면 핵심 명사를 먼저 말하고 설명을 뒤 문장으로 나눈다.

- “지난달 결제 오류를 일으킨 외부 모듈을 공급한 업체와 계약했던 담당자를 만났다.” → “담당자를 만났다. 지난달 결제 오류를 일으킨 외부 모듈의 공급 업체와 계약했던 사람이다.”

## 대칭 대구

쉼표 하나만 지우고 끝내지 말고 문장 구조를 실제로 정돈한다. 한쪽은 절로 풀어 쓰고 한쪽은 간결하게 맺거나, 두 문장으로 나누어 인과가 드러나게 잇는다.

- “속도는 무기이고, 품질은 방패다.” → “빨리 내놓는 게 무기였다. 품질은 그 뒤를 받쳤다.”
- “문제는 도구가 아니라 습관이며, 해법은 규칙이 아니라 문화다.” → “도구보다 습관이 문제였다. 규칙만 늘려서는 바뀌지 않았다.”
- “자동화는 시간을 아껴 주지만, 판단은 대신해 주지 않는다.” → “자동화로 시간은 아꼈지만, 무엇을 배포할지는 여전히 사람이 정한다.”

글에서 제 역할을 하는 대구 하나는 남긴다. 뒤쪽이 막연한 의미 부여면(“결국 태도의 문제다”) 앞쪽을 덜어 내고 원문에 있는 구체적인 내용을 직접 말한다. 구체적인 내용이 원문에 없으면 대구를 평서문으로 자연스럽게 풀기만 한다.

## 분열문과 결산 공식

- “이번 개편의 핵심은 검색 속도다.” → “이번 개편은 검색 속도에 집중했다.”
- “문제는 로그가 너무 늦게 쌓인다는 점이다.” → “로그가 너무 늦게 쌓였다.”
- “비용은 결국 사용자에게 넘어간다. … 결국 신뢰를 잃는다.” → 둘 중 하나의 `결국`만 남기거나 둘 다 뺀다.
- “수동 배포를 없애야 하는 이유다.” → “그래서 수동 배포를 없애야 한다.”

결말을 다듬으면서 `~하는 이유다`, `~해야 한다`를 새로 만들지 않는다.

## 상투구

| 감지된 표현 | 처리 방법 |
|---|---|
| 결론적으로, 요약하면, 정리하자면 | 뺀다. 마지막 문단이 이미 결론이다 |
| ~라고 할 수 있다 | 원문이 단정했으면 `~이다`, 관찰이면 `~로 보인다`. 유보를 단정으로 올리지 않는다 |
| 매우 중요하다 | 왜 중요한지 구체적인 영향으로 바꾼다. “이 값이 틀리면 정산이 멈춘다” |
| 시사하는 바가 크다, 주목할 만하다, ~라는 점에서 의의가 있다 | 빼거나 실제로 달라진 결과를 적는다 |
| 혁신적인, 획기적인 | 대부분 뺀다. 필요하면 “처음 시도한”, “전과 다른”처럼 사실로 적는다 |
| 새 지평을 열다, 시대가 열렸다 | 빼고 실제로 바뀐 내용을 적는다 |
| 앞서 말씀드린 것처럼, 이 글에서는 ~을 살펴보겠습니다 | 뺀다 |
| 다양한 기능을 지원합니다 | `다양한`을 빼고 실제로 지원하는 구체적인 기능을 적는다 |

## 근거 없는 틀

- 원문에 없는 “흔히”, “일반적으로”, “업계에서는”, “전문가들은”을 문장 연결용으로 넣지 않는다. 원문에 있으면 두고, 출처가 필요해 보이면 결과 끝에 묻는다.
- 처음 보는 개념어가 정식 용어처럼 나오면(“이른바 배포 피로 편향”) 실제 통용되는 용어인지 확인한다. 확인할 수 없으면 뜻하는 바를 평범한 문장으로 푼다(“배포가 잦아지자 사람들이 검토를 건너뛰었다”). 원문의 다른 곳에 그 내용이 없으면 표시만 한다.
- “사용 경험이 매끄러웠다”처럼 추상적인 평가가 원문의 실제 기능을 가리고 있으면 구체적인 기능을 앞으로 꺼낸다(“검색어를 지우지 않고 필터만 바꿀 수 있었다”). 원문에 그런 기능이 없으면 지어내지 않는다.

## 비유

업무 글의 기본은 직설이다. 원문의 비유를 남길지 정할 때는 비유를 빼고 직설로 한 번 써 본다. 직설 문장이 더 길고 흐릿해질 때만 비유를 남긴다. 독자가 처음 접하는 추상적인 개념을 설명하는 비유는 도움이 되지만, 이미 아는 사실을 꾸미는 비유는 대개 군더더기가 된다. 오해할 여지가 있는 비유는 짧아도 뺀다.

자주 문제가 되는 것은 과장된 은유 명사와 은유 동사다.

- 여정, 전쟁터, 생태계, 엔진, 나침반, 퍼즐 조각, 씨앗, 날개 같은 은유가 업무 문장에 나오면 실제로 일어난 일로 바꾼다. “검색 기능은 서비스의 엔진이다” → “사용자 요청의 절반이 검색이다”(원문에 그 사실이 있을 때).
- “녹여 냈다”, “담아냈다”, “엮어 냈다”, “불어넣었다”, “꽃피웠다”는 “넣었다”, “바꿨다”, “줄였다”, “보여 줬다”처럼 실제 동작 동사로 쓴다.
- 다듬는 과정에서 원문에 없던 비유를 새로 만들지 않는다.

## 유보

서법을 지키는 것이 먼저다. 불필요하게 겹친 완곡 표현을 한 겹으로 정리하는 일과, 추측을 단정적인 사실처럼 바꾸는 일은 전혀 다르다.

- 겹친 완곡 표현만 한 겹으로 줄인다. “늘어날 수 있을 것으로 예상된다” → “늘어날 것으로 보인다”는 자연스럽지만, “늘어날 것으로 보인다” → “늘어난다”로 바꾸면 안 된다.
- 같은 추측 종결이 이어지면 확신의 정도는 유지한 채 어미 형태만 나눈다. “~로 보인다 / ~일 가능성이 있다 / ~인 듯하다 / 아직 단정하기는 어렵다”.
- 단정으로 바꿔도 되는 경우는 같은 사실을 원문의 다른 곳에서 이미 단정해 말했을 때뿐이다.

## 접속

- 문두 접속사가 셋 이상 이어지면 앞뒤 문장의 논리를 실제로 잇지 않는 것부터 덜어 낸다.
- 인과가 이미 분명한 자리의 “따라서”, “그러므로”는 빼고, 꼭 필요하면 “그래서”나 연결어미(`~해`, `~하므로`)로 잇는다.
- “하지만”과 “그러나”가 문장마다 번갈아 나오면 하나를 “그런데”나 연결어미(`~지만`, `~는데`)로 바꾸거나 뺀다.

## 형식 명사

- “배포 주기가 짧아졌다는 것이다” → “배포 주기가 짧아졌다”
- “~할 필요가 있다”는 문맥에 따라 “~해야 한다”, “~하자”, 또는 주체를 밝힌 동사로 바꾼다. 의무의 강도는 그대로 둔다.
- “개선이 필요하다”는 문맥이 뒷받침되면 누가 무엇을 고쳐야 하는지로 구체화하고, 맥락이 없으면 그대로 둔다.

## 수식

- “전략적 판단” → “전략 판단”, “근본적인 원인” → “핵심 원인” 또는 “원인”
- “구조적 한계” → “구조의 한계” 또는 “구조가 한계다”
- 같은 뜻을 겹친 수식(“핵심적이고 중요한”)은 하나만 남긴다. 중복 표현은 [norms](norms.md)의 표를 따른다.

## 영어 단어

불필요한 비즈니스 외래어만 한국어로 풀고, 업계에서 그대로 쓰는 기술 용어는 유지한다. 전문 용어를 억지로 직역하지 않는다(`prompt`를 `지시문`으로, `token`을 `토막`으로 바꾸지 않는다).

| 외래어 | 자연스러운 한국어 |
|---|---|
| 레버리지하다 | 활용하다, 바탕으로 삼다 |
| 심리스한 | 매끄러운, 끊김 없는 |
| 로버스트한 | 튼튼한, 안정적인 |
| 인사이트 | 알게 된 점, 시사점, 통찰 |
| 임팩트 | 영향, 효과, 변화 |
| 어필하다 | 보여 주다, 강조하다 |
| 딥다이브 | 깊이 살펴보기, 상세 분석 |
| 얼라인하다 | 기준을 맞추다, 방향을 맞추다 |
| As-Is / To-Be | 기존 상태 / 변경 후(개선안) |

## 서식

- 불릿을 산문으로: “- 설치가 쉽다 / - 문서가 많다 / - 커뮤니티가 크다” → “설치가 쉽고 문서도 풍부하다. 막히는 부분이 있어도 커뮤니티가 커서 답을 찾기 쉽다.” 실제 목록(기술 스택, 일정, 절차)은 목록 그대로 둔다.
- 칼럼과 에세이는 소제목 대신 문단 흐름으로 자연스럽게 이을 수 있다. 보고서, 기술 문서, 포트폴리오의 제목 구조는 그대로 둔다.
- 굵은 글씨는 제목과 꼭 강조해야 할 한두 곳에만 쓰고, 줄표는 문서에 한두 번만 쓴다.

## 리듬

- 문장 길이가 비슷해 단조로우면 문단마다 간결한 문장과 연결어미로 자연스럽게 이은 문장을 섞는다. 원문에 없는 내용은 보태지 않는다.
- 같은 종결 어미가 네댓 번 이어지면 “~했다 / ~였다 / ~한 셈이다” 또는 연결어미로 문장 호흡을 섞는다. 시제와 서법은 바꾸지 않는다.
- 소리 내어 읽었을 때 숨이 차는 긴 문장은 나누고, 단문만 나열되어 뚝뚝 끊기는 곳은 연결어미로 자연스럽게 잇는다.
