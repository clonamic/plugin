# 현장 사례: AI 티를 지우다 새 티를 만든 경우

다른 호스트의 에이전트가 이 스킬 없이 개발자 포트폴리오(마크다운과 정적 HTML)의 AI 티를 지우려 한 실제 사례다. 진단은 절반쯤 맞았고, 고친 문장은 새 AI 티였다. 아래 규칙과 예문은 그 사례에서 나왔다. 예문은 회귀 시험에도 쓴다. **원문**을 **나쁜 수정**처럼 고치면 실패고, **좋은 수정**처럼 고쳐야 한다.

## 맞았던 진단

- 필자가 직접 한 일을 남 이야기처럼 쓴 문장(“~로 적혀 있습니다”)
- 초안 프롬프트나 체크리스트가 본문에 새어 나온 줄
- 같은 종결(“~했습니다. ~없습니다.”)의 반복과, 이유나 선택의 맥락이 빠진 요약
- 변명처럼 끝나는 마무리(“아직 데모에 없는 것 …”)
- 사용자가 준 가이드(“근거 없는 기여도 백분율은 피합니다”)를 어긴 표현(“기여 5:5”)

## 틀렸던 수정에서 나온 규칙

1. 사용자 지침이 일반 조언보다 앞선다. 한 규칙을 고치면서 같은 규칙을 다른 모양으로 어기지 않는다.
2. 근거가 받쳐 주지 않는 절대 표현과 과장(“100%”, “원천 차단”, “치명적”, “심각하게”, “격상”, “극대화”, “무결성”)을 쓰지 않는다.
3. 원문에 없는 숫자, 백분율, 배수, 금액, 비교를 넣지 않는다. 다른 문서에서 가져오거나 원문 숫자로 계산한 값도 넣지 않는다. 사용자가 요청하면 계산 근거와 함께 넣는다.
4. 입말에 가까운 쉬운 문장은 결함이 아니다. 동사를 “~로 인한 ~의 ~ 현상이 발생” 같은 명사 사슬로 바꾸지 않는다.
5. 자연스러운 한국어가 있으면 외래어 업무 용어(임팩트, 어필, Deep Dive, To-Be)를 쓰지 않는다. 실제 고유명사와 개발자가 영어로 말하는 기술 용어(vLLM, RAG, CER)는 그대로 둔다.
6. 서식은 훑어 읽기에 도움이 될 때만 쓴다. 구절마다 굵은 글씨, 👉, 모든 것에 번호 제목, 두 항목짜리 표, “즉시 수정을 진행하겠습니다!” 같은 들뜬 마무리는 쓰지 않는다.
7. 필자의 구조와 사실을 지키고 요청받은 범위만 고친다. 문서 전체 어조를 바꾸거나 절과 지표를 보태거나 CSS를 고치지 않는다. 필요하면 제안으로만 적는다.
8. 포트폴리오와 이력서는 1인칭 실무 문장이다. 광고 문구도, 제3자가 쓴 보고서도 아니다.
9. 빠진 이유나 맥락은 지어 넣지 않는다. 원문 다른 곳에 있으면 옮겨 오고, 없으면 필자에게 묻는다.
10. 이 스킬이 설치되지 않은 호스트에서도 같은 기준이 필요하다. 스킬 폴더는 SKILL.md와 references만으로 동작해야 한다.

## 회귀 예문

### 1. 남 이야기하듯 쓴 자기 일

**원문**
```text
PaddleOCR-VL 단독은 페이지 CER 75.9%라 배포 불가로 적혀 있습니다.
```

**나쁜 수정**
```text
PaddleOCR-VL 단독 사용 시 CER 75.9%라는 치명적 한계로 배포가 불가능한 것으로 나타났습니다.
```

**좋은 수정**
```text
PaddleOCR-VL만 썼을 때 페이지 CER이 75.9%여서 배포하지 않기로 했습니다.
```

규칙: 필자가 측정하고 결정한 일이면 필자를 주어로 쓴다. “치명적” 같은 평가를 보태지 않는다.

### 2. 본문에 새어 나온 프롬프트

**원문**
```text
OCR 정확도를 측정했습니다.
- 없는 기록: 측정 도구, 반복 횟수, 오류율
```

**나쁜 수정**
```text
OCR 정확도를 전용 측정 도구로 3회 반복 측정해 오류율 2%를 확인했습니다.
```

**좋은 수정**
```text
OCR 정확도를 측정했습니다.
```

규칙: 체크리스트 줄은 지우고, 빠진 정보는 결과 끝에 “측정 도구, 반복 횟수, 오류율을 알려 주시면 넣겠습니다”처럼 묻는다. 빈칸을 숫자로 채우지 않는다.

### 3. 사용자 가이드를 다른 모양으로 어기기

사용자 가이드: “근거 없는 기여도 백분율은 피합니다.”

**원문**
```text
기여 5:5 — OCR 파이프라인 설계, 평가 스크립트 작성
```

**나쁜 수정**
```text
전담 (100%) — OCR 파이프라인 설계, 평가 스크립트 작성
```

**좋은 수정**
```text
OCR 파이프라인 설계와 평가 스크립트 작성을 맡았습니다.
```

규칙: 비율을 다른 비율로 바꾸지 않는다. 맡은 일을 문장으로 적는다.

### 4. 근거 없는 절대 표현

**원문**
```text
사용자 입력을 이스케이프해 XSS를 막았습니다.
```

**나쁜 수정**
```text
사용자 입력 이스케이프로 XSS 공격 벡터를 100% 원천 차단했습니다.
```

**좋은 수정**
```text
사용자 입력을 이스케이프해 XSS를 막았습니다.
```

규칙: 고칠 곳이 없으면 고치지 않는다. 보안처럼 단정이 위험한 주제에서는 특히 그렇다.

### 5. 계산해서 만든 숫자

**원문**
```text
응답 시간이 3.2초에서 0.83초로 줄었습니다.
```

**나쁜 수정**
```text
응답 시간을 74% 단축(3.85배)했습니다.
```

**좋은 수정**
```text
응답 시간을 3.2초에서 0.83초로 줄였습니다.
```

규칙: 원문 숫자를 그대로 쓴다. 비율이나 배수는 사용자가 요청할 때만, 계산 근거와 함께 넣는다.

### 6. 쉬운 입말을 명사 사슬로 바꾸기

**원문**
```text
형식 제약보다 문장 생성이 이겼습니다. 응답이 늦으면 다음 강의에 못 넘어갑니다.
```

**나쁜 수정**
```text
자유 생성 시 모델의 토큰 생성 자율도로 인해 레이아웃 CSS 제약이 붕괴되는 현상이 발생했습니다. 극심한 응답 지연으로 인한 학습 흐름 단절이 발생합니다.
```

**좋은 수정**
```text
형식 제약보다 문장 생성이 이겼습니다. 응답이 늦으면 다음 강의로 못 넘어갑니다.
```

규칙: 생생한 입말은 둔다. 동사를 명사로 바꾸고 “~로 인한”, “현상이 발생”을 붙이면 번역투가 된다.

### 7. 외래어 업무 용어와 기술 용어

**원문**
```text
엔지니어링 임팩트를 어필하려고 Deep Dive 섹션을 만들었습니다. 모델은 vLLM으로 서빙하고 RAG로 검색을 붙였습니다.
```

**나쁜 수정**
```text
엔지니어링 임팩트를 극대화해 어필하려고 Deep Dive 섹션을 만들었습니다. 모델은 가상 대형 언어 모델 엔진으로 서빙하고 검색 증강 생성으로 검색을 붙였습니다.
```

**좋은 수정**
```text
엔지니어링에서 바꾼 점을 보여 주려고 깊이 다룬 절을 따로 만들었습니다. 모델은 vLLM으로 서빙하고 RAG로 검색을 붙였습니다.
```

규칙: 업무 외래어는 한국어로 바꾸고, 개발자가 실제로 영어로 말하는 기술 용어는 그대로 둔다.

### 8. 서식 과잉

**원문**
```text
응답 속도를 개선했습니다. 배포 과정을 자동화했습니다.
```

**나쁜 수정**
```text
👉 **응답 속도** **대폭 개선**
👉 **배포 자동화** 완료
```

**좋은 수정**
```text
응답 속도를 개선하고 배포 과정을 자동화했습니다.
```

규칙: 굵은 글씨와 이모지는 정보를 늘리지 않는다. “대폭”처럼 원문에 없는 정도 표현도 넣지 않는다.

### 9. 범위 넘기

사용자 요청: “소개 문단만 다듬어 줘.”

**원문**
```text
## 소개

저는 OCR 파이프라인을 만드는 개발자입니다. 저는 문서 인식 정확도를 높이는 일을 합니다.

## 프로젝트

사내 문서 검색을 만들었습니다.
```

**나쁜 수정**
```text
## 소개

OCR 파이프라인 전문 개발자로서 문서 인식 정확도 극대화에 기여하고 있습니다.

## 프로젝트

사내 문서 검색을 만들었습니다.

## 성과 지표

검색 처리량 2배 향상.
```

**좋은 수정**
```text
## 소개

OCR 파이프라인을 만드는 개발자입니다. 문서 인식 정확도를 높이는 일을 합니다.

## 프로젝트

사내 문서 검색을 만들었습니다.
```

규칙: 요청받은 소개 문단만 고친다. 새 절과 지표를 만들지 않는다. 필요해 보이면 결과 끝에 제안으로 적는다.

### 10. 같은 종결의 반복과 빠진 이유

**원문**
```text
Redis를 도입했습니다. 캐시를 적용했습니다. 응답이 빨라졌습니다.
```

**나쁜 수정**
```text
트래픽 급증에 대응하기 위해 Redis를 도입하여 캐시를 적용함으로써 응답 속도를 극대화했습니다.
```

**좋은 수정**
```text
Redis로 캐시를 적용했고, 그 뒤로 응답이 빨라졌습니다.
```

규칙: 종결을 섞어 리듬을 살린다. “트래픽 급증” 같은 이유는 원문에 없으면 쓰지 않고, 결과 끝에 “Redis를 고른 이유를 알려 주시면 넣겠습니다”라고 묻는다.

### 11. 변명처럼 끝나는 마무리

**원문**
```text
아직 데모에 없는 것: 다중 사용자, 결제.
```

**나쁜 수정**
```text
향후 다중 사용자와 결제 기능까지 완벽하게 지원할 예정입니다.
```

**좋은 수정**
```text
지금 데모에는 다중 사용자와 결제가 들어 있지 않습니다.
```

규칙: 범위를 담담하게 적는다. 원문에 없는 계획(“지원할 예정”)을 약속하지 않는다. 문서를 이 문장으로 끝내지 않도록 범위나 한계 절이 있으면 그리로 옮긴다.

### 12. 유보를 단정으로

**원문**
```text
이 방식이 기존 방식보다 빠를 수 있습니다.
```

**나쁜 수정**
```text
이 방식이 기존 방식보다 빠릅니다.
```

**좋은 수정**
```text
이 방식이 기존 방식보다 빠를 수 있습니다.
```

규칙: 필자가 유보한 판단은 유보로 둔다.

### 13. 이력서 문장을 공문서나 광고로

**원문**
```text
결제 모듈을 리팩터링해 장애 건수를 줄였습니다.
```

**나쁜 수정**
```text
본 지원자는 결제 모듈 리팩터링을 통해 장애 건수를 획기적으로 감소시킨 바 있음.
```

**좋은 수정**
```text
결제 모듈을 리팩터링해 장애 건수를 줄였습니다.
```

규칙: 이력서와 포트폴리오는 필자가 1인칭으로 쓰는 실무 문장이다. 이미 그렇게 쓴 문장은 둔다.
