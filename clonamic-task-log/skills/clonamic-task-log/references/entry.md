# 작업 기록 항목 작성법

기록은 사용자 혼자 보는 비공개 자료이고, 목적은 포트폴리오다. 따로 "포트폴리오 문장" 절은 없다. 포트폴리오로 쓸 가치는 별도 문장이 아니라 항목 안의 배경(어떤 문제였나), 접근(어떻게 진단하고 왜 그렇게 골랐나), 결과(무엇이 달라졌고 어떻게 확인했나)에 녹여 쓴다.

기록이 답해야 하는 질문은 하나다. 프로젝트를 모르는 사람이 읽어도, 그날 어떤 문제를 어떻게 진단하고 왜 그렇게 풀었으며 무엇이 달라졌는지 알 수 있어야 한다. 커밋이 몇 건이고 파일이 몇 개 바뀌었는지는 답이 아니다.

## 형식

헤딩 이름과 순서는 고정이다. 선택 절은 근거가 없으면 통째로 뺀다. 빈 절, 자리표시자, "없음"만 적힌 절, 값이 `-` 하나뿐인 칸이나 줄을 남기지 않는다. 메타데이터(지문, 해시, 수집 범위, HTML 주석)와 `[측정]` 같은 대괄호 라벨은 기록 어디에도 쓰지 않는다. 길이는 보통 15~35줄이고, 비어 있지 않은 줄이 40줄을 넘으면 게이트가 막는다.

````text
# 2026-09-29 · 영수증 OCR 파이프라인 개선

## 핵심 요약
- 한두 줄 성과 요약

## 한 일
### 목표·성과 단위 — 한 줄 성과
- 배경 — 이전 상태와 그 때문에 생긴 문제나 영향
- 접근 — 진단과 판단: 무엇을 왜 그렇게 했는지, 대안과 견준 이유
- 결과 — 바뀐 점과 검증 근거
- 그 밖에 — 작은 일 하나, 둘, 셋(최대 3개)

## 기술 판단
- **선택** — 이유

## 문제 해결
- 증상 → 원인 … → 해결 … → 확인 …

## 오늘 변화
- 기능 — 변화 (마일스톤 n/m)

## 다음 할 일
- …
````

| 절 | 필수 | 비고 |
|---|---|---|
| 제목 `# YYYY-MM-DD · 대표 성과` | 필수 | 기간이면 `# YYYY-MM-DD~YYYY-MM-DD · 대표 성과` |
| 핵심 요약 | 필수 | |
| 한 일 | 필수 | 목표·성과 단위 항목 최대 3개 |
| 기술 판단 | 선택 | 고른 방식, 대안, 접은 이유가 작업 메모에 있을 때 |
| 문제 해결 | 선택 | 증상, 원인, 해결, 확인이 모두 있을 때 |
| 오늘 변화 | 선택 | 그날 손댄 기능마다 한 줄. 마일스톤이 있으면 `(마일스톤 n/m)`을 붙임 |
| 다음 할 일 | 선택 | 사용자가 말했거나 작업 메모에 있을 때 |

`## 포트폴리오 문장`과 `## 진행 상황`은 쓰지 않는다. 게이트가 막는다.

## 항목은 목표·성과 단위로 묶는다

- 한 일 항목은 하루에 **최대 3개**다. 커밋, 파일, 하위 변경 단위로 쪼개지 않고 목표나 성과 단위로 묶는다. 한 플러그인을 만들며 생긴 구조 정리, 검사 추가, 문서 보강은 항목 셋이 아니라 하나다. 항목이 4개 이상이면 게이트가 막는다(`too-many-items`).
- 3개에 못 들어간 작은 일은 마지막에 `- 그 밖에 — …` 한 줄(최대 3개)로 묶는다. 이 줄은 항목 수에 들어가지 않는다.
- 기능이 하나뿐인 날은 항목 하나만 쓴다.

## 항목 필드: 배경 · 접근 · 결과

항목마다 세 줄을 한 번씩, 이 순서로 쓴다. 각 줄은 2문장 이하, 220자 이하(160자 안팎을 목표)다.

| 필드 | 담을 것 | 담지 않을 것 |
|---|---|---|
| `- 배경 —` | 이전 상태와 그 때문에 생긴 문제나 영향. 읽는 사람이 왜 이 일이 필요했는지 알게 쓴다 | 목표 다시 쓰기("~해야 했습니다") |
| `- 접근 —` | 진단과 판단. 무엇을 왜 그렇게 했는지, 다른 방법과 견준 이유. 여러 환경에서 원인을 가려냈다면 그 과정 | 단계 나열, 설정값·임계값 |
| `- 결과 —` | 바뀐 동작과 검증 근거(시험 통과, 실제 실행, 전후 비교). 측정값은 입력에 있을 때만 `(측정)`과 함께 | 검증하지 않았는데 "확인했습니다" |

- 게이트는 배경 줄에 기존·이전·없었·비어·하나로·통째로·수동·매번·모든·의존·섞여 같은 이전 상태 말이 있는지 본다. 이전 상태를 서술하는 과거형(`~했고`, `~였고`, `~었습니다`)도 `만`, `뿐`, `그대로`, `채`, `이후` 같은 조건·한계 말과 함께 있으면 통과한다. "~해야 했습니다"로 끝나는 목표 문장은 막는다(`problem-goal-only`).
- 작업 메모의 `검증`이 `없음`이면 그 항목의 결과 줄에 `확인`, `검증`, `통과`를 쓰지 않는다(`unverified-claim`). 검증하지 못한 것은 "검증하지 못했습니다"라고 솔직히 쓰되, 확인했다는 주장으로 쓰지 않는다.

## 작업 메모 서식 (리더 → 작성자)

작성자는 리더가 `notes --check`로 통과시킨 메모만 받는다. 항목은 기록의 항목과 같은 단위(목표·성과)다. 항목마다 이 서식이다.

```text
### <목표·성과 단위 제목>
- 이전 상태: <이전에 무엇이 있었는지. 목표가 아니라 이전 상태나 제약>
- 영향: <그 이전 상태가 무엇을 일으켰는지>
- 사실: <구체적 사실 1 — 기법·규칙·구성요소·동작>
- 사실: <구체적 사실 2>
- 판단: <고른 것> — <이유, 대안 대비>
- 검증: <시험 통과, 실제 실행, 전후 비교 같은 구체적 근거> 또는 없음
```

검사 규칙은 항목 수 3개 이하, 항목마다 이전 상태 1개·영향 1개·사실 2개 이상·판단 1개 이상·검증 1개, 사실은 15자 이상이고 서로 비슷하지 않을 것, 이전 상태는 목표만 다시 쓰지 않을 것, 판단은 `<선택> — <이유>`, 검증은 10자 이상의 구체적 근거이거나 정확히 `없음`, 파일 이름·경로·식별자·비밀이 없을 것이다. 통과한 메모는 `notes --check --save --entry -`로 날짜별 저장(`log-part/notes/<날짜>.md`)하고, 같은 날짜를 다시 실행할 때 근거 지문이 같으면 저장본을 그대로 쓴다. 메모 → 기록 대응은 이전 상태·영향 → 배경, 사실·판단 → 접근, 사실·검증 → 결과, 판단 → 기술 판단이다.

## 바깥 사람이 읽어도 알 수 있게

- 프로젝트 밖의 사람이 읽는다고 생각하고 쓴다. 이 프로젝트에서만 통하는 이름(내부 기능 별명, 검사 단계 이름, 도구 안의 용어)은 하고 있는 일을 풀어 쓴다.
- 프로필에 `내부 용어:`를 쉼표로 적으면 그 말이 기록에 나올 때 게이트가 막는다. 이 플러그인 자신의 기록이라면 `게이트`, `작업 메모`, `지문`, `리더`, `작성자` 같은 말을 적어 두면 좋다(기본값은 없다).
- 글자 수 상한, 줄 수 상한 같은 내부 매개변수 값을 문장에 쓰지 않는다. 그 값은 기록의 주제가 아니다.

## 절별 쓰는 법

### 제목
`# 2026-09-29 · 영수증 OCR 파이프라인 개선`. 날짜 뒤에 그날 가장 중요한 성과를 명사구 한 줄로 쓴다. 그 줄이 Notion 날짜 페이지의 첫 줄에도 쓰인다. 20자 안팎, 파일 이름이나 식별자 없이.

### 핵심 요약
- 그날 성과 1~3줄. 무엇을 했고 무엇이 달라졌는지. "~에서 ~을 ~해 ~했습니다." 꼴의 행위자 문장. 커밋·파일·줄 수로 시작하지 않는다. 한 줄이 두 문장을 넘지 않는다.

### 한 일
- 목표·성과 단위 항목 최대 3개, 제목은 `### 목표·성과 — 한 줄 성과`. 성과는 "~을 ~로 묶음", "~를 ~로 바꿈"처럼 결과가 보이게 쓴다.
- 파일 이름, 경로, 함수·변수 이름, 해시, 티켓 번호는 쓰지 않는다. 기능 말로 쓴다.

### 기술 판단
- `- **선택** — 이유` 한 줄씩. 선택은 굵게, 사이는 줄표(—)다. `선택 : 이유`처럼 공백 뒤 콜론을 쓰면 게이트가 막는다. 대안이 있었으면 대안과 접은 이유를 함께 쓴다. 1~3줄.

### 문제 해결
- `- 증상 → 원인 … → 해결 … → 확인 …` 한 줄. 네 칸이 모두 채워지지 않으면 이 절에 넣지 않고 한 일에 쓴다. 0~2줄.

### 오늘 변화
- 그날 손댄 기능마다 `- <기능> — <변화>` 한 줄. 입력의 `touched_features`에 있는 기능만 쓴다. 마일스톤이 있는 기능은 줄 끝에 입력의 값 그대로 `(마일스톤 n/m)`을 붙이고, 없는 기능은 붙이지 않는다. 퍼센트는 쓰지 않는다. 변화 칸을 `-`로 비우지 않는다. 프로젝트 전체 진행은 Notion 진행 현황 페이지가 맡는다.

### 다음 할 일
- 사용자가 말했거나 작업 메모에 있는 것. 동사로 끝나는 짧은 항목 1~3줄. 같은 동작은 한 줄로 합친다("세 기능의 테스트 작성하기"). 지어내지 않는다.

## 문체 (clonamic-korean 상시 규칙)

- 1인칭 실무 합쇼체. "~했습니다". 내가 한 일을 남 이야기처럼 쓰지 않는 행위자 문장.
- 추측과 얼버무림을 쓰지 않는다. 근거가 없으면 그 문장을 쓰지 않는다.
- 과장과 절대 표현(완벽히, 극대화, 원천 차단)을 쓰지 않는다. "임팩트", "어필", "인사이트" 같은 외래어 업무 용어도 쓰지 않는다.
- 명사 사슬("~로 인한 ~의 ~ 현상")로 딱딱하게 만들지 않는다. 동사는 동사로 둔다.
- 숫자는 입력에서 복사한다. 더하거나 빼거나 계산하지 않는다. 수치에는 `(측정)`만 붙이고 다른 대괄호 라벨은 쓰지 않는다.

## 이렇게 쓰지 않는다

| 나쁜 문장 | 문제 | 고친 문장 |
|---|---|---|
| 기능 커밋 1건을 반영했습니다. 파일 32개 변경, 1,006줄 추가. | git 통계. 무엇이 달라졌는지 없다 | 영수증 인식 전처리와 인식 단계를 하나의 흐름으로 묶었습니다. |
| 인식 구조를 정비하려는 것으로 보입니다 [판단] | 얼버무림과 라벨 | 인식 구조를 단계별로 나눠 각 단계를 따로 시험할 수 있게 했습니다. |
| 게이트가 대괄호 꼬리표를 막게 했습니다. | 안에서만 통하는 말(게이트, 꼬리표) | 기록에 `[판단]` 같은 대괄호 표시가 들어가면 저장 전에 걸러내도록 했습니다. |
| 한 줄은 220자 이하, 40줄을 넘으면 막습니다. | 내부 매개변수 값을 문장에 씀 | 기록이 길어지면 저장 전에 걸러내 한눈에 읽히는 길이를 지키게 했습니다. |
| 배경: 로그인 만료를 고쳐야 했습니다. | 목표를 다시 씀. 이전 상태와 영향이 없다 | 만료를 1시간으로 설정했는데 30분 만에 로그아웃되어 로그인이 자주 끊겼습니다. |
| 결과: 시험을 돌려 확인했습니다. (실제로는 돌리지 않음) | 검증하지 않은 일을 검증했다고 씀 | 설정한 시간만큼 유지되도록 고쳤습니다. 실제 환경에서는 아직 재 보지 못했습니다. |
| 진행률 70%, 남은 일 - | 근거 없는 퍼센트, 빈 칸 | 결제 모듈 — 요청 처리 흐름 구성 (마일스톤 1/2) |

## 예시 1 — 좋은 기록 (여러 환경 진단, 대안 판단, 검증)

````text
# 2026-10-05 · 여러 개발 도구에서 작업 기록 저장 실패 해결

## 핵심 요약
- 개발 도구마다 기록 폴더 쓰기를 막는 방식이 달라 저장이 실패하던 문제를 도구별로 나눠 진단하고, 저장 경로를 하나로 모아 해결했습니다.
- 사진 업로드 검증은 업로드 시점으로 앞당겼습니다.

## 한 일
### 기록 저장 — 도구마다 다르던 쓰기 실패를 하나의 저장 경로로 정리
- 배경 — 세 개발 도구 중 두 곳에서 기록 폴더 쓰기가 막혀 저장이 실패했고, 실패 메시지가 도구마다 달라 사용자가 원인을 찾지 못했습니다.
- 접근 — 도구별 차단 방식을 따로 재현해 원인이 폴더 보호와 실행 권한 두 가지임을 가려냈습니다. 도구 설정을 고치는 대신 전용 저장 명령 하나로만 쓰게 하고, 막히면 도구별 조치를 안내하게 했습니다.
- 결과 — 두 도구에서 같은 저장 명령으로 기록이 저장되고, 막힌 경우에는 그 도구의 허용 방법이 한 줄로 나옵니다. 세 도구에서 저장을 직접 실행해 확인했습니다.

### 사진 업로드 — 잘못된 사진을 업로드 직후 거절
- 배경 — 너무 크거나 형식이 다른 사진이 인식 단계에서야 실패해, 사용자가 한참 기다린 뒤 이유 없이 거절당했습니다.
- 접근 — 크기와 형식 검사를 업로드 시점으로 옮겼습니다. 인식 단계에서 거르면 서버 시간을 쓰고 사용자도 늦게 알지만, 업로드 시점에 거르면 바로 사진을 바꿀 수 있어 앞쪽을 택했습니다.
- 결과 — 잘못된 사진은 업로드 직후 이유와 함께 거절되고 정상 사진은 기존처럼 처리됩니다. 두 경우를 시험으로 고정했고 시험이 모두 통과했습니다.
- 그 밖에 — 업로드 문서 보강

## 기술 판단
````
