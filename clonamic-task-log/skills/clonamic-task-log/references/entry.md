# 작업 기록 항목 작성법

`prepare`가 준 익명화 JSON만 보고 쓴다. 기록은 사용자 혼자 보는 비공개 자료이고, 목적은 포트폴리오다. 모든 항목을 그대로 포트폴리오에 옮겨도 되는 문장으로 쓴다. 따로 "포트폴리오 모드"는 없다.

## 형식

절 순서는 고정이다. 근거가 없는 절은 통째로 뺀다. 빈 절, 자리표시자, "없음"만 적힌 절을 남기지 않는다. `한눈에 보기`와 `근거·신뢰도`는 항상 쓴다.

```text
# 2026-10-05 작업 기록

## 한눈에 보기
- 날짜 — 2026-10-05 (기간이 하루를 넘으면 2026-10-02~2026-10-05)
- 파트 — 백엔드 개발
- 핵심 성과 — 오늘 가장 중요한 성과 한 줄 [측정 또는 판단]
- (선택) 함께 한 일 — 둘째 성과 한 줄

## 목표·맥락
- 작업 목적 — 왜 이 일이 필요했는지 [판단]
- 범위 — 이번 기록에 넣은 일과 뺀 일

## 포트폴리오 하이라이트
문제 → 결정 → 실행 → 결과가 이어지는 서너 문장. 면접에서 그대로 말할 수 있게 쓴다.

## 작업 상세

### 결제 모듈
- 목표 — 이루려던 상태
- 시작 상태 — 작업 전 상태나 제약 (근거가 있을 때만)
- 실행 — 내가 한 일과 방법
- 변경점 — 이전과 달라진 구조·동작 (근거가 있을 때만)
- 선택 이유 — 왜 이 방식을 골랐는지 (커밋이나 코드에 근거가 있을 때만) [판단]
- 결과 — 확인된 산출물과 상태 [측정]
- 근거 — 근거 수준 A, 기능 커밋 2건·테스트 추가 [측정]

### 기타 3건
- 수정 2건, 문서 1건 [측정]

## 기술적 의사결정

### 결정 이름
- 선택 — 채택한 방식
- 대안 — 검토한 다른 방식 (근거가 있을 때만)
- 근거 — 품질·운영·보안·확장성 관점의 이유 [판단]
- 영향 — 얻은 것과 남은 비용 (근거가 있을 때만)

## 문제 해결 기록

### 확인된 문제
- 증상 — 관찰한 실패나 제약
- 확인 원인 — 근거로 확인한 원인
- 조치 — 적용한 수정
- 재검증 — 결과 [측정] 또는 [미확인]
- 재발 방지 — 테스트·규칙으로 고정한 것 (근거가 있을 때만)

## 검증·측정 결과
- [측정] 결제 요청 응답 시간 120ms → 80ms (33.3% 단축, 커밋 메시지에 남긴 측정값)
- [미확인] 실행하지 못했거나 근거가 부족한 검증

## 진행 정도
- 결제 모듈 — 55% [판단] 추정 (마일스톤 1/2 · 테스트 있음 · 미완 표시 1건), 지난 기록 대비 +10%p
- 스프린트 2 — 기능 평균 55% [판단] 추정, 기간 경과 55% [측정]

## 기여·영향
- 사용자·팀 영향 — 누구의 어떤 불편이나 위험이 줄었는지 [판단]
- 기술 자산 — 새로 만든 모듈·테스트·문서 [측정]
- 포트폴리오 가치 — 어떤 역량이 드러나는지 [판단]

## 회고·다음 작업
- 잘된 점 — 유지할 접근
- 보완점 — 근거상 남은 한계
- 다음 작업 — 다음 마일스톤이나 검증 가능한 후속 과제

## 근거·신뢰도
- 근거 수준 — A: git 저자 일치 커밋
- 수집 범위 — 커밋 3건 중 2건 반영, 주석만 바꾼 1건 제외 [측정]
- 수집 시점 — 2026-10-05T21:54:51+09:00
- 증거 지문 — sha256:… (prepare 결과의 evidence.fingerprint를 그대로)
```

## 증거 라벨

수치나 해석이 들어간 줄에는 아래 라벨 중 하나를 붙인다. 라벨 없는 수치 줄, 목록에 없는 라벨은 게이트가 막는다.

| 라벨 | 쓰는 곳 |
|---|---|
| `[측정]` | git에서 센 값(커밋·파일·줄 수), 커밋에 남은 전후 측정값, 기간 경과 |
| `[판단]` | 해석, 진행률 추정, 영향 평가 |
| `[전달]` | 사용자가 대화에서 직접 알려 준 사실 |
| `[가정]` | 확인하지 못한 전제를 두고 쓴 문장 |
| `[미확인]` | 실행하지 못했거나 근거가 부족한 검증 |

근거 수준: A = git 저자 일치 커밋(이 도구의 기본), B = 파일·결과 시각만 확인, C = 사용자 제공.

## 내용 규칙

- **절 매핑.** `work_items` 하나가 `작업 상세`의 `###` 항목 하나다. 항목 안의 커밋은 `detailed[rank]`로 찾는다. `others.count`가 있으면 마지막에 `### 기타 n건`을 두고 유형별 건수만 한 줄로 쓴다. 수정(fix) 커밋 가운데 증상과 원인이 커밋 내용에 드러난 것만 `문제 해결 기록`에 쓴다. 커밋이나 코드에 선택의 이유가 드러난 것만 `기술적 의사결정`에 쓴다. `new_things`는 `기여·영향`의 기술 자산 줄로 쓴다.
- **중요도 순.** `work_items`는 이미 중요도 순이다. 그 순서를 지킨다.
- **수치.** `검증·측정 결과`에는 `metrics` 항목만 쓴다. 전후 값이 모두 있는 것만 있고, 변화율은 `change_pct`를 그대로 쓴다. 직접 계산하지 않는다. 수치가 없으면 절을 뺀다. 수치를 지어내거나 "크게 개선" 같은 말로 대신하지 않는다.
- **진행 정도.** `progress`의 `pct`와 `basis`를 그대로 쓰고 `[판단] 추정`을 붙인다. `delta`가 있으면 "지난 기록 대비 +n%p"를 붙인다. `work_unit`이 있으면 한 줄 더 쓴다.
- **테스트 결과.** git에는 테스트를 추가했다는 사실만 남는다. 통과 여부는 사용자가 알려 주거나(`[전달]`) 직접 실행해 확인했을 때(`[측정]`)만 쓰고, 아니면 `[미확인]`이다.
- **다음 작업.** `progress[].next_milestones`가 우선이다. 근거 없는 계획을 만들지 않는다.
- **비공개 정보.** 파일 이름, 경로, 함수·변수 이름, 커밋 해시, 브랜치·티켓 번호, URL, 메일, 호스트, IP, 환경 변수, 키를 쓰지 않는다. 기능 라벨(`feature`, `areas`)로 쓴다. `‹비공개›`는 지워진 자리라는 뜻이다. 그 자리를 짐작해 채우지 말고 문장을 다시 짓는다.
- **코드를 더 볼 때.** 요약만으로 무엇을 했는지 알 수 없으면 바뀐 핵심 소스 파일을 읽어 확인해도 된다. 읽기 경계(SKILL.md 0절)를 지키고, 읽은 내용도 같은 규칙으로 기능 라벨로만 쓴다.

## 문장 규칙

- 1인칭 실무 합쇼체로 쓴다. "~했습니다", "~를 만들었습니다". 주어 "저는"은 대부분 뺀다.
- 성과 중심으로 쓴다. 무엇을, 어느 기능에서, 어떻게, 왜 중요한지.
- 영어 커밋 요약은 자연스러운 한국어로 옮긴다. 업계에서 영어로 부르는 기술 용어(API, CI, OAuth)는 그대로 둔다.
- "획기적", "완벽히", "극대화", "원천 차단" 같은 근거 없는 강조를 쓰지 않는다. 형용사보다 숫자, 숫자가 없으면 사실을 쓴다.
- 이모지, 굵은 글씨 남발, 같은 말 반복을 쓰지 않는다.

## 예시 (한 항목)

```text
### 결제 모듈
- 목표 — 결제 요청을 받아 처리하는 첫 API를 만드는 것이었습니다.
- 실행 — 결제 모듈을 새로 구성하고, 요청 처리 흐름과 테스트를 함께 작성했습니다.
- 변경점 — 결제 요청이 별도 모듈로 분리되어 이후 환불 처리를 같은 구조에 붙일 수 있게 됐습니다 [판단]
- 결과 — 결제 요청 API와 결제 흐름 테스트를 함께 추가했습니다 [측정] 새 코드 파일 2개, 테스트 파일 1개
- 근거 — 근거 수준 A, 기능 커밋 1건과 테스트 커밋 1건 [측정]
```
