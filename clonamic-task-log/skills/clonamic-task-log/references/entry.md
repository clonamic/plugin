# 작업 기록 항목 작성법

기록은 사용자 혼자 보는 비공개 자료이고, 목적은 포트폴리오다. 프로젝트를 모르는 사람이 읽어도 그날 어떤 문제를 어떻게 풀었고 무엇이 달라졌는지 알 수 있어야 한다. 커밋이 몇 건이고 파일이 몇 개 바뀌었는지는 답이 아니다.

세 가지를 지킨다.

- **한 사실은 한 번만 쓴다.** 핵심 요약, 한 일, 완료 정리가 같은 말을 되풀이하지 않는다. 그날 공통인 검증은 핵심 요약에 한 번만 쓴다.
- **자세함은 줄 수로 낸다.** 한 줄에는 사실 하나만 쓴다. 긴 문장에 쉼표로 늘어놓지 말고, 접근 아래 세부 줄로 나눈다.
- **항목 하나에는 문제 하나만 쓴다.** 서로 다른 기능이나 문제를 한 항목으로 묶지 않는다.

## 형식

헤딩 이름과 순서는 고정이다. 선택 절은 근거가 없으면 통째로 뺀다. 빈 절, 자리표시자, `-` 하나뿐인 줄, 메타데이터(지문, 해시, 수집 범위, HTML 주석), `[측정]` 같은 대괄호 라벨을 남기지 않는다. 비어 있지 않은 줄이 70줄을 넘으면 게이트가 막는다.

````text
# 2026-09-29 · 영수증 금액을 사진 한 장으로 인식

## 핵심 요약
- 그날의 대표 성과 1~2줄. 그날 공통 검증은 여기서 한 번만

## 한 일
### <기능> — <한 줄 성과>
- 배경 — 이전 상태 하나와 실제로 겪은 증상
- 접근 — 핵심 결정과 그 이유(버린 대안)
  - 구체적인 변경 하나
  - 구체적인 변경 하나
- 전후 — 바뀌기 전 모습 → 바뀐 뒤 모습 (선택)
- 결과 — 사용자 쪽에서 달라진 점
- 그 밖에 — 작은 일 최대 3개 (선택)

## 완료 정리
### <끝난 기능 또는 마일스톤> — 완료
- 만든 것 — 이제 무엇을 할 수 있게 됐는지
- 거쳐 온 길 — 지난 기록에서 그 기능이 지나온 단계
- 남은 한계 — 아는 한계나 다음 단계

## 다음 할 일
- …
````

| 절 | 필수 | 비고 |
|---|---|---|
| 제목 `# YYYY-MM-DD · 대표 성과` | 필수 | 기간이면 `# YYYY-MM-DD~YYYY-MM-DD · 대표 성과`. `· ` 뒤는 성과 하나, 30자 이하. 동사로 끝내고 `개선`, `정리`, `강화`, `고도화`, `보완`, `정비`로 끝내지 않는다 |
| 핵심 요약 | 필수 | 1~3줄 |
| 한 일 | 필수 | 항목 최대 3개, 항목 하나에 문제 하나 |
| 완료 정리 | 조건부 | 끝난 것이 있으면 반드시 쓰고, 없으면 쓰지 않는다 |
| 다음 할 일 | 선택 | 사용자가 말했거나 작업 메모에 있을 때 |

`## 기술 판단`, `## 오늘 변화`, `## 문제 해결`, `## 포트폴리오 문장`, `## 진행 상황`은 쓰지 않는다. 게이트가 막는다. 판단은 접근 줄에 쓰고, 기능별 진행은 Notion 진행 현황 페이지가 맡는다.

## 한 일 항목

- 항목 제목은 `### <기능> — <한 줄 성과>`다. 왼쪽 `<기능>`은 프로필의 기능 이름이나 `prepare`가 묶어 준 작업 항목 이름을 그대로 쓴다(`item-feature`). 그래야 진행 현황, 완료 정리와 이름이 맞는다.
- 항목은 하루 최대 3개다. 같은 문제를 푸는 하위 변경(구조 정리, 검사 추가, 문서 보강)은 한 항목의 세부 줄로 넣는다. 서로 다른 문제는 다른 항목으로 쓰고, 3개에 못 들어간 작은 일은 마지막 항목의 `- 그 밖에 —` 한 줄(최대 3개)로 보낸다.

| 필드 | 담을 것 | 담지 않을 것 |
|---|---|---|
| `- 배경 —` | 이전 상태 하나와 그 때문에 실제로 생긴 증상. 가능하면 실제 예를 든다 | 목표 다시 쓰기("~해야 했습니다"), 문제 여러 개 나열 |
| `- 접근 —` | 핵심 결정 하나와 그 이유. 버린 대안이 있으면 함께 쓴다 | 규칙·검사 항목 나열, 설정값, 구현 내부 설명 |
| `  - ` (세부 줄) | 접근 바로 아래 2~4줄. 줄마다 실제로 바꾼 것 하나를 쉬운 말로 쓴다. 120자 이하 | 한 줄에 여러 변경, 파일·함수 이름 |
| `- 전후 —` (선택) | 바뀌기 전에 사용자가 보던 모습과 바뀐 뒤 모습 | 결과 줄과 같은 말 |
| `- 결과 —` | 사용자 쪽에서 달라진 점. 그 항목에만 해당하는 검증이 있으면 짧게 덧붙인다 | 다른 항목과 같은 검증 문장 반복, 검증하지 않은 "확인했습니다" |

- 배경, 접근, 전후, 결과는 한 줄 160자 이하, 두 문장 이하다.
- 배경 줄에는 이전 상태를 말하는 표현이 있어야 한다(기존, 이전, 없었, 비어, 하나로, 통째로, 수동, 매번, 모든, 의존, 섞여, 또는 `만`·`뿐`·`그대로`와 함께 쓴 과거형). "~해야 했습니다"로 끝나는 목표 문장은 막는다(`problem-goal-only`).
- 작업 메모의 `검증`이 `없음`인 항목은 결과 줄에 `확인`, `검증`, `통과`를 쓰지 않는다(`unverified-claim`). 검증하지 못했다면 못했다고 쓴다.

## 완료 정리

끝난 날에는 무엇을 완성했는지를 따로 정리한다. 포트폴리오의 기능별 기여는 이 절에서 먼저 가져간다.

- **언제 쓰나.** 다음 중 하나라도 있으면 반드시 쓴다(`done-missing`). 하나도 없는데 쓰면 막는다(`done-unexpected`).
  - `prepare`의 `completions`에 항목이 있을 때. 지난 기록 뒤로 새로 체크된 마일스톤(`kind: milestone`)과, 마일스톤이 모두 체크된 기능(`kind: feature`)이 들어 있다.
  - 작업 메모에 `- 완료:` 줄이 있을 때. 마일스톤으로 잡히지 않은 작업이 끝난 경우다(예: 한 버전을 내보냄).
- 대상마다 `### <대상> — 완료` 하나를 쓴다. `<대상>`은 `completions`의 `target`이나 메모의 `완료:` 줄 왼쪽을 그대로 쓴다.
- 필드는 `- 만든 것 —`, `- 거쳐 온 길 —`, `- 남은 한계 —` 순서로 한 번씩 쓴다.
  - **만든 것:** 그 기능으로 이제 무엇을 할 수 있는지. 그날 한 일이 아니라 완성된 전체를 쓴다.
  - **거쳐 온 길:** `completions`의 `history`(지난 기록의 날짜와 대표 성과)에서 주요 단계를 날짜와 함께 쓴다. 이력이 비어 있으면 그날 기록에서 완성으로 이어진 단계를 쓴다. 이력에 없는 날짜를 만들지 않는다.
  - **남은 한계:** 작업 메모나 남은 마일스톤에 있는 한계나 다음 단계. 없으면 "알려진 한계는 아직 없습니다"라고 쓴다.

## 작업 메모 서식 (리더 → 작성자)

리더는 이 서식으로 메모를 쓰고 `notes --check --save`로 검사·저장한다. 작성자는 검사를 통과한 메모만 받는다. 메모의 항목이 곧 기록의 항목이다.

```text
### <기능> — <한 줄 성과>
- 이전 상태: <이전에 무엇이 있었는지. 목표가 아니라 이전 상태나 제약>
- 영향: <그 이전 상태 때문에 실제로 생긴 일>
- 사실: <바꾼 것 하나 — 기법·규칙·구성요소·동작>
- 사실: <바꾼 것 하나>
- 전달: <사용자가 git 밖에서 확인해 알려 준 사실> (있을 때만)
- 판단: <고른 것> — <이유, 버린 대안>
- 전후: <바뀌기 전> → <바뀐 뒤> (있을 때만)
- 검증: <시험 통과, 실제 실행, 전후 비교 같은 구체적 근거> 또는 없음
- 완료: <끝난 기능·마일스톤·작업> — <이제 무엇을 할 수 있는지> (끝난 것이 있을 때만)
```

- 검사 규칙은 다음과 같다.
  - 항목은 3개 이하다.
  - 항목마다 이전 상태 1개, 영향 1개, 사실과 전달을 합쳐 2개 이상(자세히 쓰려면 3~4개), 판단 1개 이상, 검증 1개가 있어야 한다.
  - 사실과 전달은 15자 이상이고 서로 비슷하지 않아야 한다.
  - 판단과 완료는 `<왼쪽> — <오른쪽>` 꼴, 전후는 `→`가 든 꼴이다.
  - 검증은 10자 이상의 구체적 근거이거나 정확히 `없음`이다.
  - 파일 이름, 경로, 식별자, 비밀이 없어야 한다.
- 기록에 쓰는 개수 숫자(시험 수, 횟수, 시간)는 메모에 있는 그대로만 쓴다. 메모에 없는 `숫자+개·건·회·번·배·초·분·시간`은 게이트가 막는다(`unsourced-number`).

| 메모 | 기록 |
|---|---|
| 이전 상태 + 영향 | `- 배경 —` |
| 판단 | `- 접근 —` 첫 문장(결정과 이유) |
| 사실·전달 | 접근 아래 세부 줄. 줄마다 하나 |
| 전후 | `- 전후 —` |
| 검증 | `- 결과 —`의 짧은 꼬리. 여러 항목에 공통이면 핵심 요약에 한 번 |
| 완료 | `## 완료 정리` |

## 바깥 사람이 읽어도 알 수 있게

- 이 프로젝트 안에서만 통하는 이름은 하고 있는 일로 풀어 쓴다. 이 플러그인 자신의 용어(게이트, 작업 메모, 리더, 작성자, 에이전트 폴더, 하네스, 프리플라이트)는 기본으로 막는다. 다른 프로젝트에서 이 말이 공개 용어라면 프로필 `공개 용어:`에 적어 풀어 준다. 프로필 `내부 용어:`에 적은 말도 막는다.
- 메모의 필드 이름(이전 상태, 영향, 사실, 판단, 검증, 전달)을 한 줄에 셋 이상 늘어놓으면 막는다(`notes-leak`).
- 한 문장에 쉼표가 셋 이상이면, 즉 넷 이상을 나열하면 막는다(`list-chain`). 중요한 하나만 남기거나 세부 줄로 나눈다.
- `정규식`, `해시`, `익명화`, `하한`, `상한값` 같은 구현 내부 말과 글자 수·줄 수 같은 내부 매개변수 값은 쓰지 않는다(`mechanics`).
- 내부 용어를 피하려고 `정리 담당` 같은 새 역할 명사를 만들지 않는다. 문장을 다시 쓴다.

## 문체 (clonamic-korean 상시 규칙)

- 1인칭 실무 합쇼체로 쓴다. 핵심 요약, 한 일의 모든 줄, 세부 줄, 완료 정리의 모든 줄은 `~다`로 끝나는 문장이다. `~함`, `~음`, 명사로 끝내지 않는다(`noun-ending`). 다음 할 일은 `~하기`로 끝내도 된다.
- 같은 사실을 두 번 쓰지 않는다. 비슷한 문장이 다시 나오면 막는다(`duplicate-line`).
- 추측과 얼버무림("것으로 보입니다", "것 같습니다")을 쓰지 않는다. 근거가 없으면 그 문장을 쓰지 않는다.
- 과장(완벽히, 극대화, 원천 차단)과 외래어 업무 용어(임팩트, 어필, 인사이트)를 쓰지 않는다.
- 명사 사슬("~로 인한 ~의 ~ 현상")로 딱딱하게 만들지 않는다.
- 숫자는 입력에서 복사한다. 측정값에는 `(측정)`만 붙인다.

## 이렇게 쓰지 않는다

| 나쁜 문장 | 문제 | 고친 문장 |
|---|---|---|
| 기능 커밋 1건을 반영했습니다. 파일 32개 변경. | git 통계 | 영수증 인식 전처리와 인식 단계를 하나의 흐름으로 묶었습니다. |
| 기록 전에 이전 상태, 영향, 사실, 판단, 검증을 정리합니다. | 내부 필드 이름 나열 | 기록을 쓰기 전에 그날 바뀐 내용을 먼저 정리해 빠진 것이 있으면 돌려보냅니다. |
| 목표만 쓴 배경, 얼버무림, 커밋 수 나열, 입력에 없는 숫자가 걸러집니다. | 규칙 나열 | 근거 없는 숫자가 들어간 기록은 저장 전에 걸러집니다. (나머지는 세부 줄로) |
| (두 항목 결과에) 시험 124개를 돌렸고 모두 통과했습니다. | 같은 검증 반복 | 핵심 요약에 한 번만 쓴다. |
| 배경 — 규칙 공백, 훅 설치 권유, 임시 파일, 쓰기 실패가 있었습니다. | 배경 하나에 문제 넷 | 문제마다 항목을 나누거나 가장 큰 하나만 남긴다. |
| 작업 기록 자동화 — 날짜별 수집을 갖춤 | 명사형 종결, 다른 절 반복 | (지운다. 진행은 Notion 진행 현황이 맡는다) |
| # 2026-10-06 · 작업 기록 개선 | 막연한 제목 | # 2026-10-06 · 지난 날짜도 그날 바꾼 내용으로 기록 |
| 배경: 로그인 만료를 고쳐야 했습니다. | 목표를 다시 씀 | 만료 시간을 한 시간으로 설정했는데 그 절반쯤에 로그아웃되어 로그인이 자주 끊겼습니다. |
| 결과: 시험을 돌려 확인했습니다. (실제로는 돌리지 않음) | 검증하지 않은 주장 | 설정한 시간만큼 유지되도록 고쳤지만 실제 환경에서는 재 보지 못했습니다. |

## 예시 1 — 완료가 있는 날

````text
# 2026-10-05 · 개발 도구마다 막히던 기록 저장을 해결

## 핵심 요약
- 개발 도구 세 곳 중 두 곳에서 실패하던 기록 저장을 저장 명령 하나로 모아 해결했고, 세 도구에서 직접 실행해 저장되는 것을 확인했습니다.
- 잘못된 사진을 업로드 직후 거절하게 바꿔 사용자가 인식 단계까지 기다리지 않게 했습니다.

## 한 일
### 기록 저장 — 도구마다 다르던 쓰기 실패를 저장 명령 하나로 해결
- 배경 — 세 개발 도구 중 두 곳에서 기록 폴더 쓰기가 막혀 저장이 실패했고, 실패 메시지도 도구마다 달라 원인을 찾을 수 없었습니다.
- 접근 — 도구 설정을 고치는 대신 저장을 명령 하나로만 하게 했습니다. 설정을 고치면 도구가 늘 때마다 다시 맞춰야 하기 때문입니다.

  - 실행 전에 기록 폴더에 실제로 써 보고, 막히면 그 도구의 허용 방법을 한 줄로 알려 주게 했습니다.
- 전후 — 전에는 저장이 이유 없이 실패했지만, 이제는 막힌 이유와 허용 방법이 바로 나옵니다.
- 결과 — 사용자가 도구 설정을 직접 고치지 않아도 어느 도구에서나 기록을 남길 수 있게 됐습니다.
````
