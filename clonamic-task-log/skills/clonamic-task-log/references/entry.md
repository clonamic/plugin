# 작업 기록 항목 작성법

기록은 사용자 혼자 보는 비공개 자료이고, 목적은 포트폴리오다. 각 항목은 그대로 포트폴리오에 옮겨도 되는 문장으로 쓴다. 따로 "포트폴리오 모드"는 없다.

기록이 답해야 하는 질문은 하나다. 그날 무엇을 왜 어떻게 해서 무엇이 달라졌는가. 커밋이 몇 건이고 파일이 몇 개 바뀌었는지는 답이 아니다.

## 형식

헤딩 이름과 순서는 고정이다. 선택 절은 근거가 없으면 통째로 뺀다. 빈 절, 자리표시자, "없음"만 적힌 절을 남기지 않는다. 메타데이터(지문, 해시, 수집 범위, HTML 주석)와 `[측정]` 같은 대괄호 라벨은 기록 어디에도 쓰지 않는다. 길이는 보통 15~35줄이고, 비어 있지 않은 줄이 40줄을 넘으면 게이트가 막는다. 길어지면 자세히 쓰는 항목 수를 줄이고 임계값·매개변수 같은 세부는 기술 판단에 한 줄로 두거나 뺀다.

````text
# 2026-09-29 · 영수증 OCR 파이프라인 개선

## 핵심 요약
- 한두 줄 성과 요약

## 한 일
### 기능 이름 — 한 줄 성과
- 문제 — …
- 한 일 — …
- 결과 — …
- 그 밖에 — 작은 일 하나, 둘, 셋(최대 3개)

## 기술 판단
- **선택** — 이유

## 문제 해결
- 증상 → 원인 … → 해결 … → 확인 …

## 진행 상황
| 기능 | 진행률 | 오늘 변화 | 남은 일 |
|---|---|---|---|

## 다음 할 일
- …

## 포트폴리오 문장
- …
````

| 절 | 필수 | 비고 |
|---|---|---|
| 제목 `# YYYY-MM-DD · 대표 성과` | 필수 | 기간이면 `# YYYY-MM-DD~YYYY-MM-DD · 대표 성과` |
| 핵심 요약 | 필수 | |
| 한 일 | 필수 | |
| 기술 판단 | 선택 | 고른 방식과 이유가 작업 메모에 있을 때 |
| 문제 해결 | 선택 | 증상과 원인이 작업 메모에 있을 때 |
| 진행 상황 | 프로필에 기능이 있고 그날 손댄 기능이 있으면 필수 | 손댄 기능만 |
| 다음 할 일 | 선택 | 사용자가 말했거나 진행 상황의 남은 일에서 나올 때 |
| 포트폴리오 문장 | 필수 | |

## 절별 쓰는 법

### 제목
`# 2026-09-29 · 영수증 OCR 파이프라인 개선`. 날짜 뒤에 그날 가장 중요한 성과를 명사구 한 줄로 쓴다. 그 줄이 Notion 날짜 페이지의 첫 줄에도 쓰인다. 20자 안팎, 파일 이름이나 식별자 없이.

### 핵심 요약
- 넣을 것: 그날 성과 1~3줄. 무엇을 했고 무엇이 달라졌는지.
- 쓰는 법: "~에서 ~을 ~해 ~했습니다." 꼴의 행위자 문장. 커밋·파일·줄 수로 시작하지 않는다.
- 길이: 1~3줄. 한 줄이 두 문장을 넘지 않는다.

### 한 일
- 넣을 것: 중요한 작업 항목 3~5개를 `### 기능 이름 — 한 줄 성과`로 하나씩. 나머지 작은 일은 마지막에 `- 그 밖에 — …` 한 줄로 기능 말로 묶되 항목은 최대 3개(`, ` 또는 `·`로 나눈 개수)다. 더 있으면 가장 중요한 3개만 쓴다. 항목이 하나뿐인 날은 하나만 쓴다.
- 항목 제목: 기능 이름과 성과를 한 줄에. 성과는 "~을 ~로 묶음", "~를 ~로 바꿈"처럼 결과가 보이게 쓴다.
- 각 필드는 2문장 이하, 한 줄 220자 이하다(넘으면 게이트가 막는다). 임계값, 점수 기준, 설정값 같은 세부 수치는 필드에 늘어놓지 않고 기술 판단에 쓰거나 뺀다.
- `- 문제 —`: 왜 필요했는지. 그 전에 무엇이 불편하거나 막혀 있었는지. 1문장.
- `- 한 일 —`: 내가 한 일과 방법, 고른 기술. 1~2문장. 단계를 다 나열하지 않고 핵심만 쓴다.
- `- 결과 —`: 지금 동작이 어떻게 다른지. 측정한 값이 입력에 있을 때만 숫자를 쓰고 바로 뒤에 `(측정)`을 붙인다. 없으면 숫자 없이 달라진 동작을 쓴다.
- 세 줄은 항목마다 한 번씩, 이 순서로 쓴다.
- 파일 이름, 경로, 함수·변수 이름, 해시, 티켓 번호는 쓰지 않는다. 기능 말로 쓴다.

### 기술 판단
- 넣을 것: 기술이나 방식을 고른 이유. 대안이 있었으면 대안과 접은 이유.
- 쓰는 법: `- **선택** — 이유` 한 줄씩. 선택은 굵게, 사이는 줄표(—)다. `선택 : 이유`처럼 공백 뒤 콜론을 쓰면 게이트가 막는다. 이유는 품질·운영·유지보수 중 실제로 작업 메모에 있는 것만. 1~3줄.

### 문제 해결
- 넣을 것: 막혔다가 풀어낸 일. 증상, 원인, 해결, 확인이 모두 있을 때만.
- 쓰는 법: `- 증상 → 원인 … → 해결 … → 확인 …` 한 줄. 네 칸이 모두 채워지지 않으면 이 절에 넣지 않고 `한 일`에 쓴다. 0~2줄.

### 진행 상황
- 넣을 것: 그날 손댄 기능만 한 행씩. 입력의 `touched_features`에 있는 기능만 쓰고, 손대지 않은 기능은 행을 만들지 않는다(`손대지 않음`을 쓰면 게이트가 막는다). 프로젝트 전체 진행 상황은 Notion 진행 현황 페이지가 맡는다. 입력의 진행률을 그대로 옮긴다.
- 쓰는 법: 진행률은 `약 70%`처럼 쓴다(입력에 있는 값만). 오늘 변화와 남은 일은 기능 말로 짧게.

### 다음 할 일
- 넣을 것: 사용자가 말했거나 작업 메모·진행 상황의 남은 일에 있는 것. 지어내지 않는다.
- 쓰는 법: 동사로 끝나는 짧은 항목 1~3줄. 같은 동작은 한 줄로 합친다("세 기능의 테스트 작성하기"). 기능 이름만 바꿔 같은 동작을 반복하면 게이트가 막는다.

### 포트폴리오 문장
- 넣을 것: 이력서나 면접에서 그대로 말할 수 있는 한 문장 1~3개.
- 쓰는 법: "문제를 ~으로 해결해 ~했습니다." 꼴. 결과는 입력에 있는 측정값이나 확인된 동작. 없는 숫자로 꾸미지 않는다.

## 문체 (clonamic-korean 상시 규칙)

- 1인칭 실무 합쇼체. "~했습니다". 주어를 굳이 쓰지 않아도 내가 한 일로 읽히게.
- 행위자 문장. 내가 한 일을 남 이야기처럼 쓰지 않는다.
- 추측과 얼버무림을 쓰지 않는다. 근거가 없으면 그 문장을 쓰지 않는다.
- 과장과 절대 표현(완벽히, 극대화, 원천 차단)을 쓰지 않는다. "임팩트", "어필", "인사이트" 같은 외래어 업무 용어도 쓰지 않는다.
- 명사 사슬("~로 인한 ~의 ~ 현상")로 딱딱하게 만들지 않는다. 동사는 동사로 둔다.
- 숫자는 입력에서 복사한다. 더하거나 빼거나 계산하지 않는다.
- 수치에는 `(측정)`만 붙인다. 다른 대괄호 라벨은 쓰지 않는다.

## 이렇게 쓰지 않는다

| 예전 문장 | 문제 | 고친 문장 |
|---|---|---|
| 기능 커밋 1건을 반영했습니다. 파일 32개 변경, 1,006줄 추가. | git 통계. 무엇이 달라졌는지 없다 | 영수증 인식 전처리와 인식 단계를 하나의 파이프라인으로 묶었습니다. |
| 인식 구조를 정비하려는 것으로 보입니다 [판단] | 얼버무림과 라벨 | 인식 구조를 단계별로 나눠 각 단계를 따로 시험할 수 있게 했습니다. |
| 테스트 커밋이 포함되어 안정성이 향상되었을 것으로 추정됩니다. | 추측, 명사 중심 | 새 파이프라인의 실패 경로를 시험으로 고정했습니다. |
| 영향 큼 [판단] / 근거 수준 A [측정] | 라벨 범벅, 내용 없음 | (쓰지 않는다. 결과 줄에 달라진 동작을 쓴다.) |
| 성능 개선의 임팩트를 극대화했습니다. | 외래어, 과장, 숫자 없음 | 한 장 처리 시간이 4.2초에서 1.8초로 줄었습니다(측정). (입력에 측정값이 있을 때만) |

## 예시 1 — 기능이 많은 날

````text
# 2026-09-29 · 영수증 OCR 파이프라인 개선

## 핵심 요약
- 영수증 OCR에서 전처리와 인식 단계를 하나의 파이프라인으로 묶고, 흐린 사진에서 금액을 못 읽던 문제를 고쳤습니다.
- 업로드 API에는 사진 크기 검증을 더했고, 인식 결과 확인 화면 초안을 만들었습니다.

## 한 일
### 영수증 OCR — 전처리와 인식 단계를 하나의 파이프라인으로 묶음
- 문제 — 사진 보정과 글자 인식이 따로 돌아 결과를 한 번에 확인할 수 없었습니다.
- 한 일 — 기울기 보정, 명암 보정, 인식을 하나의 흐름으로 이어 한 번 호출로 끝나게 했고, 단계마다 중간 결과를 남기게 했습니다.
- 결과 — 사진 한 장을 넣으면 보정부터 인식까지 한 번에 처리되고, 어느 단계에서 실패했는지 바로 알 수 있습니다.

### 업로드 API — 잘못된 사진을 받는 즉시 거절
- 문제 — 너무 크거나 형식이 다른 사진이 올라오면 인식 단계에서 한참 뒤에 실패했습니다.
- 한 일 — 업로드 시점에 크기와 형식을 검사하고, 사용자에게 이유를 알려 주는 응답을 추가했습니다.
- 결과 — 잘못된 사진은 업로드 직후 이유와 함께 거절됩니다.

### 확인 화면 — 인식 결과를 고칠 수 있는 초안 화면
- 문제 — 인식이 틀려도 사용자가 고칠 방법이 없었습니다.
- 한 일 — 인식된 금액과 상호를 보여 주고 직접 고칠 수 있는 화면 초안을 만들었습니다.
- 결과 — 화면에서 값을 고쳐 저장하는 흐름까지 동작합니다. 저장 후 목록 반영은 아직 연결하지 못했습니다.

- 그 밖에 — 업로드 API 문서 보강, 시험 데이터 정리

## 기술 판단
- **보정과 인식을 한 흐름으로 묶음** — 단계별 중간 결과를 남기면 실패 지점을 바로 찾을 수 있고, 단계 하나만 바꿔 다시 시험하기 쉽습니다.
- **크기 검사를 업로드 시점에 둠** — 인식에 쓰는 시간을 아끼고 사용자가 바로 사진을 바꿀 수 있습니다.

## 문제 해결
- 흐린 사진에서 금액이 빠짐 → 원인 명암 보정이 인식 뒤에 있어 흐린 영역이 이미 사라진 상태였음 → 해결 보정을 인식 앞으로 옮김 → 확인 흐린 사진 시험 세트에서 금액이 모두 읽힘

## 진행 상황
| 기능 | 진행률 | 오늘 변화 | 남은 일 |
|---|---|---|---|
| 영수증 OCR | 약 70% | 파이프라인 통합 | 실패 경로 시험 |
| 업로드 API | 약 60% | 사진 검증 추가 | 용량 제한 설정 |
| 확인 화면 | 약 30% | 초안 화면 | 저장 후 목록 연결 |

## 다음 할 일
- 저장한 결과가 목록에 바로 나오도록 연결하기
- 두 기능의 실패 경로 시험 보강하기

## 포트폴리오 문장
- 영수증 OCR의 보정·인식 단계를 하나의 파이프라인으로 묶고 보정 순서를 바로잡아, 흐린 사진에서 금액을 못 읽던 문제를 해결했습니다.
- 업로드 시점 검증을 추가해 잘못된 사진이 인식 단계까지 가지 않게 했습니다.
````

## 예시 2 — 작은 날

````text
# 2026-10-02 · 로그인 만료 시간 버그 수정

## 핵심 요약
- 로그인 세션이 설정한 시간보다 일찍 끊기던 버그를 고쳤습니다.

## 한 일
### 로그인 — 세션 만료 시간을 설정값대로 적용
- 문제 — 만료 시간을 1시간으로 설정했는데 사용자가 30분 만에 로그아웃됐습니다.
- 한 일 — 만료 시간을 분 단위로 읽는 부분을 찾아 설정값의 단위와 맞췄고, 같은 경우를 시험으로 고정했습니다.
- 결과 — 설정한 시간만큼 로그인이 유지됩니다.

## 진행 상황
| 기능 | 진행률 | 오늘 변화 | 남은 일 |
|---|---|---|---|
| 로그인 | 약 85% | 세션 만료 버그 수정 | 비밀번호 재설정 |

## 포트폴리오 문장
- 세션 만료 시간의 단위 불일치를 찾아 바로잡고 시험으로 고정해, 로그인이 설정한 시간만큼 유지되게 했습니다.
````
