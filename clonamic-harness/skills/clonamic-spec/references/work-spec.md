# 작업명세서

사용자의 의도와 할 일을 실행 전에 맞추는 문서다. 무엇을 할지(요구)와 무엇이 끝나야 하는지(산출·완료)를 고정한다. 채팅에만 쓰고 파일로 만들지 않는다.

## 언제 쓰나

- 의도가 아직 맞춰지지 않았을 때 쓴다. 새 작업의 첫 요청은 보통 여기에 해당한다.
- 의도가 이미 맞춰졌으면 쓰지 않는다. 바뀌는 것이 있는 작업은 개발명세서 하나로 가고, 읽기와 설계만이면 바로 한다. 할 수 있으면 이 길을 고른다.
- 의도가 맞춰졌다는 것은 사용자의 요청이나 고쳐 준 내용만으로 아래 세 가지가 모두 분명하다는 뜻이다.
  - 무엇: 만들거나 바꿀 대상과 결과가 이름으로 정해졌거나, 저장소를 읽으면 하나로 정해진다.
  - 범위: 항목과 수량이 정해져 있고, "등", "정리", "개선"처럼 끝이 열린 말이 남아 있지 않다.
  - 완료: 사용자가 자기 기준이라고 알아볼 완료 확인 방법을 바로 쓸 수 있다.
- 셋 중 하나라도 해석이 갈리고 그 차이가 결과를 바꾸면 맞춰지지 않은 것이다.
- 사용자가 작업명세서를 달라고 하면 의도가 맞춰졌어도 쓴다.
- 쓰지 않는다: 질문, 설명, 조회, 검토, 상태 확인, 이미 승인된 경계 안의 재시도와 짧은 후속.
- 승인 전에는 파일, 설정, 코드를 만들거나 고치거나 지우지 않는다. 읽기는 자유다. 쓰기보다 읽기가 싸므로 현재 동작과 흐름을 먼저 충분히 읽고 파악한 뒤 명세서를 쓴다. 읽은 것을 요청과 상관없는 제안이나 작업으로 넓히지 않는다.

## 형식

```text
# 작업명세서

프롬프트: 사용자가 보낸 요청. 짧으면 그대로, 길면 핵심 문장을 그대로 옮긴다.
해석: 그 요청을 지금 저장소와 상황에 맞게 다듬은 의도 한두 문장.

요구1: 사용자가 시킨 일. 수량과 대상은 그대로 적는다.
산출1: 끝나면 남는 파일, 답, 상태.
완료1: 산출1이 맞는지 확인하는 방법.
제외1: 이번 작업에서 하지 않을 일.

현재 상태: 지금 저장소와 설정이 어떤지.
기존 흐름: 이 일이 지금 어디서 어디로 가는지.
가정: 확실하지 않아 기본값으로 정한 것. 없으면 "없음".
위험: 승인하면 생길 수 있는 손실이나 범위 이탈.
복구: 잘못되면 무엇을 어느 상태로 되돌리는지.
충돌: 없음
개발명세서: 다음에 정할 구현 선택. 바꿀 것이 없으면 "쓰지 않음".

승인 대기 — 작업명세서 (승인:XXXXXX)
```

- 이름은 작업명세서로 고정한다. 버전, 단계 번호, 다른 이름을 붙이지 않는다.
- 각 줄은 그 줄만 읽고 끝났는지 판단할 수 있게 쓴다.
- 항목이 여러 개면 요구1, 요구2처럼 번호를 붙이고 같은 번호끼리 대응시킨다(요구1 → 산출1 → 완료1). 이 번호는 개발명세서의 변경·검증·복구와 보고서의 결과까지 그대로 이어진다.
- 해석이 갈리는 곳은 따로 묻지 않고 `가정:`에 기본값으로 적는다. 사용자는 틀린 곳만 고치면 된다.
- 충돌이 없으면 `충돌: 없음`이라고 쓴다. 충돌이 있으면 한 줄에 대상, 계획, 관례, 승인 시 기본값을 모두 쓴다.
- 맨 위의 프롬프트·해석 줄로 요청이 제대로 읽혔는지 사용자가 먼저 확인한다. 해석이 틀렸으면 그 줄만 고치면 된다.
- 마지막 줄은 항상 `승인 대기 — 작업명세서 (승인:코드)`이다.

## 예시

```text
# 작업명세서

프롬프트: 설정에 다크 모드 넣어 줘. 껐다 켜도 유지되게.
해석: 설정 화면에 라이트/다크 전환 토글을 하나 넣고, 고른 값을 저장해 다음 실행에도 적용한다.

요구1: 설정 화면에 다크 모드 토글을 추가한다.
요구2: 고른 테마를 다음 실행에도 유지한다.
산출1: 설정 화면의 토글 1개.
산출2: 저장된 테마 값.
완료1: 토글을 누르면 화면 테마가 바로 바뀐다.
완료2: 앱을 다시 켜도 마지막 선택이 유지된다.
제외1: 다른 화면의 색상 정리.

현재 상태: 테마는 라이트로 고정, 설정은 settings.json에 저장.
기존 흐름: 앱 시작 → settings.json 읽기 → 화면 그리기.
가정: 시스템 테마 따라가기는 넣지 않는다.
위험: settings.json 형식이 바뀌면 기존 설정을 못 읽을 수 있다.
복구: settings.json과 바꾼 코드를 git으로 되돌린다.
충돌: 없음
개발명세서: 테마 값 저장 키와 토글 위치.

승인 대기 — 작업명세서 (승인:3F9A0C)
```

## 승인과 수정

- 한 작업의 승인은 많아야 두 번(작업명세서, 개발명세서)이다. 세 번째 승인은 어떤 경우에도 없다.
- 승인은 대기 중인 명세서에 대한 사용자의 분명한 동의다("승인", "진행" 등). 질문이나 부분 의견은 승인이 아니다.
- 승인은 `승인` 또는 `승인:코드`로 한다. 코드는 명세서마다 새로 만드는 영문 대문자·숫자 6자리다. 백틱, 전각 콜론(：), 앞뒤 공백, 소문자도 받는다. 대기 중인 명세서는 늘 하나라서 코드 없이 `승인`만 보내도 된다. 코드가 대기 중인 명세서와 다르면 승인이 아니고, 한 줄로 알린다.
- 사용자가 틀린 곳을 고쳐 주는 것은 의도를 맞추는 일이고, 승인 횟수를 늘리지 않는다.
  - 고친 뒤에도 무엇·범위·완료 중 해석이 갈리는 곳이 남으면 작업명세서를 고쳐 다시 낸다.
  - 고친 내용으로 의도가 맞춰졌으면 작업명세서를 다시 내지 않는다. 바뀌는 것이 있으면 바로 개발명세서를 내고(요구·완료 줄을 맨 위에 옮겨 적는다), 읽기와 설계만이면 바로 한다. 승인은 한 번으로 끝난다.
- 승인 대기 중인 명세서는 늘 하나다. 새 명세서를 내면 이전 명세서는 무효다.

## 승인 뒤 규칙

- 읽기와 설계만이면 바로 한다. 개발명세서는 쓰지 않는다.
- 파일, 설정, 코드, 배포, 공개, 보호 명령이 있으면 개발명세서를 한 번 쓴다. 이것이 마지막 승인이다.
- 승인된 작업명세서를 다시 쓰거나 다시 승인받지 않는다. 개발명세서를 내기 전에 사용자가 요구를 바꾸면 바뀐 요구를 개발명세서 맨 위에 적고 그 승인 하나로 간다.
