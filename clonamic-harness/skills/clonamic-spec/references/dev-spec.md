# 개발명세서

요구를 어떻게 바꾸고(변경) 어떻게 증명할지(검증) 실행 전에 고정하는 문서다. 한 작업의 마지막 승인이고, 의도가 맞춰진 작업에서는 유일한 승인이다. 채팅에만 쓰고 파일로 만들지 않는다.

## 언제 쓰나

- 파일·코드·설정·배포·공개·보호 명령이 있는 작업에서, 대상을 바꾸기 직전에 한 번 쓴다.
- 길은 두 가지다.
  - 의도가 이미 맞춰졌을 때: 작업명세서 없이 바로 쓰고, 맨 위에 요구·완료 줄을 적는다. 승인 한 번으로 끝난다. 할 수 있으면 이 길을 고른다.
  - 작업명세서가 승인된 뒤: 승인된 요구를 그대로 받는다. 두 번째이자 마지막 승인이다.
- 의도가 맞춰졌다는 것은 사용자의 요청이나 고쳐 준 내용만으로 무엇(대상과 결과), 범위(항목과 수량, 열린 말 없음), 완료(확인 방법)가 모두 분명하다는 뜻이다.
- 아주 작은 변경은 한 줄 형식을 쓴다. 조건: 사용자가 대상과 변경을 이미 정확히 정했고, 프로젝트 안이며, 바로 되돌릴 수 있다.
- 쓰지 않는다: 읽기와 설계만인 작업.
- 승인 전에는 대상을 바꾸지 않는다.

## 형식

```text
# 개발명세서

요구1: 작업명세서 없이 바로 쓸 때만. 사용자가 시킨 일.
완료1: 작업명세서 없이 바로 쓸 때만. 요구1이 끝났는지 확인하는 방법.

변경1: 요구1을 위해 어느 파일을 어떻게 바꾸는지.
검증1: 완료1을 증명할 명령이나 확인할 결과.
복구1: 프로젝트 밖 변경일 때만. 백업 위치, 되돌릴 조건, 되돌리는 방법, 되돌림 확인.

파일: 만들고 고치고 지울 경로.
런타임: 바꾼 뒤 실행이 지나가는 경로.
명령·권한: 실행할 명령 종류와 필요한 권한.
실패·보안: 멈추는 조건, 비밀 값을 남기지 않을 위치.
배포: 배포하거나 공개할 대상. 없으면 "없음".

승인 대기 — 개발명세서
```

한 줄 형식:

```text
개발명세서 — 대상: 변경; 검증: 확인 방법; 복구: 되돌리는 방법
승인 대기 — 개발명세서
```

- 이름은 개발명세서로 고정한다. 버전, 단계 번호, 다른 이름을 붙이지 않는다.
- 작업명세서가 승인됐으면 요구·완료 줄은 뺀다. 작업명세서 없이 바로 쓰면 요구·완료 줄을 반드시 쓰고, 하지 않을 일이 있으면 제외1 줄도 쓴다.
- 변경N은 같은 번호의 요구N을, 검증N은 완료N을 증명한다. 번호가 어긋나면 `변경3 [요구1]`처럼 대응을 적는다.
- 프로젝트 안 변경이면 복구 줄은 뺀다. 프로젝트 밖 변경(홈 디렉터리 설정, 원격 저장소, 배포 대상 등)이면 복구N을 반드시 쓴다.
- 마지막 줄은 한 줄 형식에서도 항상 `승인 대기 — 개발명세서`이다.

## 예시

작업명세서가 승인된 뒤:

```text
# 개발명세서

변경1: src/settings/SettingsView.tsx에 테마 토글을 넣고 ThemeContext에 연결한다.
변경2: src/settings/store.ts에 theme 값 저장·읽기를 추가한다. 기본값은 light.
검증1: npm test -- SettingsView 통과, 토글을 누르면 data-theme 값이 바뀌는지 확인.
검증2: theme=dark로 저장한 뒤 앱을 다시 켜서 다크가 유지되는지 확인.

파일: src/settings/SettingsView.tsx, src/settings/store.ts, src/settings/store.test.ts
런타임: 앱 시작 → store.load() → ThemeContext → 화면.
명령·권한: npm test, npm run build. 추가 권한 없음.
실패·보안: 기존 settings.json을 못 읽으면 기본값으로 시작하고 파일을 덮어쓰지 않는다. 비밀 값 없음.
배포: 없음

승인 대기 — 개발명세서
```

의도가 맞춰져 바로 쓸 때:

```text
# 개발명세서

요구1: 로그인 실패 문구를 "이메일 또는 비밀번호가 맞지 않습니다."로 바꾼다.
완료1: 틀린 비밀번호로 로그인하면 바꾼 문구가 보인다.

변경1: src/auth/messages.ts의 LOGIN_FAILED 값을 바꾸고 테스트 기대값을 맞춘다.
검증1: npm test -- auth 통과, 실패 응답 화면에서 새 문구 확인.

파일: src/auth/messages.ts, src/auth/messages.test.ts
런타임: 로그인 요청 → 401 응답 → LOGIN_FAILED 표시.
명령·권한: npm test. 추가 권한 없음.
실패·보안: 비밀 값 없음.
배포: 없음

승인 대기 — 개발명세서
```

한 줄 형식 예시:

```text
개발명세서 — README.md 12행: `npm i` → `npm install`; 검증: git diff 1줄 확인; 복구: git checkout README.md
승인 대기 — 개발명세서
```

## 승인과 수정

- 승인은 대기 중인 명세서에 대한 사용자의 분명한 동의다("승인", "진행" 등). 질문이나 부분 의견은 승인이 아니다.
- 대기 중인 개발명세서에 사용자가 의견을 주면 고쳐서 다시 낸다. 승인 횟수는 늘지 않는다. 승인 대기 중인 명세서는 늘 하나다.

## 승인 뒤 규칙

- 승인 한 번이 허락하는 것: 적힌 대상, 작업 종류, 효과, 검증, 복구, 그리고 그 경계 안에서 고치고 다시 시험하고 적용하는 반복 전체.
- 다시 묻지 않는 것: 도구 선택, 내부 명령, 명령 횟수, 시도 횟수, 같은 경계의 재시도, 적힌 대상 안에서 구현 방식을 바꾸는 일. 방식을 바꿨으면 보고서에 한 줄로 적는다.
- 실행 중에 명령 확인, 명령 복사 요청, "계속할까요?"를 묻지 않는다.
- 비밀번호, 로그인, 생체 인증, 운영체제 확인창은 승인으로 대신하지 않는다. 사용자가 직접 하고, 그동안 승인은 그대로 유지된다.
- 적힌 경계 안에서 끝까지 한다. 명세서를 다시 쓰지 않는다. 세 번째 승인은 어떤 경우에도 없다.
- 적힌 대상 밖을 바꿔야 하거나, 적지 않은 되돌릴 수 없는 효과가 생기거나, 사용자만 정할 수 있는 일이 나오면 중간에 승인을 묻지 않는다. 경계 안에서 할 수 있는 일을 끝내고 막힘 보고서로 멈춘다.
- 사용자가 요구를 바꾸면 새 작업이다. 사용자의 메시지가 곧 맞춰진 의도이므로 작업명세서 없이 개발명세서 한 번(작으면 한 줄 형식)으로 간다.
- 끝나면 모든 완료 항목을 다시 확인하고 보고서를 쓴다.
