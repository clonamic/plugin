# 개발명세서

요구를 어떻게 바꾸고(변경), 왜 그렇게 바꾸는지(이유), 어떻게 증명할지(검증) 실행 전에 고정하는 문서다. 이유가 없으면 사용자는 바뀌는 파일 목록만 보고 승인하게 되므로, 같은 결과를 내는 다른 방법보다 이 방법이 나은 까닭을 함께 적는다. 한 작업의 마지막 승인이고, 의도가 맞춰진 작업에서는 유일한 승인이다. 채팅에만 쓰고 파일로 만들지 않는다.

## 언제 쓰나

- 파일·코드·설정·배포·공개·보호 명령이 있는 작업에서, 대상을 바꾸기 직전에 한 번 쓴다.
- 길은 두 가지다.
  - 의도가 이미 맞춰졌을 때: 작업명세서 없이 바로 쓰고, 맨 위에 요구·완료 줄을 적는다. 승인 한 번으로 끝난다. 가능하면 이 방식을 쓴다.
  - 작업명세서가 승인된 뒤: 승인된 요구를 그대로 받는다. 두 번째이자 마지막 승인이다.
- 의도가 맞춰졌다는 것은 사용자의 요청이나 고쳐 준 내용만으로 무엇(대상과 결과), 범위(항목과 수량, 열린 말 없음), 완료(확인 방법)가 모두 분명하다는 뜻이다.
- 아주 작은 변경은 한 줄 형식을 쓴다. 조건: 사용자가 대상과 변경을 이미 정확히 정했고, 프로젝트 안이며, 바로 되돌릴 수 있다.
- 쓰지 않는다: 읽기와 설계만인 작업.
- 승인 전에는 대상을 바꾸지 않는다.

## 형식

```text
# 개발명세서

## 핵심 요약
- 무엇을 어떻게 바꾸는지 한 줄. 승인 1/1(바로 쓸 때) 또는 2/2(작업명세서 다음).
- 왜: 이 변경이 필요한 원인이나 근거 한 줄.

## 요구 — 작업명세서 없이 바로 쓸 때만
- 요구1: 사용자가 시킨 일.
- 완료1: 요구1이 끝났는지 확인하는 방법.

## 변경과 검증
- 변경1: 요구1을 위해 어느 파일의 무엇을 어떻게 바꾸는지. 함수, 데이터 흐름, 순서까지.
- 이유1: 왜 이렇게 바꾸는지. 원인이나 근거(파일:줄, 동작, 수치)와, 이 방식을 고른 까닭.
- 대안1: 검토했지만 버린 방법과 버린 이유. 없으면 이 줄을 뺀다.
- 영향1: 변경1 때문에 함께 고치거나 다시 확인할 곳(호출부, 문서, 테스트, 설정). 없으면 이 줄을 뺀다.
- 검증1: 완료1을 증명할 명령이나 확인할 결과.
- 복구1: 프로젝트 밖 변경일 때만. 백업 위치, 되돌릴 조건, 되돌리는 방법, 되돌림 확인.

## 실행
- 파일: 만들고 고치고 지울 경로.
- 런타임: 바꾼 뒤 실행이 지나가는 경로.
- 명령·권한: 실행할 명령 종류와 필요한 권한.
- 실패·보안: 멈추는 조건, 비밀 값을 남기지 않을 위치.
- 배포: 배포하거나 공개할 대상. 없으면 "없음".

승인 대기 — 개발명세서 (승인:XXXXXX)
```

한 줄 형식:

```text
개발명세서 — 대상: 변경; 이유: 왜; 검증: 확인 방법; 복구: 되돌리는 방법
승인 대기 — 개발명세서 (승인:XXXXXX)
```

- 두괄식·개괄식으로 쓴다. 맨 위 `## 핵심 요약`에 무엇을 하려는지 한 줄과 승인 차례(1/2, 2/2, 1/1)를 쓰고, 나머지는 제목 아래 목록으로 쓴다.
- 이름은 개발명세서로 고정한다. 버전, 단계 번호, 다른 이름을 붙이지 않는다.
- 작업명세서가 승인됐으면 요구·완료 줄은 뺀다. 작업명세서 없이 바로 쓰면 요구·완료 줄을 반드시 쓰고, 하지 않을 일이 있으면 제외1 줄도 쓴다.
- 변경N은 같은 번호의 요구N을, 검증N은 완료N을 증명한다. 번호가 어긋나면 `변경3 [요구1]`처럼 대응을 적는다.
- 변경N은 그대로 따라 하면 같은 결과가 나올 만큼 구체적으로 쓴다. "개선한다", "정리한다"처럼 무엇을 하는지 모르는 말은 쓰지 않는다.
- 이유N은 "깔끔해서", "좋아서" 같은 말로 쓰지 않는다. 읽어서 확인한 사실이나 사용자 말에 근거하고, 작업명세서의 이유N과 어긋나면 무엇이 바뀌었는지 적는다.
- 버그 수정이면 이유N에 원인(어디서 왜 틀리는지)을 쓴다. 증상만 적지 않는다.
- 영향N은 변경N이 닿는 다른 곳을 grep이나 호출 관계로 찾아 쓴다. 검증N은 이 곳들까지 확인한다.
- 프로젝트 안 변경이면 복구 줄은 뺀다. 프로젝트 밖 변경(홈 디렉터리 설정, 원격 저장소, 배포 대상 등)이면 복구N을 반드시 쓴다.
- 마지막 줄은 한 줄 형식에서도 항상 `승인 대기 — 개발명세서 (승인:코드)`이다.
- 승인은 `승인` 또는 `승인:코드`로 한다. 코드는 명세서마다 새로 만드는 영문 대문자·숫자 6자리다. 백틱, 전각 콜론(：), 앞뒤 공백, 소문자도 받는다. 대기 중인 명세서는 늘 하나라서 코드 없이 `승인`만 보내도 된다. 코드가 대기 중인 명세서와 다르면 승인이 아니고, 한 줄로 알린다.

## 예시

작업명세서가 승인된 뒤:

```text

## 핵심 요약
- 설정 화면 테마 토글과 테마 저장을 추가한다. 승인 2/2.
- 왜: 테마가 라이트로 고정되어 있고, 고른 값을 저장할 곳이 없다.

## 변경과 검증
- 변경1: src/settings/SettingsView.tsx에 테마 토글을 넣고, 누르면 ThemeContext.setTheme을 부른다. ThemeContext는 html의 data-theme 값을 바꾸고 theme.css의 색 변수가 그 값에 따라 바뀐다.
- 이유1: 모든 화면이 theme.css의 색 변수를 쓰므로(grep 결과 12개 화면) data-theme 하나로 전체가 바뀐다.
- 대안1: 화면별 다크 스타일. 12곳을 각각 고쳐야 하고 새 화면마다 다시 필요해 버렸다.
- 영향1: SettingsView 테스트, README의 설정 설명.
- 변경2: src/settings/store.ts에 theme 값 저장·읽기를 추가한다. 기본값은 light, 모르는 값이면 light로 읽는다.
- 이유2: 다른 설정이 이미 store.ts로 settings.json에 저장되므로 같은 경로를 쓴다. 모르는 값을 light로 읽어 옛 설정 파일도 그대로 열린다.
- 검증1: npm test -- SettingsView 통과, 토글을 누르면 data-theme 값이 바뀌는지 확인.
- 검증2: theme=dark로 저장한 뒤 앱을 다시 켜서 다크가 유지되는지 확인.

## 실행
- 파일: src/settings/SettingsView.tsx, src/settings/store.ts, src/settings/store.test.ts
- 런타임: 앱 시작 → store.load() → ThemeContext → 화면.
- 명령·권한: npm test, npm run build. 추가 권한 없음.
- 실패·보안: 기존 settings.json을 못 읽으면 기본값으로 시작하고 파일을 덮어쓰지 않는다. 비밀 값 없음.
- 배포: 없음

승인 대기 — 개발명세서 (승인:8B1D4E)
```

## 승인과 수정

- 승인은 대기 중인 명세서에 대한 사용자의 분명한 동의다("승인", "진행" 등). 질문이나 부분 의견은 승인이 아니다.
- 대기 중인 개발명세서에 사용자가 의견을 주면 고쳐서 다시 낸다. 승인 횟수는 늘지 않는다. 승인 대기 중인 명세서는 늘 하나다.

## 승인 뒤 규칙

- 승인 한 번이 허락하는 것: 적힌 대상, 작업 종류, 효과, 검증, 복구, 그리고 그 경계 안에서 고치고 다시 시험하고 적용하는 반복 전체.
- 다시 묻지 않는 것: 도구 선택, 내부 명령, 명령 횟수, 시도 횟수, 같은 경계의 재시도, 적힌 대상 안에서 구현 방식을 바꾸는 일. 방식을 바꿨으면 보고서에 한 줄로 적는다.
- 실행 중에 명령 확인, 명령 복사 요청, "계속할까요?"를 묻지 않는다.
- 비밀번호, 로그인, 생체 인증, 운영체제 확인창은 승인으로 대신하지 않는다. 사용자가 직접 하고, 그동안 승인은 그대로 유지된다.
- 적힌 경계 안에서 끝까지 한다. 명세서를 다시 쓰지 않는다. 세 번째 승인은 어떤 경우에도 없다.
- 사용자 환경을 지킨다. 범위 밖 제어나 과한 자동화로 사용자의 기존 환경을 바꾸고 되돌리지 않는 것이 가장 큰 실패다. 변경N에 적지 않은 환경(홈 설정, 셸 설정, 전역 패키지와 도구, OS 설정, git 전역 설정, 다른 저장소)은 바꾸지 않는다. 시험하느라 잠깐 바꾼 것은 보고 전에 되돌린다. 프로젝트 밖을 바꾸면 복구N을 반드시 쓰고 보고서 `환경:` 줄에 적는다.
- 승인 범위 밖이 필요해도 멈추지 않는다. 범위 안의 일을 먼저 전부 끝낸다.
- 사용자 지침이 1순위다. 사용자가 "바로 진행", "다 해도 돼", "묻지 말고"처럼 명시적으로 지시했으면 그 지시가 덮는 범위 밖 일도 한다. 사용자의 명시적 지시를 이 규칙이 막는 일은 없다. 사용자 몫으로 남는 것은 비밀번호, 로그인, 생체 인증, 운영체제 확인창처럼 에이전트가 직접 할 수 없는 일뿐이다.
- 위험도가 낮은 범위 밖 일은 바로 하고 보고서의 `범위 밖 진행:`에 적는다. 위험도가 낮다는 것은 다음을 모두 만족한다는 뜻이다: 프로젝트 안이다, git이나 직접 만든 백업으로 되돌릴 수 있다, 사용자 데이터를 지우지 않는다, 사용자 전역 환경(홈 설정, 셸, 설치된 도구, OS 설정, 다른 저장소)을 바꾸지 않는다, 배포·공개·push가 아니다, 비용이나 자격 증명이 들지 않는다.
- 그 밖의 범위 밖 일은 하지 않고 보고서에 `승인 시 진행N:`으로 남긴다. 사용자가 승인하면 그 항목만 명세서 없이 바로 한다.
- 사용자가 요구를 바꾸면 새 작업이다. 사용자의 메시지가 곧 맞춰진 의도이므로 작업명세서 없이 개발명세서 한 번(작으면 한 줄 형식)으로 간다.
- 끝나면 모든 완료 항목을 다시 확인하고 보고서를 쓴다.
